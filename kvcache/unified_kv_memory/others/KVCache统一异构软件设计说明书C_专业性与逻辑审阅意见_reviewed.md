# 《KVCache统一异构软件设计说明书 C》专业性与逻辑审阅意见

## 一、审阅结论

《KVCache统一异构软件设计说明书 C》已经形成较清晰的技术主线：以 usable hit 为收益判断核心，以 QueryPlan 为跨层决策载体，以 KVAccessIntent、AttachHandle、ExtentManifest 和 Descriptor 为关键契约，以硬件 capability 和路径 telemetry 驱动异构位置选择，并通过 fallback、lease/refcount、ready bitmap 和 trace 建立正确性与可运维闭环。上述内容与《KVCache SRS需求列表 V2.1.xlsx》的主要架构方向基本一致。

但按照“为第三方专家评审 SRS V2.1 提供必要背景和评审导航”的用途衡量，当前文档仍属于质量较好的总体架构摘要，尚未完全形成可独立支撑需求评审的导读材料。主要原因是：需求完整性的结论缺少可追溯证据，验收与工程基线仅作概括，部分先进性表述超出当前软件边界，外部方案比较缺少版本与比较口径，核心对象中的“需求规定字段”和“设计建议字段”没有区分。

综合建议为：**文档可作为修订基础，但建议完成关键修改后再正式提交第三方评审。** 不建议推翻现有结构；应重点补强证据链、边界说明和 SRS 导航能力。

## 二、值得保留的内容

1. **问题主线合理。** 文档把重复 Prefill、HBM 容量墙、跨框架与跨介质语义差异、后台迁移干扰 Decode、单一 hit rate 不可解释等问题连接到 TTFT、TPOT、HBM 有效容量和 NPU 利用率，方向正确。
2. **usable hit 取代 raw hit 的论证有辨识度。** “命中、可消费、值得消费”三层判断能够解释为什么统一池不能只做外部 KV Store 查询。
3. **软硬协同位置正确。** capability matrix、registered pool、extent handle、visibility fence、SG descriptor 和 per-path telemetry 被前置到 QueryPlan 和 cost model，而非作为后期驱动优化，符合本项目的关键差异化方向。
4. **三条业务流程能够构成最小闭环。** Prefix Hit、Load/Attach、Publish/Lifecycle 覆盖了查询、消费和发布三个关键路径。
5. **核心对象表格具有详细设计输入价值。** 字段的含义、作用及生产者/消费者已经列明，明显优于只列接口名称的描述方式。
6. **阶段演进总体稳健。** P0 旁路、P1 受控闭环、P2 生产化、P3 最终交付的路径避免了高级硬件能力过早成为在线主路径。

## 三、必须修改的问题

### 3.1 技术愿景被写成无条件交付承诺

第 4.1 节使用“分布式异构虚拟内存操作系统”“彻底融合”“无感底座”“颠覆式重构”“彻底解除”“无缝支撑”等措辞。这些表达无法直接由当前 SRS 的功能与验收条目证明，也容易使评审专家误判软件边界：本项目并不替代操作系统虚拟内存、推理框架内存管理、硬件驱动或所有介质的数据一致性机制。

建议把该段改为“项目愿景”和“本期可验收目标”两层：

- 愿景：面向 KVCache 的统一异构存储与数据访问基础设施。
- 本期目标：在明确支持矩阵、场景和硬件平台范围内，实现 KVCache 的统一建模、查询、位置选择、搬运、生命周期管理和可观测闭环。
- 将“彻底、无感、无缝、颠覆式、零损耗”替换为“在满足 capability、成本模型和 SLO 准入条件时”“降低”“扩展”“支持受控接入”等可验收措辞。

** 我的审核意见和补充内容：**
* 同意将本届内容分为“项目愿景”和“本期可验收目标”两层。
* 本项目的核心目的是：针对当前AI在线推理场景下KVCache的生成、消费、维护等一系列动作，为HBM容量有限、DDR价格高企等实际业务痛点问题，利用底层UBMEM的内存语义和URMA的传输语义，提供融合HBM、本地DDR、本地SSD、远端DDR、远端SSD等统一异构内存，通过合理底层硬件的不同传输能力，建设以KVCache为中心的KVCache存储池，解决在线推理场景下的关键业务痛点问题，并达到提升TTFT、TPOT等关键业务性能指标的目的。

### 3.2 “需求完整性”结论缺少逐项证据

第 10 节直接宣称 140 余条需求“逐一托底并闭环互锁”“完全覆盖”，但没有给出需求数量的准确统计、层级分布、阶段分布、模块映射、主流程映射或未闭合风险。对于第三方评审，这是当前最关键的逻辑缺口：结论先于证据。

建议新增“需求体系与评审导航”章节，至少包括：

| 证据维度 | 应呈现内容 |
|---|---|
| 总量 | 明确为 140 条：L1 21、L2 22、L3 66、L4 31 |
| 阶段 | P0 63、P0 子集/P1 完整 4、P1 45、P2 17、P3 11 |
| 横向模块 | TM1-TM6 的职责、需求数量或代表需求、端到端作用 |
| 主流程 | Prefix Hit、Load/Attach、Publish/Lifecycle 各自由哪些需求支撑 |
| 横切属性 | 正确性、安全隔离、QoS、可观测、容错、工程基线对应哪些需求 |
| 风险状态 | 已闭合、需详细设计确认、依赖平台能力、仅旁路验证四类状态 |

不宜写“完全覆盖”作为无条件判断，宜改为：“从需求分类看已覆盖主要功能链路和横切质量属性；其完备性仍需通过需求追踪矩阵、接口一致性检查和验收可执行性审查确认。”

** 我的审核意见和补充内容：**
* 同意本评审意见
* 你先根据SRS需求列表以及其它必要支撑文件，并结合本软件的愿景和交付目标，给出第一版修订，之后我再审阅。

### 3.3 验收章节过薄，不能帮助专家评审 SRS 的可验证性

第 9 节只说“6 类 10 项指标”和“8 类工程基线”，却未列出完整名称、定义、计算口径、基线、场景及判定方式。第三方专家因此无法判断需求是否可测、指标是否存在分母歧义，以及收益是否来自统一池本身。

建议至少增加两张表：

1. 端到端指标表：指标名称、定义/公式、基线、测试工作负载、统计窗口、分位数、通过条件、关联需求。
2. 工程基线表：Workload、Framework、Hardware Capability、Network/Storage Path、KV Layout、Cost Model、Trace Schema、Failure Injection 等基线的冻结时间、输入和输出。

其中 TTFT Benefit 和 TPOT Interference 必须说明 baseline、命中前缀长度、并发度、batch、模型、硬件拓扑和统计分位数；raw/usable/stale/abandoned/fallback 必须给出互斥或包含关系，避免重复计数。

** 我的审核意见和补充内容：**
* 同意本评审意见
* 你先根据SRS需求列表以及其它必要支撑文件，并结合本软件的愿景和交付目标，给出第一版修订，之后我再审阅。

附录 B 中 tokenizer_hash、template_version、LoRA 标识、confidence、STREAMING_ATTACH 等字段具有合理性，但文档没有说明它们是 SRS 明示要求、从语义正确性推导出的设计候选，还是未来扩展字段。评审专家可能误以为所有字段均已在 V2.1 中定版。

## 四、重要改进建议

### 4.1 真实业界场景需要客观化

第 3 节的场景方向正确，但“TTFT 突破几十秒”“吞噬大部分算力”等描述没有给出适用模型、输入长度、并发配置或来源。建议把每个痛点写成“场景—现象—根因—本项目响应—边界”的固定结构；没有可靠数据时不写绝对数值，改用“可能显著增加”等审慎表述。

至少覆盖：RAG 公共知识前缀、多轮 Agent 会话、PD 解耦跨节点复用、HBM 水位压力、后台 SSD 回源干扰 Decode、多租户隔离六类场景，并明确这些是“典型行业场景”，不是本项目已验证结果。

** 我的审核意见和补充内容：**
* 本《导读》确实可以先采用模糊化的性能度量方式，但实际SRS需求中，作为验收标准的一部分，仍然需要有明确的验收场景和验收指标。
* 上述这些“典型行业场景”也确实是本项目想真正面对的实际场景，但当前还没有开展任何实际的功能开发和性能实际验证，确实无法给出具体能提升多少性能的预估。

### 4.2 Mooncake 比较需要版本、层次和证据边界

当前比较表总体公平，但缺少 Mooncake/NIXL/vLLM/SGLang 的版本或资料基准，也没有专门说明“未覆盖不等于不具备”。建议恢复独立的“比较口径与边界”小节：

- 明确比较日期、软件版本或论文/仓库基准。
- 区分 serving architecture、data movement library、framework-native cache 和本项目统一池，不做跨层次的简单优劣排名。
- 比较“公开材料明确提供的能力”和“本项目 SRS 规定的目标能力”，不能把尚未验收的目标写成已实现优势。
- Mooncake/NIXL 可作为后端或生态组件，本项目优势是把推理消费语义、KV 位置语义、硬件路径语义和业务指标语义统一起来。

** 我的审核意见和补充内容：**
* 同意本评审意见
* 你先根据SRS需求列表以及其它必要支撑文件，并结合本软件的愿景和交付目标，给出第一版修订，之后我再审阅。

### 4.3 UBMEM 与 URMA 的语义边界需定义

第 5.4 节的方向是文档中最硬核的差异点之一，但目前只有一句概括。建议明确：

- UBMEM 在本文中承担哪些内存语义：地址/对象可见性、映射、注册、访问保护或一致性边界。
- URMA 承担哪些传输语义：路径选择、提交/完成、批量传输、fence、QoS、错误和 telemetry。
- 哪些能力是平台已提供，哪些由本软件适配，哪些只是 capability flag，哪些在 P0-P3 进入主路径。
- UBMEM、URMA、RDMA、C2C、SSD/object 是并列 backend、上下层关系还是能力组合，避免表格中概念层级不一致。

** 我的审核意见和补充内容：**
* UBMEM在设计初衷预期承担的范围：KVCache前缀匹配表的访问、系统中元数据的访问；必要时，部分KVCache的传输等。具体能承担哪些任务，需要等拿到底层传输能力性能摸底表后，才能给出更加具体的适用范围。
* URMA的使用范围较为明确：KVCache在SSD、DDR、HBM、本地设备、远端设备之间的传输；

### 4.4 应增加“架构决策如何回答需求评审问题”

| 如何避免影响 Decode | traffic class、QoS、migration interlock | TM4/TM5 | TPOT Interference |
| 如何证明收益 | estimated/actual cost 和全链路 trace | TM6 | 指标对账与原因覆盖率 |
