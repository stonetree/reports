# 统一异构KVCache存储池：项目启动前关键技术原型验证与性能摸底分析报告

## 一、 原型验证目标与原则
**目标**：在进入项目全面开发前，通过构建小规模、高针对性的技术原型，对《统一异构KVCache存储池》架构中的核心创新点和高风险技术进行摸底验证。
**原则**：不追求业务全流程闭环（不提前开发全量需求），仅剥离出“技术上最不确定”、“对系统底座有颠覆性影响”以及“决定系统性能天花板”的核心机制。优先验证软硬件协同和并发正确性边界。

## 二、 待验证关键技术列表（按综合优先级排序）

综合评估技术创新度、项目影响面及技术风险度，推导出以下六大候选待验证技术：

| 优先级 | 待验证关键技术领域 | 技术创新性 / 新技术应用 | 核心风险度 | 项目影响面 |
|:---:|---|---|:---:|:---:|
| 1 | **UBMEM 内存语义在分布式元数据与前缀树中的应用** | 采用 UBMEM 取代传统 RPC 查表，实现去中心化的超低时延 `Prefix Hit` 匹配 | 高 | 决定 TTFT 基础开销与元数据查询性能天花板 |
| 2 | **基于 Load-vs-Recompute 收益模型的拓扑感知动态准入** | 将静态“命中即加载”升级为实时的 `T_load < T_recompute` SLO 代价评估与实时回退机制 | 中 | 决定 KVCache 调度是“正收益”还是“负优化” |
| 3 | **碎片化 KV 到 Descriptor 硬件数据流的编译转换** | 将上层（如 vLLM PagedAttention）不连续小块编译为 URMA/RDMA 支持的 Scatter-Gather 批量描述符 | 高 | 决定数据面底层的传输吞吐和网络/CPU提交开销 |
| 4 | **KVCache 并发跨层迁移的 Visibility Fence 与 Lease 机制** | 分布式环境下的 exactly-once 语义、对象 ready 状态及租约 (Lease/Refcount) 的生命周期强互锁 | 极高 | 决定并发数据正确性（防止读脏数据、悬空指针与泄漏） |
| 5 | **前后台数据流在底层硬件中的 QoS 隔离与干扰控制 (Interlock)** | 通过 Traffic Class 控制后台降级/回源 KV 流，保障其不阻塞前台 Decode (TPOT) 关键网络和 PCIe 队列 | 中 | 决定系统并发长尾延迟 (P99) 与核心业务 SLO 稳定性 |
| 6 | **远端 SSD / 本地 NVMe 上的 Log-structured 布局与直接预取** | 结合 GDS/直接存储访问与 Log-structured 聚合写入，避免海量小 KV 导致 SSD 读写风暴与元数据膨胀 | 中 | 决定超长上下文容量扩展成本与大 I/O 效率 |

## 三、 候选待验证技术详细分析与验证方案

### 1. UBMEM 内存语义在分布式元数据与前缀树中的应用 (Priority: 1)
* **候选理由**：KVCache 调度的第一步是查表（判断是否有可复用的前缀缓存）。如果查表本身耗时过长，就会吞噬远端复用带来的 TTFT 收益。引入 UBMEM 内存语义实现分布式元数据共享，属于底层架构的重大创新，但也面临可见性屏障、锁机制和异常处理的硬件成熟度风险。
* **验证方案**：
    * 剥离实际 KVCache 数据加载，纯粹构造千万级别的 KVCache 索引/前缀哈希表；
    * 采用 UBMEM 并发读写更新该全局目录，验证查询时延（期望微秒级别）和并发更新的一致性。
* **验收指标**：UBMEM P50/P99 读取时延；跨节点状态可见性的更新时延；异常断联情况下的超时与隔离感知能力。

### 2. 基于 Load-vs-Recompute 收益模型的拓扑感知动态准入 (Priority: 2)
* **候选理由**：本项目架构的核心思想在于“提升可用命中（Usable Hit），坚决放弃无效命中”。在发现物理命中后，系统必须计算加载代价是否优于直接计算（Recompute），防止遇到网络拥塞、设备过载时强行加载而导致 TTFT 飙升。由于这属于纯粹且极易出错的软算法控制逻辑，必须及早通过原型验证。
* **验证方案**：
    * 编写 Cost Model 的微缩模拟器模块，在测试脚本中动态注入不同层级的传输延迟、当前 HBM 水位与 Deadline；
    * 验证算法引擎能否在 `LOAD_TO_HBM`, `DIRECT_VIEW` 与 `RECOMPUTE_FALLBACK` 模式之间完成毫秒级快速切换。
* **验收指标**：代价模型评估本身耗时 (<100us)；边界异常场景（拥塞、超时）下系统能否 100% 触发重算回退 (Fallback)。

### 3. 碎片化 KV 到 Descriptor 硬件数据流的编译转换 (Priority: 3)
* **候选理由**：主流推理框架（如 vLLM, SGLang）为优化内部显存管理，HBM 中的 KV 对象存在高度碎片化现象（例如 16 token 的细粒度 Block）。直接用这些非连续的小碎片触发远端 URMA/RDMA 传输会导致巨大的 DMA/网络连接建立开销。验证统一 Descriptor Compiler 机制是否能够实现有效的数据聚合是传输性能达标的前提。
* **验证方案**：
    * 构建 `ExtentManifest` 原型模块，实现将几千个离散的虚拟 KV block 地址快速聚合并映射为 `Scatter-Gather` (SG) 列表；
    * 压测底层 URMA/RDMA 硬件，在 Scatter-Gather 模式下传输海量小块，对比它与单一连续大块的有效带宽占比。
* **验收指标**：百万级别小块聚合编译的 CPU 额外开销；底层网卡在 Scatter-Gather (批量离散块) 下的吞吐能否达到理论峰值带宽的 80% 以上。

### 4. KVCache 并发跨层迁移的 Visibility Fence 与 Lease 机制 (Priority: 4)
* **候选理由**：该技术是系统正确性的最后一道防线。当远端 Prefill 产生 KV 并推送给 Decode 节点，或系统内部发生各存储介质 (HBM/DDR/SSD) 间对象的淘汰降级时，若 Decode 端读到了未完整下刷的 KV，或者正在被高频引用的 KV 被后台 GC 误清理，将直接导致模型推理出乱码幻觉或引擎 Crash。
* **验证方案**：
    * 构造超高并发的 生产者-迁移者-消费者 模型队列，注入大量人工并发抢占行为和时延抖动；
    * 验证 Ready Bitmap、Refcount (引用计数)、原子 Tombstone 和 Visibility Fence (内存可见屏障) 是否会发生崩溃或逻辑不一致。
* **验收指标**：千万次并发读、写、迁移交叉压测场景下，读脏数据、悬挂指针 (Dangling Reference) 的发生率为 0；租约申请和释放的 CPU 等待开销限制在规定容忍范围内。

### 5. 前后台数据流在底层硬件中的 QoS 隔离与干扰控制 (Priority: 5)
* **候选理由**：在一个统一的异构池里，后台任务（如向 DDR/SSD 驱逐历史不活跃 KV 以腾出 HBM）会产生极高的写出流量（Write-back 风暴）。如果无法对这部分流量加以限制，其将与前台 Decode 计算的短平快 KV 读取行为争夺有限的 PCIe 通道与网卡队列，导致 TPOT（每输出 Token 时延）产生致命的抖动尖刺 (Tail Spike)。
* **验证方案**：
    * 持续向底层设备压入全速负载（模拟疯狂驱逐行为），在此恶劣环境中发送模拟的前台 Decode 级敏感 KVCache 数据读取；
    * 开启底层硬件配置或软件层的 Traffic Class / 令牌桶限流。
* **验收指标**：后台业务满载状态下，前台读取链路的 P99 传输时延较绝对空闲时退化不超过规定阈值（例如不超过 20%），且尾延迟尖刺发生率大幅下降。

### 6. 远端 SSD / 本地 NVMe 上的 Log-structured 布局与直接预取 (Priority: 6)
* **候选理由**：使用 SSD 是实现廉价、海量长上下文 (Long Context) 缓存的核心手段。但 SSD 介质先天不适宜海量随机零碎小块的反复擦写（容易引发写入放大、寿命短缩及 I/O 拥塞）。验证基于日志结构 (Log-structured) 追加写，以及后续通过类似 GDS 技术绕过 CPU 直接将大块日志预取回 HBM 是成功运用 SSD 的基石。
* **验证方案**：
    * 利用 FIO 等压测工具模拟碎片化的 KVCache 卸载，比对“随机小块直接追加写入”与“基于内存聚合为大日志块 (MB 级) 再异步落盘”的 IOPS 与有效吞吐表现。
* **验收指标**：SSD 写放大比例显著降低；支持高频、并发大块异步写入和快速读取操作，且不会阻塞主线程调度。

## 四、 结论与建议
上述候选验证技术严格剥离了传统软件开发中的“常规增删改查”和简单的“外部框架 API 封装”，直击 **统一异构KVCache存储池** 系统底层在时延、并发、吞吐以及软硬件结合部的技术盲区。
建议在项目正式启动全部 L1-L4 层模块详细设计与编码之前，由核心架构师或基础设施团队抽出专项时间（预估 2-3 周）构建上述最小技术原型闭环（PoC）。提前跑通上述六项关键技术，即可极大程度上扫清架构实现上的颠覆性未知风险，为项目主体的高质量、按期交付保驾护航。
