## 第 0 部分：大模型推理与 KVCache 底层原理

### 0.1 传统后端服务 vs 大模型推理：从无状态计算到自回归逐字生成

在传统后端服务（如 Web API、微服务）中：
- 客户端发起一次请求，服务端调用 CPU 计算、查询数据库并生成完整响应返回。请求处理过程通常是**无状态或短生命周期的会话状态**，单请求内存开销小且处于固定区间。

在大模型（LLM，Large Language Model）自回归推理中：
- 客户端输入一段提示词（Prompt，例如输入一段 5,000 字的技术文档并要求进行总结）；
- 大模型无法一次性输出全部结果，而是通过**自回归（Autoregressive）**方式，逐个生成 Token（1 个 Token 约等于 0.75 个汉字或英文单词）：
  - 第 1 步：输入 5,000 个 Prompt Token $\rightarrow$ 经过神经网络前向计算生成第 1 个输出 Token；
  - 第 2 步：将前序 5,000 个 Prompt Token 与第 1 个输出 Token 拼接 $\rightarrow$ 计算生成第 2 个输出 Token；
  - 第 3 步：拼接历史所有输入与已输出 Token $\rightarrow$ 计算生成第 3 个输出 Token；
  - 循环迭代，直至生成结束符（EOS）。

整个推理过程在物理硬件上分为两个阶段：

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                               大模型自回归推理的两大物理阶段                             │
├────────────────────────────────────────┬─────────────────────────────────────────────────┤
│ 阶段一：Prefill (输入理解 / 首字预计算)│ 阶段二：Decode (逐字生成 / 解码阶段)             │
├────────────────────────────────────────┼─────────────────────────────────────────────────┤
│ • 输入：Prompt 的全部 N 个输入 Token   │ • 输入：前一个 Token + 历史全部上下文           │
│ • 特征：批量矩阵乘法，一次性并发计算   │ • 特征：每次仅计算 1 个 Token，循环执行数百次   │
│ • 瓶颈：【算力受限 (Compute-Bound)】   │ • 瓶颈：【显存带宽受限 (Memory-Bandwidth)】     │
│ • 核心指标：TTFT (Time To First Token, │ • 核心指标：TPOT (Time Per Output Token,        │
│   首字生成延迟 / 首 Token 响应时间)    │   每个输出 Token 的生成耗时 / 单字生成延迟)     │
└────────────────────────────────────────┴─────────────────────────────────────────────────┘
```

### 0.2 什么是 KVCache？为什么注意力计算会引发显存容量瓶颈？

在 Transformer 神经网络的自注意力机制（Self-Attention）中，模型在计算当前 Token 时，必须与历史所有 Token 计算注意力关联度：
$$\text{Attention}(Q, K, V) = \text{Softmax}\left(\frac{Q \cdot K^T}{\sqrt{d_k}}\right) \cdot V$$
其中：
- $Q$ (Query / 查询张量)：代表当前正在计算的 Token 特征；
- $K$ (Key / 键张量) 与 $V$ (Value / 值张量)：代表历史所有 Token 在各神经网络层计算出的激活特征张量。

**【若不使用缓存的计算开销】**：
如果每生成 1 个新 Token，都要把历史所有 Token 重新执行一次神经网络前向计算，则生成第 $N$ 个 Token 的计算复杂度将达到 $O(N^2)$。当 Prompt 长度达到 32K 时，重复计算会迅速耗尽 NPU/GPU 算力，导致推理延迟急剧上升。

**【KVCache 机制】**：
为了避免重复计算，系统把历史每个 Token 在各神经网络层计算得出的 $K$ 向量与 $V$ 向量缓存在高带宽显存 (HBM, High Bandwidth Memory) 中，这部分缓存即为 **KVCache（大模型注意力键值缓存）**。
后续生成新 Token 时，硬件仅需计算当前 1 个 Token 的 $Q$，随后直接读取显存中已缓存的 $K, V$ 张量进行注意力计算，计算复杂度由 $O(N^2)$ 降为 $O(N)$。

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                             KVCache（键值缓存）的工作机制原理                            │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                          │
│   Prompt Tokens (例如 4096 tokens)                                                       │
│   ┌──────┬──────┬──────┬──────┬──────┐                                                   │
│   │ tok1 │ tok2 │ tok3 │ ...  │tok4096│                                                  │
│   └──────┴──────┴──────┴──────┴──────┘                                                   │
│       │      │      │            │                                                       │
│       ▼      ▼      ▼            ▼      Prefill 计算阶段（一次性算完）                   │
│   ┌─────────────────────────────────────────────────────────────────┐                    │
│   │ 计算出每个 Token 的 Key 张量与 Value 张量，存入显存 (HBM)       │                    │
│   └─────────────────────────────────────────────────────────────────┘                    │
│                                      │                                                   │
│                                      ▼                                                   │
│   ========================= HBM 显存中的 KVCache =======================                 │
│   [ Layer 0: K_tok1..4096 , V_tok1..4096 ] ──► 占用显存 (如 320 KB/token)                │
│   [ Layer 1: K_tok1..4096 , V_tok1..4096 ]                                               │
│   [ Layer ... ]                                                                          │
│   [ Layer 63: K_tok1..4096 , V_tok1..4096 ]                                              │
│   ======================================================================                 │
│                                      │                                                   │
│                                      ▼  Decode 阶段（生成第 4097 个字）                  │
│   当前新字 tok4097 ──► 只算 1 个 Q ──► 直接读取显存缓存的全部 K, V ──► 吐出 tok4098      │
│                                                                                          │
│ 收益：消除了历史 Token 的重复前向计算，显著降低了后续 Decode 阶段的算力消耗。            │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

**【KVCache 带来的显存容量挑战】**：
KVCache 虽然减少了重复计算，但显著占用了显存空间：
- 以 **Qwen2.5-72B (MHA 多头注意力)** 模型为例：单个 Token 的 KVCache 约占用 **320 KB** 显存；
- 单个 32K 上下文长度的请求，仅 KVCache 需占用显存：
  $$32\text{K} \times 320\text{ KB} \approx 10\text{ GB}$$
- 一台 8 卡国产 NPU 服务器（每卡 64GB HBM，整机总显存 512GB）：
  - 模型权重本身占用约 144GB；
  - 剩余可用显存约 300GB；
  - 单机最多仅能支持约 30 个 32K 长度的并发请求，进一步增加并发极易因显存不足触发 OOM（Out Of Memory）。

### 0.3 为什么需要“前缀复用 (Saved-Prefill)”与“PD 分离”？

#### 1. 前缀复用 (Prefix Caching / Saved-Prefill)
在实际业务场景（如多轮对话、代码助手、企业知识库检索、Agent 协作）中，不同请求往往包含**相同的前缀内容**（例如长达数万 Token 的系统提示词、行业知识库文档或公共代码库）。
- **若不复用缓存**：每次收到新请求，即便前 32K 提示词完全相同，硬件也需完整重新执行一次 Prefill，耗时数秒，造成算力浪费并拉长首字响应时延 TTFT；
- **前缀复用方案**：首个请求完成 Prefill 后，系统将计算出的 KVCache 存储到底座存储池中。后续具有相同前缀的请求到达时，**直接从存储池加载 KVCache 至显存，跳过神经网络重算**，实现 **Saved-Prefill（首字生成预计算节省）**；
- **业务收益**：TTFT 由数秒缩短至数百毫秒，集群整体算力吞吐显著提升。

#### 2. PD 分离 (Prefill-Decode Disaggregation)
- **资源冲突问题**：Prefill 阶段重在算力吞吐（占满矩阵计算单元），Decode 阶段重在显存访存带宽（每次生成均需读取大容量 KVCache）。若将两者混跑在同一物理计算卡上，Prefill 的突发计算会打断并阻塞 Decode 线程，导致单字生成耗时 (TPOT) 出现明显波动；
- **PD 分离架构**：将集群节点划分为 Prefill 节点与 Decode 节点：
  - **Prefill 专职节点**：专注处理长 Prompt 输入理解，计算完成后将 KVCache 通过高速网络传输至存储池或 Decode 节点；
  - **Decode 专职节点**：加载 KVCache 并专注执行逐字生成，保障推流平稳；
  - **核心支撑**：该架构高度依赖一套低时延、高吞吐、支持零拷贝的分布式 KVCache 传输与分层存储底座。

### 0.4 开源软件方案瓶颈与本架构重构要点

针对 KVCache 的管理与传输，业界已有代表性开源实现：
1. **vLLM**：提出 PagedAttention（类似操作系统的虚拟内存分页机制，将连续的 KVCache 拆分为离散物理 Block 进行管理），但其原生设计主要面向单机单卡，跨节点共享与分层存储能力较弱；
2. **Mooncake**：使用 RDMA 网络在节点间传输 KVCache，初步实现了分布式存储与传输解耦。

在深入分析开源 Mooncake 后，我们发现其存在以下 5 个关键性能瓶颈，这也是本架构进行深度重构的核心动因：
1. **Host CPU 内存拷贝开销大**：开源方案在传输数据时，数据流经 Host CPU 内存（`NPU HBM -> CPU DDR -> 网卡`），导致高吞吐传输时 CPU 成为性能瓶颈，无法充分发挥高速网卡带宽；
2. **控制面协议序列化开销高**：采用 Python 字典与消息中间件打包离散物理 Block 地址，序列化与解析耗时达到数毫秒，阻塞控制流；
3. **缺少动态选路导致搬运开销高于重算**：开源方案无论网络当前是否拥塞、数据量大小均尝试网络拉取。当网络繁忙时，网络拉取 KVCache 的耗时可能超过本地直接重算，导致端到端时延反而增加；
4. **张量并行 (TP=8) 缺少跨卡同步**：大模型通常采用 8 卡张量并行。若各卡独立查询缓存且动作不一致（部分卡命中、部分卡未命中），后续执行集合通信（AllReduce）时会因状态不一致导致进程挂死；
5. **前后台流量缺少 QoS 隔离**：后台向存储池换出冷 KV 的大流量 I/O 会抢占前台在线推理的通信与显存带宽，导致在线请求的 TPOT 尾部时延劣化。

基于上述问题，我们设计了**面向国产 AI 硬件的统一异构 KVCache 存储与调度底座 (Unified KV)**，通过软硬件协同优化突破上述物理瓶颈。

## 第 1 部分：提前原型验证的工程定位与阶段划分

### 1.1 提前原型验证的工程定位

大模型推理加速系统涉及计算卡、高速互联、网卡驱动、操作系统内核与存储介质的紧密协同。若在未摸清底层硬件物理特性的情况下直接进行大规模工程开发，容易在后期遇到难以调优的物理瓶颈。

因此，我们确立了提前原型验证的实施准则：
1. **采用微基准 (Micro-Benchmark) 探明物理边界**：通过精简的 C++/Python 代码，剥离复杂的业务逻辑，直接对底层通信（URMA 通用远程直接内存访问、UBMEM 统一总线内存直通共享协议）、异步 I/O (`io_uring`) 与 POSIX 共享内存等接口进行极限性能摸底；
2. **坚持以实测数据为准绳**：各项技术方案均设立清晰的量化判定门限（Go / No-Go），杜绝主观推断；
3. **明确技术主路径与备选方案**：通过实测检验各项技术路线的可行性，确定系统实现的主路径，对存在强外部依赖或收益不明确的特性及时设立纯软替代方案。

#### 1. 【痛点背景与验证必要性】
- **核心疑问**：在实际业务场景下，从存储池拉取历史 KVCache 是否稳定快于本地 NPU 直接重算？

#### 4. 【架构决策】
- **若达标**：证明外置 KVCache 存储底座具备明确的加速收益，测得的基准数据将作为 PVT-04 动态调度器的初始代价参数；
- **若不达标**：明确在低复用率（如 $<30\%$）或极短文本下不执行网络拉取，调度器应主动回退至本地重算。

### PVT-01：Host CPU 零数据拷贝传输底座与硬件能力矩阵 (CapabilityMatrix)

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-01 │ 优先级: 🟡 P1 (底座支撑) │ 对应阶段: E1 底座打通                       │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-01/ (raw_trans_bench.cc, host_touch_monitor.py)             │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **痛点分析**：传统方案在跨节点搬运数据时往往经过 Host 内存中转（`NPU HBM -> CPU DDR -> 网卡`）。在高速网络并发下，CPU 需执行大量 `memcpy`，占用大量算力与总线带宽，导致 CPU 利用率打满；
- **本方案设计**：确立 **Host CPU 零数据拷贝（CPU 仅负责下发控制指令，不参与正文数据搬运，Host Payload Touch Bytes 严格为 0）**，使数据直接在 NPU HBM 与网卡 DMA 之间直达传输（Peer-to-Peer）。

#### 2. 【核心验证指标与门限】
- 通过 Linux eBPF 内核探针验证数据传输过程中 Host CPU 数据搬运字节数严格为 0；
- 在高速线速传输下，Host CPU 利用率增量 $< 5\%$；
- 自动探测并输出各物理链路参数表（`capability_matrix.json` 硬件能力矩阵）。

#### 3. 【底层技术机制】
- **P2P 显存锁定与注册**：通过底层驱动接口锁定显存物理页（Pinning），将 HBM 物理地址注册到网卡 Memory Region (MR) 中；
- **eBPF 监控探针 (`host_touch_monitor.py`)**：利用 eBPF 挂载内核 `memcpy`、`copy_to_user` 等函数，统计传输期间是否存在正文数据流经 CPU。

#### 4. 【架构决策】
- **若达标**：将全链路 CPU 零拷贝确立为主路径，CPU 仅承担微秒级控制面调度；
- **若不达标**：若硬件驱动暂不支持直接 P2P，则使用固定大页内存（Pinned DDR Pool）作为环形缓冲区，严格限制 CPU 拷贝次数。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text
> 我正在开展 PVT-01 CPU 零拷贝验证：
> 1. 阅读 ./原型验证代码/PVT-01/host_touch_monitor.py，配置 eBPF 监控环境；
> 2. 检查 raw_trans_bench.cc 中的 DMA 内存注册逻辑；
> 3. 执行压测并运行监控脚本，验证高吞吐传输下 Host CPU 拷贝字节数是否为 0。
> ```

### PVT-02：异构框架 Layout 描述符编译器与跨节点异步流水

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-02 │ 优先级: 🔴 P0 (核心决胜) │ 对应阶段: E1 底座打通                       │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-02/ (descriptor_compiler.cc/.h, async_dag_bench.cc)         │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **痛点分析**：在 vLLM 中，显存以固定大小的 Block 离散分配。传输一个长上下文请求可能涉及数百乃至数千个离散块。开源方案使用 Python 字典与消息队列打包离散物理地址，序列化开销显著；
- **本方案设计**：我们在 C++ 层实现 **描述符编译器（DescriptorCompiler）**，使用贪心算法将相邻离散 Block 聚合为连续的 Scatter-Gather 描述符（64 字节紧凑结构体），并通过多 Stream 实现逐层计算与传输重叠的异步流水。

#### 2. 【核心验证指标与门限】
- 描述符编译与提交耗时相比 Python 序列化降低 $\ge 40\%$（由毫秒级降至 $<50\mu\text{s}$）；
- 跨节点传输与 Prefill 计算的流水重叠率 $\ge 60\%$。

#### 3. 【底层技术机制】
- **连续块贪心合并**：遍历 Block 列表，若相邻块物理地址连续则合并为一个 Extent 描述区间，将大量离散 DMA 请求合并为少量批量操作；
- **异步多 Stream 重叠 (`async_dag_bench.cc`)**：利用 NPU 计算流 (Compute Stream) 与传输流 (DMA Stream) 并行，第 0 层计算完成后立即触发传输，传输同时计算第 1 层，实现时间重叠。

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                   Layerwise 边算边传 (计算与传输异步重叠流水)                          │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 计算流 (Compute Stream):  [ 计算 Layer 0 ] ──► [ 计算 Layer 1 ] ──► [ 计算 Layer 2 ]   │
│                                  │                   │                   │             │
│                                  ▼ 触发 DMA          ▼ 触发 DMA          ▼ 触发 DMA    │
│ 传输流 (DMA Copy Stream):         [ 传输 Layer 0 ] ──► [ 传输 Layer 1 ] ──► [ 传输 L2 ]│
│                                                                                        │
│ 收益：在最后一层计算完成时，前序网络传输已大部分结束，有效掩盖了网络时延。             │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 4. 【架构决策】
- **若达标**：将紧凑 POD 描述符编译器作为跨节点通信的标准协议格式；
- **若不达标**：增加基于连续物理页池（Super-Block）的预分配机制以降低合并开销。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text
> 我正在实现 PVT-02 描述符编译器与异步流水：
> 1. 查看 ./原型验证代码/PVT-02/descriptor_compiler.cc，检查连续块合并算法边界；
> 2. 模拟不同显存碎片率下的 Block 输入并运行单元测试；
> 3. 编译 async_dag_bench，验证计算流与传输流的重叠掩盖率。
> ```

### PVT-03：远端直读 (Direct-View) vs 显存拷贝 (Copy-to-HBM) 适用边界与 ViewGuard 容错

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-03 │ 优先级: 🟡 P1 (底座支撑) │ 对应阶段: E1/E2 边界测定                   │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-03/ (view_vs_copy_bench.cc, view_guard.cc/.h)               │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **两种数据读取方式**：
  1. **Direct-View（远端直读）**：本地不分配显存，计算算子直接跨网络读取远端显存数据；
  2. **Copy-to-HBM（拷贝到本地显存）**：先通过 DMA 将远端数据一次性搬运至本地 HBM，算子再从本地高速显存读取。
- **权衡与风险**：远端直读无需将数据拷入本地显存，适合单次或极低频读取；本地拷贝虽有一开始的搬运开销并占用本地显存，但后续多次重复读取时可以直接走本地 HBM 高速访存，效率更高。因此两者存在明确的访问频次临界点。此外，若远端节点发生故障，直读操作可能引发 `SIGBUS` 异常导致进程崩溃。

#### 2. 【核心验证指标与门限】
- 测定两种方式的耗时交叉曲线，明确 Decode 阶段的适用边界；
- 验证 **ViewGuard 视图租约安全守卫机制**：在远端超时或异常断开时，本地在 $< 1\text{ms}$ 内捕获 `SIGBUS` 异常并安全回退至本地重算，保障服务稳定运行。

#### 3. 【底层技术机制】
- **交叉点测量 (`view_vs_copy_bench.cc`)**：测试在不同重读次数 $R$ 下两种模式的端到端耗时；
- **ViewGuard 异常恢复 (`view_guard.cc`)**：通过 Linux `sigaction` 注册 `SIGBUS` 信号处理函数，结合 `sigsetjmp`/`siglongjmp` 实现异常栈恢复与安全回退。

#### 4. 【架构决策】
- **架构决策**：**在单次读取的 Prefill 阶段或超大共享提示词场景下支持 Direct-View；在多次迭代读取的 Decode 阶段强制执行 Copy-to-HBM**；全链路部署 ViewGuard 防护。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text
> 我正在验证 PVT-03 访问边界与 ViewGuard 容错机制：
> 1. 查看 ./原型验证代码/PVT-03/view_guard.cc 中的 SIGBUS 信号捕获与异常恢复逻辑；
> 2. 运行 view_vs_copy_bench，绘制不同读取次数下的耗时对比曲线；
> 3. 注入网络故障，测试 ViewGuard 是否能在 1ms 内安全回退至本地重算。
> ```

### PVT-04：微秒级动态决策引擎 (QueryPlan) 与 CostEvaluator 成本模型

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-04 │ 优先级: 🔴 P0 (核心决胜) │ 对应阶段: E2 调度决策                       │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-04/ (query_plan_fastpath.cc/.h, query_plan_bench.cc)         │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **痛点分析**：集群网络负载是动态变化的。若缺乏动态决策机制而盲目拉取缓存，在网络拥塞或命中前缀较短时，网络拉取耗时可能反超本地重算耗时，产生“负加速”；
- **本方案设计**：构建微秒级**动态决策引擎（QueryPlan）**与**成本预估模型（CostEvaluator）**，在每次请求到达时实时估算拉取开销与重算开销，仅在“拉取与加载总开销 < 本地直接重算耗时”时才执行拉取，否则主动回退至本地重算。

#### 2. 【核心验证指标与门限】
- 决策引擎单次决策耗时 P99 $< 5\mu\text{s}$，吞吐支持 $\ge 100\text{K QPS}$；
- 动态选路准确率 $\ge 90\%$，负加速发生率严格 $< 1\%$。

#### 3. 【底层技术机制】
- **CostEvaluator 代价模型**：
  $$T_{\text{load}} = T_{\text{meta\_query}} + \frac{\text{DataSize}}{\text{Bandwidth}_{\text{realtime}}} + T_{\text{attach}}$$
  $$T_{\text{recompute}} = \frac{\text{HitTokens} \times \text{FLOPs\_per\_token}}{\text{NPU\_Compute\_Power}}$$
- **无锁微秒决策分支 (`query_plan_fastpath.cc`)**：使用紧凑查找表与轻量位运算，结合实时链路带宽快速完成决策。

#### 4. 【架构决策】
- **若达标**：将该动态决策引擎作为存储底座的全局调度核心；
- **若不达标**：采用预先构建的静态查找表 (Look-Up Table, LUT) 降低计算开销。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text
> 我正在开发 PVT-04 动态选路决策引擎：
> 1. 阅读 ./原型验证代码/PVT-04/query_plan_fastpath.cc 中的成本预估公式；
> 2. 编译并执行 query_plan_bench，施加 10 万 QPS 并发压测；
> 3. 统计 P50/P90/P99 决策耗时，并验证负加速拦截率。
> ```

### PVT-05：HBM-SSD 直达容量主路径与分层存储扩容 (Tiering)

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-05 │ 优先级: 🔴 P0 (核心决胜) │ 对应阶段: E2 分层扩容                       │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-05/ (tier_storage_bench.cc, benchmark_tiering.py)           │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **痛点分析**：NPU 高带宽显存 (HBM) 容量有限且成本高昂，单机通常仅有数百 GB，难以长期驻留大量历史长会话的 KVCache。需要将冷数据异步沉淀至大容量 NVMe SSD；
- **开源缺陷**：开源文件级换出方案经过了 Linux 文件系统与 CPU 内存拷贝，读写带宽较低；
- **本方案设计**：基于 Linux `io_uring` FIXED Direct I/O 机制管理 4KB 对齐的物理扇区，实现 **NPU HBM ↔ NVMe SSD 裸盘直接 DMA 交换（Payload Bypass DDR，绕过主机内存）**。

#### 2. 【核心验证指标与门限】
- NVMe 裸盘读写吞吐达到硬件物理极限的 $\ge 80\%$（相比开源文件系统 Offload 提升 $\ge 50\%$）；
- 在显存负载超载 150%~200% 时，实现平滑分层换入换出，**显存溢出 (OOM) 发生率降低 $\ge 50\%$**。

#### 3. 【底层技术机制】
- **`io_uring` FIXED Buffer Direct I/O**：预先向内核注册固定物理缓冲区，减少系统调用开销；
- **分层块分配器 (`TierBlockAllocator`)**：维护 4KB 对齐的磁盘扇区物理位图，管理数据块在 HBM 与 SSD 之间的异步迁移。

#### 4. 【架构决策】
- **若达标**：将“HBM-SSD 直达分层存储”确立为容量扩展主路径，提升集群有效缓存容量 $\ge 30\%\sim 50\%$；
- **若不达标**：排查 PCIe 控制器通道瓶颈，评估多盘软 RAID0 并发方案。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text

> 1. 查看 ./原型验证代码/PVT-05/tier_storage_bench.cc 中的 io_uring 初始化与提交逻辑；
> 2. 对比 POSIX read/write 与 io_uring Direct I/O 的读写吞吐；

### PVT-06：多维度语义一致性校验 (ConsumeEligibility) 与 TP=8 多卡状态同步 (RankConsensus)

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-06 │ 优先级: 🔴 P0 (核心决胜) │ 对应阶段: E1 一致性底座                     │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-06/ (consume_eligibility.cc/.h, rank_consensus_bench.cc)     │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **痛点一：语义失效引发脏读**：若仅根据文本字面哈希匹配缓存，一旦模型权重版本、Tokenizer 词表或系统提示词模板发生微调，错误复用旧缓存会导致模型输出异常乱码；
- **痛点二：多卡张量并行步调不一致**：在 TP=8 多卡并行时，若各卡独立查询缓存且结果不一致（部分卡命中拉取、部分卡未命中重算），后续跨卡集合通信（AllReduce）将因状态冲突发生死锁挂死。

#### 2. 【核心验证指标与门限】
- **消费资格校验引擎 (ConsumeEligibility)**：对“模型架构、Tokenizer 词表、Prompt 模板、LoRA 适配器、Ready 就绪位、租约有效性”进行 6 维语义校验，杜绝错误消费；
- **张量并行多卡状态同步机制 (RankConsensus)**：在 TP=8 并行下，多卡状态同步耗时 P99 $< 100\mu\text{s}$，杜绝集合通信死锁。

#### 3. 【底层技术机制】
- **6 维 xxHash64 校验 (`consume_eligibility.cc`)**：将多维元数据计算为 64 位整型指纹，在微秒级时间内完成精确匹配校验；
- **POSIX 共享内存多卡同步 (`rank_consensus_bench.cc`)**：在 `/dev/shm` 建立跨卡共享内存段，Rank 0 统一裁决后通过原子变量与内存屏障广播动作，确保多卡状态一致。

#### 4. 【架构决策】
- **若达标**：将 6 维语义校验与共享内存状态同步固化为分布式读取的通用准入机制；
- **若不达标**：若共享内存延迟异常，则采用主卡统一广播机制。

### PVT-07：前后台混压全链路端到端总门禁与 SemanticQoS 干扰保障

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-07 │ 优先级: 🔴 P0 (核心决胜) │ 对应阶段: E3 混压总门禁                     │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-07/ (mixed_workload_bench.py, semantic_qos_controller.py)   │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **痛点分析**：在实际生产中，前台在线推理服务（在线对话）与后台数据搬运（冷 KV 换出至存储池或从远端拉取）同时运行。后台大流量容易抢占网络与访存带宽，导致前台请求的单字生成耗时 (TPOT) 出现剧烈抖动；
- **本方案设计**：建立 **SemanticQoS（前后台服务质量保障策略）**，利用网络 RoCE 硬件优先级队列映射（前台映射高优先级队列 TC0，后台映射低优先级队列 TC1）与应用层微秒级自适应退避流控，降低后台搬运对前台在线推理的影响。

#### 2. 【核心验证指标与门限（E3 阶段总门禁）】
在真实 2 节点集群、前台在线推理 + 后台满载 I/O 混压下，满足以下量化指标：
1. 全链路首字生成时延 **TTFT 降低 $\ge 20\%$**；
2. 集群整体推理吞吐 **QPS 提升 $\ge 10\%$**；
3. 前台在线推理单字延迟 **TPOT 干扰率严格 $< 3\%$**。

#### 3. 【底层技术机制】
- **网络硬件优先级映射**：配置 RoCE 网卡 DSCP/PCP 映射，使交换机优先调度前台报文；
- **自适应令牌桶退避 (`semantic_qos_controller.py`)**：后台换出任务在感知到前台处于活跃 Decode 阶段时，自动以微秒级粒度进行速率退避。

#### 4. 【架构决策】
- **若达标**：**整个提前验证体系通过 E3 阶段总门禁**，验证了原厂软硬件协同系统在真实混压环境下的加速与抗干扰能力；
- **若不达标**：精细调整 QoS 令牌桶退避窗口与硬件队列深度配置。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text

> ```

### PVT-08：1-to-N 组播式 KV 分发：硬件多播 vs 软件分层中继 (Staging Fanout)

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-08 │ 优先级: 🟢 P2 (拓展证伪) │ 对应阶段: E1 拓扑分发                       │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-08/ (multicast_fanout_bench.cc, test_fanout_scenarios.py)   │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **典型业务场景**：
  1. **热点提示词广播**：超长系统提示词更新时需分发至集群多个 Decode 节点；
  2. **Multi-Agent 协作**：主 Agent 生成的上下文需广播给多个子 Agent；
  3. **PD 分离 1P-to-ND**：单 Prefill 节点生成的 KV 数据需推送到多个 Decode 副本。
- **物理瓶颈**：若源节点采用多次单播方式逐个发送，源端网卡上行带宽容易被迅速占满。

#### 2. 【核心验证指标与门限】
- 验证**软件分层中继转发（Staging Fanout）**拓扑相比朴素单播，源端网卡带宽占用降低 $\ge 60\%$；
- 评估软件树状中继相比交换机硬件多播的性能差异，验证系统是否可以脱离对专用硬件多播配置的依赖。

#### 3. 【底层技术机制】
- **树状分层中继 (`multicast_fanout_bench.cc`)**：源节点将数据分发给一级中继节点，再由中继节点并发接力转发给下一级节点，将源端带宽开销由 $O(N)$ 降为 $O(1)$，整网广播时间降为 $O(\log N)$。

#### 4. 【架构决策】
- **架构决策**：以纯软件树状 Staging Fanout 为默认主路径，确保系统可在标准通用商用交换机网络环境中快速部署。

> 2. 模拟 1 个源节点向 16 个目标节点广播 64MB 数据，对比单播、硬件多播与软件 Staging 的耗时与源端带宽；

### PVT-09：DPU 硬件安全加速与算力卸载 vs Raw Direct 软硬双轨协同

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-09 │ 优先级: 🟡 P1 (底座支撑) │ 对应阶段: E1 双轨协同                       │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-09/ (offload_fallback_bench.cc, inject_fault.py)            │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **企业安全诉求**：金融与政企专线环境对跨节点传输的 KVCache 有加密（AES-256）与数据校验（CRC64）要求。若全部由 Host CPU 软算，CPU 负载会迅速打满；若由 NPU 计算，会占用宝贵的模型计算算力；
- **软硬双轨设计**：
  1. **标准环境**：采用 **Raw Direct（原始直达路径）**，以纯软直达为主路径，架构精简、部署通用；
  2. **硬件增强环境**：采用 **DPU 硬件卸载路径**，由 DPU 协处理器线速完成加解密与数据校验；
  3. **高可用降级保护**：当 DPU 出现超时或故障时，系统在 $< 500\mu\text{s}$ 内平滑降级回退至 Raw Direct 路径，确保业务连续性。

#### 2. 【核心验证指标与门限】
- 测定 DPU 硬件卸载在 AES/CRC 运算上的性能收益；
- 验证在注入 DPU 故障后，系统在 $< 500\mu\text{s}$ 内完成平滑降级回退。

#### 3. 【底层技术机制】
- **双轨适配层 (`offload_fallback_bench.cc`)**：封装统一的传输接口，根据运行时硬件能力矩阵动态路由；
- **看门狗与故障注入 (`inject_fault.py`)**：模拟 DPU 响应超时，检验故障状态机与降级逻辑。

#### 4. 【架构决策】
- **架构决策**：确立以 Raw Direct 纯软直达为基础主路径、DPU 硬件卸载为可选加速轨的双轨协同体系，消除对专用硬件的单一强依赖。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text
> 我正在开展 PVT-09 DPU 双轨协同与降级回退验证：
> 1. 查看 ./原型验证代码/PVT-09/offload_fallback_bench.cc 中的双轨切换逻辑；
> 2. 运行 inject_fault.py 模拟 DPU 超时，记录故障发生到成功回退至纯软路径的微秒级耗时。
> ```

### CVT-01：显存页迁移软件 RCU 机制 vs 硬件 AtomicRemap 必要性证伪

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: CVT-01 │ 优先级: 🟢 P2 (拓展证伪) │ 对应阶段: 条件证伪项                       │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/CVT-01/ (rcu_migration_bench.cc, Makefile)                       │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【痛点背景与验证必要性】
- **技术分歧**：在后台对显存进行碎片整理或页迁移时，前台推理正在并发读取相应显存页。部分观点认为必须依赖专用硬件原子重映射（Hardware Atomic Remap）芯片才能避免读写加锁停顿；
- **证伪目标**：借鉴 Linux 内核经典的 **RCU（Read-Copy-Update，读-拷贝-更新）** 机制，采用纯软件方案实现前台并发读取零加锁停顿，评估是否可以免除对专用硬件芯片的依赖。

#### 2. 【核心验证指标与门限】
- 在 32 线程并发读取压测下，验证纯软件 RCU 方案的迁移停顿 $< 1\text{ms}$，P99 访问抖动 $< 50\mu\text{s}$。

#### 3. 【底层技术机制】
- **RCU 宽限期管理 (`rcu_migration_bench.cc`)**：后台线程先将显存页复制到新地址并通过原子 CAS 更新页表指针，旧页面等待当前所有并发读取离开宽限期（Grace Period）后再异步回收，前台读取全过程无需互斥锁。

#### 4. 【架构决策】
- **架构决策**：确立纯软件 RCU 显存整理主路径，消除对专用硬件 AtomicRemap 的硬性依赖。

#### 5. 【实战指引与 Agent 协作 Prompt】
> **💡 Prompt 模板**：
> ```text
> 我正在执行 CVT-01 软件 RCU 机制验证：
> 1. 查看 ./原型验证代码/CVT-01/rcu_migration_bench.cc 中的原子指针替换与宽限期同步实现；
> 2. 启动 32 线程并发读取压测，统计页迁移期间读取线程的单次延迟与抖动；
> 3. 输出互斥锁与软件 RCU 的性能对比表。
> ```

### 3.1 常见问题排查指引 (FAQ)

1. **编译 C++ 代码时提示缺少 `urma.h` 或 `liburma.so`：**
   - 原厂驱动通常位于 `/usr/include/` 与 `/usr/lib64/`。若当前开发机暂无实际硬件环境，可启用 Mock 模式（通过单机共享内存或内存拷贝模拟通信接口）验证上层算法逻辑，待具备硬件条件时再链接真实驱动。
2. **PVT-06 运行多进程同步时出现 `/dev/shm` 权限或段不存在错误：**
   - 检查 `/dev/shm` 挂载空间（建议 $\ge 2\text{GB}$），确认 `shm_open` 创建的文件权限为 `0666`，且多进程使用了统一的共享内存段标识。
3. **PVT-05 运行 `io_uring` 报错 `EPERM` 或 `EINVAL`：**
   - `io_uring` FIXED I/O 要求使用 `O_DIRECT` 模式打开存储设备或预分配文件，且内存地址与写入长度须严格满足 **4096 字节（4KB）物理扇区对齐**（可通过 `posix_memalign` 分配对齐内存）。
