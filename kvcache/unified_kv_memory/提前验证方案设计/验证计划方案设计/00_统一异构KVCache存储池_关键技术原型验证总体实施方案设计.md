## 第 0 部分：零基础前置：大模型推理与 KVCache 底层第一性原理

### 0.1 传统后端服务 vs 大模型推理：从无状态请求到自回归逐字生成

在传统后端开发（如 HTTP/gRPC 服务）中：
- 客户端发来一个请求，CPU 查数据库、执行业务逻辑，一次性生成响应并返回。整个过程是**无状态（Stateless）或普通会话状态**，内存占用极小且固定。

在大模型（LLM，Large Language Model）推理中：
- 客户端发来一段提示词（Prompt，例如输入了 5,000 字的文档，并提问“请总结这篇文章”）。
- 大模型**无法一次性吐出所有回答**，而是以**自回归（Autoregressive）**方式，一个字一个字（准确地说是 Token by Token，1 Token 约等于 0.75 个汉字或英文单词）依次生成：
  - 第一次计算：输入 5,000 个 Prompt Token $\rightarrow$ 计算生成第 1 个输出字；
  - 第二次计算：输入 5,000 个 Prompt Token + 第 1 个输出字 $\rightarrow$ 计算生成第 2 个输出字；
  - 第三次计算：输入 5,000 个 Prompt Token + 前 2 个输出字 $\rightarrow$ 计算生成第 3 个输出字；
  - $\dots$ 直到生成终止符。

整个推理过程被天然划分为两个性质截然不同的物理计算阶段：

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                               大模型自回归推理的两大物理阶段                             │
├────────────────────────────────────────┬─────────────────────────────────────────────────┤
│ 阶段一：Prefill (输入理解 / 首字预计算)│ 阶段二：Decode (逐字生成 / 解码阶段)             │
├────────────────────────────────────────┼─────────────────────────────────────────────────┤
│ • 输入：用户 Prompt 的全部 N 个 Token   │ • 输入：前一个 Token + 历史全部上下文           │
│ • 特征：矩阵乘法，一次性并发计算       │ • 特征：每次只计算 1 个 Token，循环执行数百次   │
│ • 瓶颈：【算力密集型 (Compute-Bound)】 │ • 瓶颈：【显存带宽密集型 (Memory-Bandwidth)】   │
│ • 核心指标：TTFT (Time To First Token, │ • 核心指标：TPOT (Time Per Output Token,        │
│   首字生成延迟 / 首 Token 响应时间)    │   每个输出 Token 的生成耗时 / 单字生成延迟)     │
└────────────────────────────────────────┴─────────────────────────────────────────────────┘
```

### 0.2 什么是 KVCache？为什么注意力计算会引发显存“内存黑洞”？

在 Transformer 神经网络的注意力机制（Self-Attention）中，模型在计算当前 Token 时，必须与历史所有 Token 计算相关性：
$$\text{Attention}(Q, K, V) = \text{Softmax}\left(\frac{Q \cdot K^T}{\sqrt{d_k}}\right) \cdot V$$
其中：
- $Q$ (Query / 查询张量)：代表当前正在生成的 Token；
- $K$ (Key / 键张量) 与 $V$ (Value / 值张量)：代表历史所有 Token 的激活特征张量。

**【如果没有缓存的灾难】**：
如果每生成 1 个新 Token，都把前面的所有 Token 重新跑一遍神经网络矩阵乘法，那么生成第 $N$ 个 Token 的计算复杂度将高达 $O(N^2)$。当 Prompt 达到 32K 时，GPU/NPU 算力会被海量重复计算彻底压垮！

**【KVCache 的诞生与机制】**：
为了消除重复计算，系统把历史每个 Token 在每一层神经网络算出的 $K$ 向量和 $V$ 向量，**完整缓存在高带宽显存 (HBM, High Bandwidth Memory) 中**，这就是 **KVCache（大模型注意力键值缓存）**。  
在后续生成新 Token 时，只需要计算当前 1 个 Token 的 $Q$，然后直接读取显存中已缓存的 $K, V$ 张量做乘法，计算复杂度瞬间从 $O(N^2)$ 降为 $O(N)$！

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                             KVCache（键值缓存）的工作机制原理                            │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                          │
│   Prompt Tokens (例如 4096 tokens)                                                       │
│   ┌──────┬──────┬──────┬──────┬──────┐                                                   │
│   │ tok1 │ tok2 │ tok3 │ ...  │tok4096│                                                  │
│   └──────┴──────┴──────┴──────┴──────┘                                                   │
│       │      │      │            │                                                       │
│       ▼      ▼      ▼            ▼      Prefill 计算阶段（一次性算完）                   │
│   ┌─────────────────────────────────────────────────────────────────┐                    │
│   │ 计算出每个 Token 的 Key 张量与 Value 张量，存入显存 (HBM)       │                    │
│   └─────────────────────────────────────────────────────────────────┘                    │
│                                      │                                                   │
│                                      ▼                                                   │
│   ========================= HBM 显存中的 KVCache =======================                 │
│   [ Layer 0: K_tok1..4096 , V_tok1..4096 ] ──► 占用显存 (如 320 KB/token)                │
│   [ Layer 1: K_tok1..4096 , V_tok1..4096 ]                                               │
│   [ Layer ... ]                                                                          │
│   [ Layer 63: K_tok1..4096 , V_tok1..4096 ]                                              │
│   ======================================================================                 │
│                                      │                                                   │

│   当前新字 tok4097 ──► 只算 1 个 Q ──► 直接读取显存缓存的全部 K, V ──► 吐出 tok4098      │
│                                                                                          │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

**【然而，代价是什么？显存容量遭遇毁灭性爆炸！】**
KVCache 虽然省了算力，但吞噬了极其恐怖的显存空间：
- 以经典的 **Qwen2.5-72B (MHA 多头注意力)** 模型为例：单 Token 的 KVCache 占用约 **320 KB**。
- 单个 32K 上下文的请求，仅 KVCache 就需要霸占：
  $$32\text{K} \times 320\text{ KB} \approx 10\text{ GB 显存！}$$
- 一台 8 卡国产 NPU 服务器（每张卡 64GB HBM，总共 512GB）：
  - 72B 模型权重本身占用约 144GB；
  - 剩余可用显存约 300GB；
  - **最多只能同时处理 30 个长文本并发请求！** 超过就会直接触发 **OOM（Out Of Memory，显存溢出奔溃）**！

### 0.3 为什么要做“前缀复用 / Saved-Prefill”与“PD 分离”？

#### 1. 前缀复用 (Prefix Caching / Saved-Prefill)
在大模型真实业务（如多轮对话助手、代码补全、法律/医疗长文档检索、企业知识库问答）中，大量请求具有**完全相同的前缀**（例如 32K 的系统提示词、行业规章制度文档或代码库仓库）。
- **传统笨做法**：每次来一个新请求，即便前 32K 提示词一模一样，GPU/NPU 也要吭哧吭哧重新跑一遍 Prefill，耗时 3~8 秒（TTFT 极长，白白浪费算力）；
- **前缀复用做法**：第一次请求跑完 Prefill 后，把这 32K 算好的 KVCache 保存到存储池中。后续所有带有相同前缀的请求进来时，**直接从存储池拉取 KVCache 注入显存，跳过神经网络重算**！这就是 **Saved-Prefill（首字生成预计算节省）**！
- **业务收益**：TTFT 从 5 秒断崖式下降到 0.2 秒，单机请求吞吐量提升数倍！

#### 2. PD 分离 (Prefill-Decode Disaggregation)
- **物理冲突**：Prefill 是算力大杀器（占满矩阵计算核心），Decode 是显存搬运工（每吐一个字都要从显存搬一次几 GB 的 KVCache）。如果把它们混跑在同一张卡上，Prefill 会瞬间打断并阻塞 Decode，导致在线用户的打字机输出严重卡顿（TPOT 出现剧烈毛刺）；
- **PD 分离架构**：将集群物理节点拆分为两组：
  - **Prefill 专职节点**：只负责大并发算 Prompt，算完将 KVCache 通过高速网络发送出去；
  - **Decode 专职节点**：只负责接收 KVCache，细水长流专心给用户吐字；
  - **核心纽带**：两者之间依赖一套极速、零拷贝、高可靠的分布式 KVCache 存储与传输底座。

### 0.4 开源软件是怎么做的？为什么遇到“物理性能悬崖”？

为了解决 KVCache 的管理与传输，业界出现了两款代表性开源软件：
1. **vLLM**：大模型推理引擎标杆，提出 PagedAttention（类似操作系统的虚拟内存分页机制，将连续的 KVCache 拆为离散的物理 Block 进行管理），但原生只适合单机单卡，缺乏分布式跨节点高效共享与分层存储能力；
2. **Mooncake**：月之暗面 (Kimi) 开源的分布式 KVCache 传输与存储解耦底座，尝试使用 RDMA 网络在节点之间搬运 KVCache。

**【Mooncake 存在的 5 大致命物理瓶颈（为什么我们必须深度重构增强？）】**：
1. **CPU 拷贝包袱（CPU Touch）**：开源 Mooncake 在数据传输时，数据在 Host DDR、CPU 缓存与 NPU 之间来回中转（`memcpy`），导致高吞吐时 Host CPU 100% 满载，形成严重的“CPU 墙 (CPU Wall)”，网卡带宽根本跑不满；
2. **控制面协议序列化开销大**：使用 Python 字典与 ZMQ 消息打包数百个离散物理 Block 地址，打包与解析耗时达到 3~5ms，甚至超过了底层网络传输本身；
3. **盲目搬运引发“负收益”（变慢）**：开源方案不管当前网络是否拥塞、不管前缀有多长一律尝试拉取。在网络繁忙时，从网络拉取 KVCache 的耗时居然超过了“本地 NPU 直接重新计算”，业务延迟不降反升；
4. **多卡并行 (TP=8) 缺乏同步机制**：大模型通常跨 8 张卡做张量并行 (TP=8)。开源方案各卡独立查询缓存，一旦出现卡 0 查到缓存去拉取、而卡 1 没查到去重算，8 张卡在后续集合通信（AllReduce）时会因状态不一致而**瞬间死锁挂死**；
5. **前后台流量缺乏隔离 (QoS)**：后台大流量把冷 KV 换出到存储池时，把网卡和 PCIe 带宽彻底占满，导致前台正在给用户打字返回的实时请求发生严重排队，TPOT 尾部延迟劣化超过 30%。

这就是我们要做**面向国产 AI 硬件的统一异构 KVCache 存储与调度底座 (Unified KV)** 的根本原因！

## 第 1 部分：提前原型验证的战略定位与验证哲学

### 1.1 为什么必须在立项初期开展“提前验证”？

大模型推理系统是一套软硬件高度协同的复杂工程。如果我们不摸清底层硬件物理特性，直接开始堆砌几万行生产业务代码，极易在后期遭遇根本无法调优的物理瓶颈（例如网卡 DMA 无法直达显存、共享内存跨卡同步死锁、决策失误导致负加速）。

**【提前原型验证的核心哲学】**：
1. **用最小的微内核 (Micro-Benchmark) 探明物理极限**：用几百行精炼的 C++/Python 代码，脱离复杂的上层业务逻辑，直接对底层驱动（URMA 通用远程直接内存访问、UBMEM 统一总线内存直通共享协议、Linux `io_uring` 异步 I/O、POSIX 共享内存）进行极限压测；
2. **以客观实测数据为准绳**：绝不在纸面上做主观臆断。每个方案都必须有清晰的量化判定门限（Go / No-Go）；
3. **摸清边界，为后续系统架构锁定最优主路径**：验证哪些设计行得通（主路径）、哪些设计行不通（及时止损，确立纯软替代方案）。

#### 1. 【为什么要做（前因与现实痛点）】
- **业务疑问**：大模型推理时，把历史 KVCache 存在存储池里再拉回来，真的比本地 NPU 重新计算更快吗？

│ 验证ID: PVT-01 │ 优先级: 🟡 P1 (底座支撑) │ 对应阶段: E1 底座打通 │ 周期: 5~6 人日      │

#### 1. 【为什么要做（前因与现实痛点）】
- **现实痛点**：传统开源方案在搬运 KVCache 时，数据流经 Host CPU 内存（`NPU HBM -> CPU DDR -> 网卡`）。在 400Gbps 高速网络下，CPU 的内存带宽和算力瞬间被 `memcpy` 占满（CPU 100%），形成严重的“CPU 墙”，导致推理服务瘫痪。
- **核心主张**：必须实现 **Host CPU 零数据拷贝（CPU 仅负责下发控制指令，不参与正文数据搬运，Host Payload Touch Bytes 严格为 0）**，让数据直接在 NPU HBM 与网卡 DMA 之间直达流转（Peer-to-Peer）。

#### 2. 【核心验证目标（量化门限）】
- 验证在大流量数据传输时，Linux eBPF 内核探针捕获到的 Host CPU 拷贝字节数严格为 0；
- 在万兆线速传输下，Host CPU 利用率增量 $< 5\%$；
- 自动探测并输出各链路物理参数表（`capability_matrix.json` 硬件能力矩阵）。

#### 3. 【底层技术机制（操作系统与硬件视角）】
- **CANN P2P Pinning**：通过国产 NPU 驱动接口锁定显存物理页（Pinning），将 HBM 物理地址直接注册到 URMA/RDMA 网卡的内存区域（Memory Region, MR）中；
- **eBPF 零拷贝探针 (`host_touch_monitor.py`)**：利用 Linux eBPF 技术 Hook 内核的 `memcpy`、`copy_to_user` 和 `copy_from_user` 函数，统计传输期间是否有正文数据流经 CPU。

#### 4. 【后果与架构决断】
- **若达标（通过）**：正式确立全链路 CPU 零拷贝架构，将 CPU 从沉重的数据搬运中彻底解放，专注于微秒级控制面调度；
- **若不达标（回退）**：若底层驱动暂不支持直接 P2P，则定位驱动瓶颈，设计固定大页内存（Pinned DDR Pool）作为临时环形缓冲区，严格限制 CPU 拷贝开销。

### PVT-02：异构框架 Layout 描述符编译器与跨节点异步流水

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-02 │ 优先级: 🔴 P0 (核心决胜) │ 对应阶段: E1 底座打通 │ 周期: 7~8 人日      │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-02/ (descriptor_compiler.cc/.h, async_dag_bench.cc)         │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【为什么要做（前因与现实痛点）】
- **现实痛点**：vLLM 的显存是以 16 个 Token 为一个 Block 离散分配的。跨节点传输 32K 上下文时，包含多达 2,000 个离散的内存块碎片。
- **开源缺陷**：Mooncake 与 vLLM 默认使用 Python 字典和 ZMQ 消息打包这 2,000 个块的物理地址，序列化耗时高达 3~5ms，严重阻塞控制面；
- **核心主张**：开发高性能 C++ **描述符编译器（DescriptorCompiler）**，用贪心算法将相邻的离散 Block 合并为一个连续的硬件 Scatter-Gather 描述符（64 字节紧凑结构体），并实现逐层边算边传（Layerwise Streaming）的异步 DAG 流水。

#### 2. 【核心验证目标（量化门限）】
- C++ 描述符编译与提交耗时相比 Python 序列化降低 $\ge 40\%$（从毫秒级降至 $<50\mu\text{s}$）；
- 跨节点传输与 Prefill 计算的流水重叠率 $\ge 60\%$（实现计算与传输高度并发掩盖）。

#### 3. 【底层技术机制（算法与异步流水视角）】
- **贪心合并算法**：遍历离散 Block 数组，如果 `block[i+1].paddr == block[i].paddr + BLOCK_SIZE`，则在微秒级时间内自动合并为一个 Extent 区间，将 2,000 次 DMA 提交压缩为几十次；
- **异步 DAG 多 Stream 重叠 (`async_dag_bench.cc`)**：利用 NPU 的多流机制（Compute Stream 与 DMA Copy Stream 并行），第 0 层算完立刻触发 DMA 发送，在传输第 0 层数据的同时计算第 1 层，实现时间重叠。

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                   Layerwise 边算边传 (计算与传输 100% 异步重叠流水)                    │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 计算流 (Compute Stream):  [ 计算 Layer 0 ] ──► [ 计算 Layer 1 ] ──► [ 计算 Layer 2 ]   │
│                                  │                   │                   │             │
│                                  ▼ 触发 DMA          ▼ 触发 DMA          ▼ 触发 DMA    │
│ 传输流 (DMA Copy Stream):         [ 传输 Layer 0 ] ──► [ 传输 Layer 1 ] ──► [ 传输 L2 ]│
│                                                                                        │
│ 收益：当最后一层神经网络计算完成时，整网数据传输也同步结束，传输时间被完全掩盖！       │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 4. 【后果与架构决断】
- **若达标（通过）**：彻底剔除 Python 序列化模块，将 64B POD 描述符编译器固化为系统跨节点通信的标准数据结构；
- **若不达标（回退）**：分析合并算法的 CPU 开销，增加基于固定物理页池（Super-Block）的预分配机制。

### PVT-03：远端直读 (Direct-View) vs 显存拷贝 (Copy-to-HBM) 适用边界与 ViewGuard 容错

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-03 │ 优先级: 🟡 P1 (底座支撑) │ 对应阶段: E1/E2 边界测定 │ 周期: 4~5 人日    │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 源码目录: ./原型验证代码/PVT-03/ (view_vs_copy_bench.cc, view_guard.cc/.h)               │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【为什么要做（前因与现实痛点）】
- **技术争论**：分布式集群中有两种使用远端 KVCache 的方式：
  1. **Direct-View（远端直读）**：本地不分配显存，计算算子直接跨网络读取远端节点的显存；
  2. **Copy-to-HBM（拷贝到本地显存）**：先通过 DMA 把远端 KVCache 完整拷贝到本地显存，本地算子再读取本地显存。
- **痛点与风险**：Direct-View 虽然省了本地显存，但如果每个 Token 都跨网络读一次，网络会被高频小包瞬间打爆；且一旦远端机器断电崩溃，本地算子会因内存非法访问触发 `SIGBUS` 崩溃退出！

#### 2. 【核心验证目标（量化门限）】
- 测定两者性能交叉点，**实测证伪 Decode 阶段使用 Direct-View 的可行性**；
- 验证 **ViewGuard 视图租约安全守卫机制**：当远端节点发生网络超时或断电崩溃时，本地在 $< 1\text{ms}$ 内捕获 `SIGBUS` 信号，并 100% 安全回退至本地重算，服务绝不崩溃。

#### 3. 【底层技术机制（操作系统信号与内存保护视角）】
- **交叉点测量 (`view_vs_copy_bench.cc`)**：测试在重读次数 $R=1, 2, 4, 8, 16\dots$ 情况下两种模式的耗时曲线；
- **ViewGuard 容错机制 (`view_guard.cc`)**：使用 Linux `sigaction` 注册 `SIGBUS` 信号捕获句柄，结合 `sigsetjmp` 与 `siglongjmp` 保存和恢复异常上下文，在远端故障时瞬间释放租约并平滑回滚至本地 Prefill 重算。

#### 4. 【后果与架构决断】
- **架构决断**：明确系统规则——**仅在 Prefill 阶段（只读 1 次）或只读共享大提示词时允许使用 Direct-View；在活跃 Decode 阶段强制执行 Copy-to-HBM**；全系统接入 ViewGuard 确保生产高可用。

> **💡 给 Agent 的 Prompt 指引模板**：

### PVT-05：HBM-SSD 直达容量主路径与分层存储扩容 (Tiering)

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 验证ID: PVT-05 │ 优先级: 🔴 P0 (核心决胜) │ 对应阶段: E2 分层扩容 │ 周期: 5~6 人日      │

└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【为什么要做（前因与现实痛点）】
- **现实痛点**：NPU 显存（HBM）极贵且单机只有几百 GB，海量长文本对话的历史 KVCache 根本存不下。必须将冷 KVCache 下沉到价格极低的 NVMe SSD（每台服务器数 TB 到数十 TB）。
- **开源缺陷**：Mooncake 的文件级 Offload 经过了 Linux 传统文件系统、PageCache 与 Host CPU 拷贝，每秒读写只有几百 MB，慢到无法在生产中使用；
- **核心主张**：使用 Linux 6.6+ 的 `io_uring` FIXED I/O 机制，管理 4KB 对齐的磁盘物理扇区，实现 **NPU HBM ↔ NVMe SSD 裸盘直接 DMA 交换（Payload Bypass DDR，严格绕过主机内存）**。

#### 2. 【核心验证目标（量化门限）】
- NVMe 裸盘读写吞吐达到硬件物理极限的 $\ge 80\%$（相比开源文件系统 Offload 提升 $\ge 50\%$）；
- 在集群显存负载超载 150%~200% 时，实现平滑分层换入换出，**OOM 奔溃发生率降低 $\ge 50\%$**。

#### 3. 【底层技术机制（存储 I/O 与块分配器视角）】
- **`io_uring` FIXED Buffer Direct I/O**：通过 Linux 内核最新的异步 I/O 框架，预先注册物理缓冲区，实现用户态零系统调用的极速磁盘提交；
- **分层块分配器 (`TierBlockAllocator`)**：维护 4KB 对齐的磁盘 LBA 物理块位图，管理冷热页面在 HBM 与 SSD 之间的异步迁移流水。

#### 4. 【后果与架构决断】
- **若达标（通过）**：确立“HBM-SSD 裸盘直达”为主路径，使系统无需采购昂贵的超大显存服务器，即可实现集群有效缓存容量 $\ge 30\%\sim 50\%$ 的跨代级扩展，大幅降低 TCO；
- **若不达标（回退）**：排查 NVMe 控制器 PCIe 通道瓶颈，增加多盘软 RAID0 条带化并发。

### PVT-08：1-to-N 组播式 KV 分发：硬件多播 vs 软件分层中继 (Staging Fanout)

```
┌────────────────────────────────────────────────────────────────────────────────────────┐

└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 【为什么要做（前因与现实痛点）】
- **三大业务痛点**：
  1. **热点提示词广播**：当一个通用超长系统提示词（如 64K tokens）更新时，需瞬间分发给集群 16~64 个 Decode 节点；
  2. **Multi-Agent 协作**：主 Agent 生成庞大的环境上下文，需广播给 8 个子 Agent；
  3. **PD 分离 1P-to-ND**：单个 Prefill 节点生成的 KV 需推给多个 Decode 副本。

- 验证**软件分层中继转发（Staging Fanout）**拓扑相比单播，源端网卡带宽节省 $\ge 60\%$；
- 测定是否可以通过纯软树状分发达到接近硬件多播的效果，从而**免除对昂贵交换机专用硬件多播配置的依赖**。

#### 3. 【底层技术机制（分布式树状拓扑算法视角）】
- **树状分层广播 (`multicast_fanout_bench.cc`)**：源节点只发送给 2 个一级中继节点，一级节点再接力并发发送给下一级子节点，将源端带宽开销从 $O(N)$ 降低为 $O(1)$，整网广播时间降为 $O(\log N)$。

#### 4. 【后果与架构决断】
- **架构决断**：以纯软树状 Staging Fanout 为默认主路径，保证系统可以在普通商用交换机网络中即插即用部署。

```

│ 验证ID: CVT-01 │ 优先级: 🟢 P2 (拓展证伪) │ 对应阶段: 条件证伪项 │ 周期: 2~3 人日      │

└────────────────────────────────────────────────────────────────────────────────────────┘
```

- **证伪使命**：借鉴 Linux 内核经典的 **RCU（Read-Copy-Update，读-拷贝-更新）** 无锁机制，用纯软件方案证明前台读请求零停顿，从而**彻底证伪硬件专用芯片的必要性**，大幅降低硬件采购成本。

#### 2. 【核心验证目标（量化门限）】
- 在 32 并发 Reader 读压测下，验证纯软件 RCU 迁移停顿 $< 1\text{ms}$，P99 抖动 $< 50\mu\text{s}$。

#### 3. 【底层技术机制（无锁并发与 RCU 内存管理视角）】
- **RCU 宽限期机制 (`rcu_migration_bench.cc`)**：后台写线程先将显存页复制到新地址并更新指针（原子指针翻转），老页面等待所有前台读线程离开宽限期（Grace Period）后再异步释放，前台读完全无需加锁！

#### 4. 【后果与架构决断】
- **架构决断**：彻底剔除对专用硬件 AtomicRemap 芯片的依赖，确立纯软 RCU 内存整理主路径。

   - **答**：原厂驱动默认安装在 `/usr/include/` 和 `/usr/lib64/`。如果开发机暂未安装真实硬件驱动，可以直接让 Agent 开启 `Mock` 模式（使用单机共享内存或内存拷贝进行接口模拟），先跑通上层算法与逻辑，待上机时再链接真实驱动。
2. **问：PVT-06 运行多进程同步时报错 `/dev/shm` 权限不足或找不到段？**
   - **答**：检查 Linux `/dev/shm` 挂载目录大小（确保 $\ge 2\text{GB}$），确保 `shm_open` 创建的文件权限为 `0666`，多进程使用相同的 `shm_name = "/unified_kv_rank_consensus"`。
3. **问：PVT-05 运行 `io_uring` 报错 `EPERM` 或 `EINVAL`？**
   - **答**：`io_uring` FIXED I/O 要求以 `O_DIRECT` 模式打开裸盘或预分配文件，且内存地址与写入长度必须严格按照 **4096 字节（4KB）物理扇区对齐**（使用 `posix_memalign` 分配内存）。
