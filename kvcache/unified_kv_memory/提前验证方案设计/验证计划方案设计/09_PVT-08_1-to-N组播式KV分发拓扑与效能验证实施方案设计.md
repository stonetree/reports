# PVT-08：1-to-N 组播式 KV 分发拓扑与效能验证实施方案设计
## —— 真实业务广播场景验证：硬件网络多播与软件分层中继的拓扑、成本与故障对比

> **公共执行契约**：本项遵循 [Benchmark 公共契约与证据分级规范](./Benchmark公共契约与证据分级规范.md)。每个测试 `run_id` 需在运行前完整固化集群节点拓扑、源端节点、消费者节点集合、KVCache 对象大小、分片颗粒度 (Chunk Size)、中继转发树形拓扑、分发方案、重复测试轮次、故障注入参数、代码包版本、拓扑版本快照及目标证据等级；实测产出必须完整保留源端网卡物理出向字节数 (Egress Bytes)、各消费者节点的硬件接收与完成事件、端到端完成时间戳、重试计数、数据完整性校验结果、错误码、硬件网络多播探测日志、`planned_path`/`actual_path` 路径对账及原始交换机/网卡计数器。严禁使用理想数学公式推导值替代底层的真实完成事件。

> **验证范围声明**：在当前受控的原型验证工程中，`multicast_fanout_bench.cc` 仅根据静态代数公式在输出 CSV 中固定生成单播 (Unicast)、软件分层中继 (Staging Fanout) 与硬件网络多播 (Hardware Multicast) 三类演示数据行；`test_fanout_scenarios.py` 仅生成静态的场景描述 JSON 清单，并未执行真实的底层网络数据发送、接收确认 (ACK)、重传重试或慢节点物理统计，且当前工程目录中尚未受控提供独立的 `eval_fanout.py` 脚本。因此，现有受控源码仅用于验证参数解析、数据结构定义与场景清单生成逻辑，不可直接作为证明网络实际吞吐、源端出向流量节省、消费者完成时延优化、真实硬件网络多播打通或故障容错收益的依据。在缺乏现场硬件多播能力探测、真实底层数据传输及完整事件日志的前提下，测试结论统一限定标记为 `DEMO` 或 `LAB`；若现场网络不支持硬件多播，该路径需标记为 `NOT-SUPPORTED`。

> **术语速查**：
> - **KVCache**：大模型注意力键值缓存（大模型自回归生成过程中缓存的历史 Key 与 Value 激活状态张量，用于避免后续 Token 生成时重复计算注意力）；
> - **1-to-N 分发**：单源广播分发（单一源节点向 $N$ 个分布式消费者节点广播分发同一共享 KVCache 业务对象的传输模式）；
> - **Unicast**：单播分发（源节点为每个消费者分别建立点对点独立传输连接并重复发送数据）；
> - **Staging Fanout**：软件分层中继转发（利用集群计算节点建立树状中继转发拓扑，分层接力广播热点前缀数据）；
> - **Hardware Multicast**：硬件网络多播（利用底层网络交换机与网卡硬件的多播复制能力，仅发送一份数据即可被组播组内所有节点接收）；
> - **RDMA**：Remote Direct Memory Access（远程直接内存访问）；
> - **URMA**：通用远程直接内存访问（面向新一代高性能网络的用户态远程内存访问接口与协议）；
> - **ACK**：接收确认（消费者节点在完整接收并校验数据分片后向发送端返回的确认报文）；
> - **Egress**：源端出向网络流量（源节点物理网卡实际向外发送的总字节数）；
> - **Straggler**：慢节点（由于节点算力瓶颈或局部网络拥塞导致接收处理明显落后的长尾消费者）；
> - **Incast**：多对一突发网络拥塞（多个发送节点在极短时间内同时向单一接收节点回传数据包，导致交换机出端口缓冲区瞬间耗尽而引发的排队丢包风暴）；
> - **PD 分离**：Prefill 与 Decode 计算生成解耦架构（将大模型的输入理解 Prefill 阶段与逐字生成 Decode 阶段分别部署在不同的物理硬件节点上，通过高速网络传输 KVCache 实现独立资源弹性伸缩）；
> - **Quorum**：法定完成数门限（在分布式协议中允许达到一定比例节点完成即放行后续计算的仲裁机制）；
> - **P99**：99 分位值（数据集中 99% 样本均优于该阈值的统计指标）。

## 0. 架构导读与核心概念第一性原理剖析

### 0.1 三种分发方案的物理拓扑与网络动力学特征

在大模型分布式推理集群中，针对同一段 KVCache 共享对象（大小为 $S$）向 $N$ 个消费者节点进行广播分发时，三种候选分发方案在计算机体系结构与物理网络传输上存在本质差异：

```text
1. 朴素单播方案 (Unicast) :
   源节点 ──► 串行/并发向 N 个节点分别建立连接发送 ──► 源端物理出向总流量: Egress = S × N
   [物理瓶颈] : 源节点网卡出端口瞬间被打满，随着 N 增大产生线性发送瓶颈与首字延迟恶化

2. 软件分层中继转发方案 (Staging Fanout) :
   源节点 ──► 发送给 k 个一级中继节点 ──► 中继节点接力树状转发给下游 ──► 源端物理出向总流量: Egress = S × min(N, k)
   [物理优势] : 将单点源端出向带宽压力分散至集群中继节点，利用树状拓扑降低广播完成时间

3. 硬件网络多播方案 (Hardware Multicast) :
   源节点 ──► 单次发送一份数据至交换机 Multicast 组 ──► 交换机硬件复制 ──► 源端物理出向总流量: Egress = S
   [物理优势] : 理论上源端网络开销最小；但强烈依赖交换机组播协议支持、IGMP 组管理及硬件丢包重传机制
```

在工程实测中，源端实际 Egress 流量除了包含数据载荷外，还受通信协议分片包头、控制面握手、拥塞重传、慢节点重试及中继重复发送等底层网络因素影响。因此，需以源端物理网卡与底层通信库的实际硬件计数器为准，严禁直接套用代数公式推导值。

### 0.2 三类核心业务广播场景

| 典型业务广播场景 | 源端广播对象特征 | 目标消费者特征 | 底层网络面临的主要物理风险 |
|---|---|---|---|
| **热点系统提示词广播** (`prompt_broadcast`) | 超长通用 System Prompt 对应的预计算 KVCache | 多个负责下游生成的 Decode 实例 | 源端重复发送带宽瓶颈导致新请求首字延迟上升 |
| **多 Agent 协同共享上下文** (`multi_agent`) | 主控 Agent 产生的公共规划与上下文记忆 KV | 多个并行执行的专业子 Agent 节点 | 多个子 Agent 节点并发拉取触发网络 Incast 拥塞 |
| **PD 分离 1-to-N 调度** (`pd_1p_to_nd`) | 单个 Prefill 节点计算出的超长 Prompt KV | 多个负责投机解码或并行生成的 Decode 节点 | 生成时间与接收消费时间窗口错位引发缓冲区溢出 |

## 1. 验证目标、交付物与候选准入门槛

### 1.1 核心验证目标

| 验证核心维度 | 核心物理与工程问题 | 所需客观证据 |
|---|---|---|
| 源端出向带宽削峰 | 软件分层中继转发在真实物理拓扑中能否显著削减源端网卡 Egress 流量 | 源端网卡/通信库硬件计数器、逐分片发送日志及对象 ID 对账表 |
| 全局广播完成时延 | 从源节点开始发送到所有合法消费者节点校验就绪，端到端实际耗时如何分布 | 源端开始时间戳、各消费者节点完成中断、全量完成时间 CDF 曲线 |
| 树状中继转发流水 | 中继节点在物理上能否实现“边接收边转发”的重叠流水，实际排队开销如何 | 各跳 (Hop) 接收/转发事件日志、物理拓扑映射图及中继硬件队列监控 |
| 慢节点故障隔离 | 单个消费者节点发生慢卡或网络丢包时，其余健康消费者节点是否被不必要地阻塞 | 健康节点完成时延、慢节点时延偏离度、逐节点 ACK 与重传时间线 |
| 全链路数据正确性 | 跨多级中继广播后，所有消费者接收到的张量数据是否完整且未消费陈旧代际 | 逐分片 xxHash64 checksum 校验、Generation 代际对账及对象 ID 验证 |
| 硬件多播现场可行性 | 现场网络交换机、网卡固件及通信协议栈是否真正具备硬件网络多播能力 | 交换机组播配置快照、网卡能力探针日志及实际组播数据收发凭证 |

### 1.2 候选工程准入门槛

在消费者节点数 $N \ge 8$、相同 Payload 大小及相同测试轮次条件下，候选准入门槛如下：
- **源端出向流量节省**：相对朴素单播方案，软件分层中继转发的 **源端物理 Egress 流量节省比例 $\ge 60\%$**（以源端物理网卡实测字节为准）；
- **慢节点长尾隔离度**：注入单消费者慢节点故障时，**健康消费者的 P99 完成时延劣化率 $< 10\%$**，系统不发生全网同步死锁挂起；
- **硬件网络多播判定**：若现场交换机或网卡不支持硬件组播，规范输出客观探测证据并判定为 `NOT-SUPPORTED`，不影响软件中继方案的独立准入判定。

### 1.3 阶段交付资产

每个正式 `run_id` 交付：
1. **《三类业务场景下分发方案对比报告》**：涵盖单播、软件分层中继与硬件多播在各 Payload 下的实测对账数据；
2. **《源端、中继与消费者全量事件轨迹日志》**：逐节点记录分片发送、接收校验、中继转发、ACK 返回及完成时间戳；
3. **《慢节点与故障注水测试报告》**：记录慢节点注入、叶子节点崩溃、丢包重传及健康节点时延影响分析；
4. **《网络拓扑与交换机/网卡配置快照》**：完整记录物理拓扑连接、MTU、PFC/ECN 配置及通信库参数；
5. **标准证据包与判定报告**：包含 `manifest.json`、原始事件日志、CDF 绘图及 `GO | CONDITIONAL | NO-GO | NOT-SUPPORTED | INVALID-EVIDENCE` 最终判定。

## 2. 目标拓扑、消息结构与确认协议设计

### 2.1 目标树节点描述符与广播对象定义

面向分布式广播分发的目标拓扑与对象描述符标准化定义：

```cpp
struct alignas(64) FanoutTreeNode {
    uint32_t node_id;                   // 物理节点唯一标识
    char     endpoint[48];              // 节点网络通信地址 (IP/RDMA GID)
    uint32_t parent_id;                 // 上游父节点 ID (源节点此项为自身)
    uint32_t children_count;            // 下游子节点数量
    uint32_t children_ids[8];           // 下游子节点 ID 列表
    bool     is_source;                 // 是否为源节点
    bool     is_relay;                  // 是否承担中继转发角色
};

struct alignas(64) BroadcastObject {
    uint64_t broadcast_id;              // 本次广播任务唯一序列号
    uint64_t object_id;                 // KVCache 对象全局唯一 ID
    uint64_t generation;                // 显存代际版本号
    uint64_t payload_bytes;             // 广播正文总字节数
    uint32_t chunk_bytes;               // 单分片物理字节大小 (如 1MB 或 4MB)
    uint32_t total_chunks;              // 总分片数
    uint32_t expected_consumers;        // 预期必须完成接收的消费者总数
    uint64_t checksum;                  // 原始张量 xxHash64 校验码
};
```

### 2.2 分片传输与状态生命周期流转

```text
[SOURCE_READY 源端就绪]
     │
     ▼
[CHUNK_SUBMITTED 分片提交发送]
     │
     ├──────────────────────────┬──────────────────────────┐
     ▼                          ▼                          ▼
(单播直发路径)           (软件中继接收路径)          (硬件组播路径)
[CONSUMER_RECEIVE]       [RELAY_RECEIVED]           [CONSUMER_RECEIVE]
     │                          │                          │
     │                   [CHUNK_VERIFIED]                  │
     │                          │                          │
     │                   [RELAY_FORWARD 转发]              │
     │                          │                          │
     └──────────────────────────┼──────────────────────────┘
                                ▼
                      [CHUNK_VERIFIED 校验]
                                │
                                ▼
                      [ACK_SENT 返回确认]
                                │
                                ▼
                      [OBJECT_READY 对象就绪]
```

## 3. 实验方案与测试矩阵设计

### 3.1 场景与拓扑压力矩阵

| 测试维度 | 正式实施计划标准 | 工程说明与约束 |
|---|---|---|
| 业务广播场景 | `prompt_broadcast`、`multi_agent`、`pd_1p_to_nd` | 覆盖大模型推理中不同的广播应用负载 |
| 消费者节点规模 | 4、8、16 节点 | 正式准入门槛要求在 8 个独立物理节点上验证 |
| 分发方案对比 | 单播、软件分层中继、硬件网络多播 | 全量开展三方案的同场景 A/B 评测 |
| 树状分支因子 | 2（二叉树）、4（四叉树） | 评估不同分支度对中继节点带宽与计算负载的影响 |
| Payload 数据量 | 16MB、64MB、256MB | 构造真实大模型长上下文与不同 Batch 维度的数据量 |
| 分片颗粒度 (Chunk) | 64KB、1MB、4MB | 遵循底层网络 MTU 与硬件 DMA 对齐约束 |
| 测试重复轮次 | 预热后每测试点至少重复 30 次 | 充分捕获长尾完成时延的 CDF 分布 |
| 故障注水场景 | 无故障基线、单消费者慢节点、叶子节点崩溃、随机丢包 | 验证分布式拓扑在异常扰动下的鲁棒性与隔离度 |

### 3.2 同场景 A/B 对照准则

三组分发方案在以下一致的物理条件下开展对比：
- 相同的源端 KVCache 数据对象、代际版本号及原始 Checksum 指纹；
- 相同的物理消费者节点拓扑集合与硬件资源状态；
- 相同的分片颗粒度、测试重复轮次及启动时序；
- 相同的 CPU 亲和性绑核、网卡驱动、MTU、RoCE 队列及交换机拥塞控制参数；
- 相同的故障注入位置、时延偏离度及故障持续窗口。

6. **全链路物理计数器采集**：对接网卡 ethtool/RDMA 计数器，严格分离源端 Egress 流量与中继转发流量。

### 6.3 核心对账指标计算公式

$$
\text{源端 Egress 流量节省比例} = \frac{\text{Egress}_{\text{Unicast}} - \text{Egress}_{\text{StagingFanout}}}{\text{Egress}_{\text{Unicast}}} \times 100\%
$$

$$
\text{长尾时延扩散度 (Tail Spread)} = T_{\text{done}}(\text{P99}) - T_{\text{done}}(\text{P50})
$$

$$
\text{慢节点对健康节点时延影响率} = \frac{T_{\text{healthy}}(\text{Fault}) - T_{\text{healthy}}(\text{NoFault})}{T_{\text{healthy}}(\text{NoFault})} \times 100\%
$$

## 7. 候选准入门槛、判定规则与立即止损机制

### 7.1 候选工程准入门槛一览表

| 核心评估维度 | 候选工程准入门槛 | 权威取证要求 |
|---|---:|---|
| 源端出向流量削峰 | 软件分层中继相对单播 **源端物理 Egress 节省 $\ge 60\%$** | 源端物理网卡与底层通信库实际完成字节数对账 |
| 健康节点长尾隔离 | 注入单节点慢卡时 **健康消费者 P99 完成时延恶化 $< 10\%$** | 同一节点规模与 Payload 下的故障前后 A/B 对照 |
| 数据传输正确性 | 全量消费者节点 **0 校验损坏、0 陈旧代际读取** | 逐节点分片 xxHash64 校验与 Generation 版本比对 |
| 硬件多播能力支持 | 客观探测现场交换机与网卡多播支持状态 | 若不支持则规范标记 `NOT-SUPPORTED` 并输出客观依据 |

### 7.2 状态判定枚举与规则

- **GO（全链路证据闭环）**：软件分层中继在目标节点规模下达成 $\ge 60\%$ 流量削减，数据校验 100% 正确，慢节点隔离度达标，原始事件完整；
- **CONDITIONAL（局部场景或特定规模达标）**：核心门限在特定节点规模或特定 Payload 下达标，但扩展时存在网络波动；
- **NO-GO（发生数据损坏或严重长尾阻塞）**：发生数据校验失败、慢节点导致全网死锁、重传风暴无法收敛或完成时延超出止损线；
- **NOT-SUPPORTED（物理环境未支持）**：现场交换机或网卡不支持硬件网络多播；该状态仅针对硬件多播路径，不影响软件中继方案的独立判定；
- **INVALID-EVIDENCE（无效证据）**：仅有理论公式推导值、静态演示 JSON、缺失逐节点完成事件或实际路径未证实。

### 7.3 立即安全止损条件

在测试过程中凡触发以下任一异常，立即终止测试并保存现场：
- 消费者节点校验 Checksum 失败、读取到已过期的陈旧代际数据；
- 源端或中继节点的物理发送字节持续上升，但消费者节点的完成进度完全停滞；
- 网络发生剧烈 Incast 拥塞，导致交换机队列溢出、触发大面积丢包重传风暴；
- 单个慢节点引发全网树状中继无限期等待，或叶子节点崩溃后中继资源无法回收；
- 声明使用硬件多播路径，但底层实际数据包退化为单播逐个发送。

### 9.3 常见排错指南

- **输出 CSV 中所有方案的耗时均基于固定公式生成**：当前受控 C++ 代码仅为公式演示 DEMO；必须接入真实的底层数据面传输引擎。
- **硬件网络多播行显示有数据但交换机完全未配置**：排查命令行中是否传入了 `--hardware-supported` 开关；必须执行现场客观能力探测。
- **执行命令提示找不到 `eval_fanout.py` 脚本报错**：当前受控工程中尚未包含该脚本；需补齐评估器实现或人工核验。
- **向 Python 脚本传入 `--fault slow_node_c6` 报错未知参数**：当前脚本仅接受标准的 `slow_node` 枚举；应在扩展实现中增加 `fault_node` 字段。
- **多次运行生成的场景 JSON 中 `workload_id` 始终变化**：当前脚本使用随机 UUID 生成该字段；在正式 A/B 对照时必须在外部 Manifest 中严格固化唯一的 Workload ID。
- **源端 Egress 流量显著下降但全网总流量大幅上升**：说明中继节点承担了下游复制开销；需分别报告源端开销与全网成本。
- **注入慢节点后其余健康消费者节点被拖慢挂起**：说明上层协议采用了全局强同步阻塞逻辑；需核验业务场景是否支持 Quorum 机制并优化 ACK 异步处理。
- **发生网络重传后消费者节点收到重复张量数据**：排查分片序号与 Generation 代际去重逻辑；必须在接收端增加幂等性检查机制。
- **硬件多播模式下底层数据包实际走单播逐个发送**：说明交换机 IGMP 组播流表未正确建立或网卡多播配置失效；需通过网络抓包确认真实的 `actual_path`。
