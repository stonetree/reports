# 统一异构 KVCache 存储池关键技术原型验证实施方案 B

> 文档状态：可执行设计基线（实验结果待执行后填写）  
> 适用基线：原型清单 V1.6、需求树 V2.3.1、SRS V2.2  
> 默认周期：4～5 周，8 个 PVT 纳入资源基线，3 个 CVT 仅在触发门满足后启动

## 1. 交付目的

本目录把《统一异构KVCache存储池_关键技术原型验证清单_V1.6_V2.3.1需求树与竞争力对齐完善版.xlsx》中的每一条验证计划展开为可执行的实施计划和实施方法详细设计。目标不是完成一次性 Demo，而是按 E0～E3 证据门得到可复现、可证伪、可迁移到正式项目的结论，并明确其对架构、首发范围、硬件采购、人员配置和竞争力主张的影响。

当前所有门槛都是待验证目标，不是既有成绩。未关闭 E3 前，不得表述为已经优于 Mooncake、LMCache 等当前最佳可行开源组合。

## 3. 事实优先级

发生口径不一致时按以下顺序处理：

1. SRS V2.2：正式需求语义、优先级与阶段验收基线；
2. 全量需求树 V2.3.1：38 条独立交付 SR 和 203 条 AR 的工程分解；
3. 原型清单 V1.6：11 项验证的范围、门槛、交付证据和实施波次；
4. 总体架构与 SRS 评审导读 V2.3.1：总体原则、架构边界和统一 KPI；
5. 竞争力材料：第一方责任、公平开源基线、客户价值与证据表达；
6. `kvcache_transfer_quantitative_model.md`：开源机制、量化公式和测试向量参考，不覆盖 V1.6 的正式门槛。

例如，定量模型中出现的“线速 90%”“Revoke ≤10μs”和旧称“PVT-08”，分别只作为挑战目标或测试参考；正式判定仍采用 V1.6 的“代表路径 ≥峰值/线速 80%”“Revoke P99 <1ms”和“CVT-01”。

## 5. 使用规则

- 开始任何实验前先执行公共底座的 DoR 检查；公共字段、时钟、版本和统计窗口不得由单项实验自行改名。
- 每个 case 必须生成唯一 `experiment_id`，关联 `request_id`、`plan_id`、`object_id`、`path_id` 和 `fault_id`。
- 所有物理路径同时记录 Planned Path、ActualPathReceipt、Host Payload Touch 和 fallback；不能只用配置文件或峰值带宽证明实际路径。
- 每项至少提交冻结配置、原始数据、P50/P95/P99、置信区间、资源计数、异常样本、适用边界、一键复现入口和评审签字。
- Go/Conditional 的接口、探针、标准正确结果用例和回放器必须进入正式模块候选；No-Go/Not Supported 也必须保留证据、功能开关和回退资产。
