# SGLang / vLLM + Mooncake 的 KVC 压缩测试验证方案

> 版本：V2.0｜日期：2026-11-04（北京时间）  
> 配套文档：[优化方案与实施指导](SGLang_vLLM_Mooncake_KVC压缩_优化方案与实施指导_V2.0_20261104.md)。  
> 状态：已通过三位 AI 专家的设计复核，8 条审核意见及整改见配套方案 §12；验证待开发和执行。本次核对材料、源码和测量方法，没有实测基线、编译通过或性能 PASS 结论。数字均为建议验收目标。

## 1. 要回答的业务问题

每个框架分别回答：压缩是否让真实请求更早返回首字，是否在相同机器和时延约束下服务更多有效请求，是否减少相同业务产出的 CPU 与 I/O 资源消耗；IOStash 是否在软件压缩之上带来可重复的增量价值。任何一项无收益或退化都应保留，不能只展示最有利的长上下文命中样本。

术语：KVC 为大模型注意力键值缓存；TTFT 为首 Token 响应时间；TPOT 为每请求平均输出 Token 间隔；ITL 为相邻 Token 间隔；SLO 为服务时延要求；Goodput 为同时满足时延与质量要求的有效请求吞吐；PD 为预填充与逐字生成分离部署。HBM、DDR、DDRC 分别为设备显存、主存及主存控制器；PMU 为硬件性能监控；I/O Die 与 RC 分别为 I/O 芯粒和 PCIe 根复合体；IOStash 为待目标平台确认的 I/O 缓存驻留能力。

### 1.1 分层结果与声明规则

| 证据层级 | 能证明什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 静态/功能 | 格式、恢复、生命周期和错误处理符合设计 | 实机吞吐或推理收益 |
| 纯 codec | 真实 KVC 上的压缩分布、编解码吞吐、核秒 | 网络可饱和、业务 TTFT 降低 |
| 传输闭环 | 从发起读取到恢复就绪的传输性能 | attention 负载和排队下仍有收益 |
| 在线推理 | 指定模型、框架、拓扑、负载下的端到端效果 | 另一个框架、硬件或所有业务同样受益 |
| IOStash 增量 | 受支持配置下开/关造成的变化 | 无平台证据时声称数据一定入 L3 或 DDR 写被消除 |

SGLang 与 vLLM、GPU 与 NPU、Store 与 PD 的结论均分开。没有运行的组合标“未执行”；能力不具备标“不适用”；噪声大标“无确定结论”，不能写 PASS。

## 2. 测试床、冻结与数据准备

### 2.1 拓扑

基础测试使用两台物理服务器：一台运行推理与缓存客户端，一台运行远端 Mooncake Store；记录控制面服务位置。两端都有 CPU、内存和网卡统计。PD 测试将两台作为 Prefill/Decode，Store 复用测试另安排明确服务进程与资源预算。若新增服务器，也要计入整套方案的资源成本。

允许先用本机回环或单机功能验证，但结果标 `MOCK_SOFTWARE_ONLY` 或“单机功能”，不用于跨节点网络或 I/O Die 结论。单机双网卡光纤环回可做局部硬件实验，却不能等同于双机分布式推理。

固定网卡、链路和固件、有效设备频率与功耗模式、推理模型权重和 tokenizer、模板、注意力后端、TP/流水并行配置、KV dtype/page size、HBM 配额、Host 总预算、Mooncake 副本与 SSD 策略、线程亲和和日志级别。协议名或编译开关不足以证明传输路径，需保留运行日志、端口字节与实际引擎/设备映射。

### 2.2 每轮冻结清单

运行前生成 `manifest`：框架/插件/设备后端/Mooncake/库的版本与提交、补丁哈希、构建选项、内核/驱动/固件、启动命令、配置、模型与语料哈希、随机种子、SLO、节点拓扑、CPU/NUMA绑定、缓存命名空间、编码格式及算法。实际加载动态库和原生扩展版本也要记录。

本地参考源码与目标机版本不同，先由 Agent 输出函数映射表。特别检查 vLLM 回调到底在 `get_finished`、`start_load_kv` 还是别的入口触发；SGLang 是否使用 v1、v2 和 NPU 专用池。冻结后完成 RAW 往返再跑压缩，防止测试的开关没有命中实际代码。

### 2.3 真实 KVC 语料

从两个框架各导出**有效而非未初始化的**真实 K、V 或实际潜变量张量段；记录模型版本、层、token 范围、分量、head、dtype、shape、stride、位置编码阶段、rank 和源事件完成时刻。不要只导出早期层或只挑高可压缩样本。小模型层数不足 80 时，不能照搬第 79 层。

首轮包含业务主模型和一个不同结构的对照模型，短中长提示、代码/问答/检索、多轮缓存复用、不同层与 K/V。主结果覆盖全层或按各层真实字节权重聚合；给出分层、分量的最差分布。数据总量应超过 codec 所用末级缓存；小于缓存的热数据单列，不混成 DDR 稳态性能。

校准集与测试集按会话划分；码本不能用最终测试集重新调到最优后冒充泛化。随机数据、全零、极端异常与混合 RAW 仅用于正确性和最坏界，不承担真实压缩率结论。

## 3. 对照与消融矩阵

### 3.1 软件路径

| 组 | 配置 | 要隔离的因素 |
| --- | --- | --- |
| B0 | 冻结的原生框架 + Mooncake；已有生产优化保持 | 最终业务与资源的真实基线 |
| B1 | 新适配器 + RAW 帧 + 相同 scratch / worker / 排队路径 | 格式、插桩、Host 整备和适配器成本 |
| B2 | B1 + 原始字节 LZ4/Zstd | 普通压缩库的效果 |
| B3 | B1 + C-Blosc2 shuffle 及相同后端 | 现成重排的增量与维护成本 |
| B4 | B1 + 自定义 NEON 重排 / 指数编码，IOStash off | 自定义算法对 B2/B3 是否真正值得 |
| B5 | 选中的 codec + 有界流水、组批/线程优化 | 排队与重叠带来的增量 |
| B6 | B5 + 自适应 RAW/压缩/重算决策 | 混合业务能否减少负收益请求 |

B1 不能替代 B0。特别是 vLLM，B1 的额外 D2H/H2D 可能已明显慢于原生直达；所有最终结论必须直接比较 B5/B6 与 B0，不能只比较 B4 与较差的 B1。

描述符优化、分配器、传输窗口、选择性完成和链路调优默认冻结。若需组合，另设 `压缩off/on × 描述符优化off/on` 二因素实验，报告交互；组合收益不得把两个独立百分比相加。

### 3.2 IOStash 分支

在 B5 的同一 codec、线程、切片、队列、CPU/NUMA与缓存预算下先做 I0/I1 对照：

| 组 | 唯一变化 | 目的 |
| --- | --- | --- |
| I0 | 受支持的 IOStash off | 软件压缩基线 |
| I1 | IOStash on，其他同 I0 | 直接硬件驻留增量 |
| I2 | I1 增加/优化输入、输出信用窗口 | 流控收益；另对 I0 开相同流控以分离通用收益 |
| I3 | 对已选窗口比较普通/非临时输出写 | 写策略增量；不把 STNP 名称当生效证据 |
| I4 | 在已选配置上开/关平台支持的分区或亲和改进 | 隔离资源策略增量 |

先单因素筛选，再对最佳组合复测，不全量笛卡尔积。不能把同时增加 CPU 核数、改亲和、减窗口、开 IOStash 的组合提升全部归给 IOStash。硬件开关作用于全局时，每次切换后核验状态并处理残留缓存，随机化 A/B 顺序。

## 4. 功能与正确性验证

### 4.1 无损与格式

- 对真实 corpus 和包含所有 BF16/FP16 位模式的专用样本做逐位往返；有序与乱序数据均测。包括正负零、NaN 载荷、Inf、次正规数、不可压缩数据、空输入的约定、奇数长度、片尾、未对齐地址和超大对象拆片。
- 测 RAW 与压缩片混合、异常值逃逸、字典缺失/错误、协议版本不支持、截断、校验错、offset 溢出、声明长度与目标页不符。接收完整性不能只测返回值为正。
- 对原 256 KiB 边界及更大容量测试长度字段；随机制造最坏膨胀，验证 bound 与 fallback。分配/对齐占用与网络实际传输长度分别核对。
- 恢复后原生页地址、有效 token 与分量映射一致。使用实际 scatter 目标，不能只测连续数组恢复。
- 交换两个同长合法 key 帧、K/V 帧或 rank 帧，保持各自校验正确，确认预期物理 key 指纹仍能阻断错误。重算校验后构造中间漏片、重复片、短解码，确认规范化有效区恰好覆盖 `[0,U)`，实际恢复长度精确相等；未初始化 padding 不算有效 KV。

准出：所有定义有效输入逐位一致；非法输入必须明确失败且没有越界或半页可消费。数据恢复不一致立即停止性能验收。

### 4.2 两框架生命周期

从单页单请求开始，依次测试部分前缀命中、尾页未满、多请求共享前缀、重复 key、K/V 或 sidecar 部分失败、缓存淘汰、备份超时、取消、设备事件迟到、网络重试、worker 停止和关闭。强制把 decoder 或 H2D 延迟，检查框架绝不会在实际设备就绪前使用该页。

验证取消前已下发 DMA 排空后才复用槽；用槽 generation 检查迟到完成。单独测试输入槽先释放、输出槽仍由 H2D 持有的阶段；压力下不可因缺输出槽卡死输入。TP>1 注入单 rank 失败，确认全部 rank 的可用前缀一致，且不会进入不一致的集合通信。

SGLang 检查 backend 成功→prefetch ack→原生加载的顺序，包含实际使用的 v1/v2 池。vLLM 检查真实 `get_finished`/错误块接口，加载成功必须晚于恢复事件；Store 无逐层支持时，以全命中前缀就绪为准。

增加三页前缀的中间页损坏用例，第三页放在尚未提交的后续批；不得报告三页全部成功。SGLang 只确认连续正确前缀；vLLM 把损坏页及后续所有未完成/未提交承诺页通过错误块通道上报。分别运行部署的 `kv_load_failure_policy=fail/recompute`：前者失败响应计入业务分母，后者须见到原生调度器重新计算且多 rank 一致。主动绕过应发生在 `get_num_new_matched_tokens` 等返回承诺之前；工作线程故障不是任意切换重算的许可。

无损推理使用固定输入与采样参数，先确认原生重复运行的确定性。确定性条件成立时比较 token/输出；非确定性环境仍以 KV 逐位恢复为硬条件，再比较重复运行的输出/任务质量分布，不能把随机漂移归为压缩误差或用它掩盖恢复错误。

## 5. L0：真实语料 codec 性能

测量顺序：单核→同局部簇多核→同 socket→必要时跨 socket；每阶段只增加一个因素。固定总核数比较算法，避免库内部线程数膨胀。NEON、标量与条件可用的 SVE 分开构建/记录。

记录各片 U、C、r、编码/解码墙钟、CPU 核秒、cycles/byte、临时峰值内存、RAW 比例、失败量与校验耗时。吞吐分别按原始字节与编码字节计算，表头明确；聚合压缩率用 `sum(U)/sum(C)`，不要平均各片压缩倍数。

分三个输入档位：缓存内热输入、超过 L3 的循环数据集、真实生产/接收流水。接收持续增长会影响频率和带宽，至少验证达到稳态；报告总样本量、核数、内存节点、缓存冷热、编译选项和是否计校验/分配。每项不少于 5 次独立重复，波动大时先查频率、NUMA、线程与带宽争用。

筛选条件：无损通过；扣除格式/分配开销仍有物理空间节省；编码/解码在计划核数预算内，并且按主方案 §6 的成本模型存在业务机会。这里不设“必须 1.55 倍 / 45 GB/s”门槛，避免因初版承诺而筛掉真实有效路线。

## 6. L1：IOStash 可用性与微架构实验

### 6.1 从最小硬件实验开始

1. 收集目标平台手册/驱动接口、能力查询与配置前后状态，明确实际目标缓存和设备路径。
2. 用真实 RNIC/设备 DMA 将输入写入注册槽，完成后同局部 worker 立即校验读取，比较 off/on 的访问时延、缓存命中、DDR、片间流量和正确性。纯 CPU 预热实验不能证明 DMA stashing。
3. 加入可控等待，扫“DMA 完成到 CPU 消费”的延迟，观察驻留何时衰减；扫描并发槽和输入大小。
4. 加入真实解码、输出存储和 H2D，随后加入推理、后台换出负载，验证输入驻留仍有价值。

若只观察到缓存命中上升，但缺受支持配置证据，结论写“缓存局部性改善，IOStash 归因不足”。若硬件没有可用接口，标记该分支不适用，不输出模拟开启脚本。

### 6.2 窗口、槽与预算

按主方案工作集约束设置初始窗口，扫描 D=1/2/4/8/16/32 仅作为候选。每点记录输入槽最坏容量、输出槽容量、scratch 峰值、缓存预算、平均/尾部驻留等待、信用耗尽时间、实际在途网络字节和队列空闲时间。

同时核对带宽时延积：小窗口造成链路等待时，不能只因 L3 命中率更高而选它。选择依据是恢复就绪吞吐和在线业务，不是单一 hit-rate。MPAM/绑核只能作为已支持功能测试，实际分区容量与 DMA 分区归属必须核实。

输入信用按完整对象序列化上界计费，输出按完整有效原始长度计费；并发批次的所有整帧及工作区合计纳入预算。测试对象跨多片、单帧大于局部缓存窗口、RAW最坏帧、大小对象混批和跨小批并行。只有整批 `batch_get_into` 返回且 DMA 可见后解码，记录批返回到首次读取和首/尾对象等待；无法观察最早对象到达时，不生成片级驻留数据。超对象硬上限在承诺命中前绕过，写端不得创建读者能力外表示。大对象的 IOStash 旁路还须硬件具有对应区域/流隔离能力，全局开关不具备隔离时按平台组合实验处理。

### 6.3 PMU 统计边界

先用目标机 `perf list`、sysfs 与厂商文档建立事件清单，注明事件名称、unit、作用范围、字节换算系数、counter width、采样窗口、time_enabled/time_running、权限和有效状态。不预填 `flux_rd/rd_hit_cpipe` 为所有鲲鹏通用事件；没有事件时标不可观测。

DDR 流量、L3 hit/miss、CPU stall/IPC、片间一致性、RC/I/O 通路事务分别收集。单个事件只有在文档明确含义时才能换算带宽；hit-rate 要有匹配的分子分母。CPU 的 LLC 指标不能代表设备写分配。

分为稳态服务窗、停止新流量后的观察窗，以及同样长度的匹配背景窗。稳态窗用于吞吐与业务时延；DMA、codec 排空后的 DDR 回到背景，只能证明当前没有明显流量，不能证明脏缓存行全部写回。分别报告各窗读写字节；停流后观察值不并入稳态 QPS。

需要声称覆盖残留写回时：采用平台支持且语义明确的同步写回操作，A/B 同样执行并记录其费用；或定义目标缓存/设备所有残留脏行的保守字节上界，使最坏情况下的 A/B 差仍达到目标。若无法做到，结果明确为“观察窗内字节”和长稳态流率，不判“完整总量节省”或“零写回”。短时边界影响以运行时长扫描和残留上界说明，禁止用空闲计数代替证据。

比较 `总DDR字节/U`、`总DDR字节/有效请求`，同样记录读写分项。测试组与空闲背景按匹配窗口采样；原值与扣背景值同时保存，噪声大时不作强归因。IOStash 输入变热不等于脏行写回消失。

## 7. L2：Mooncake 传输与恢复闭环

使用大于缓存容量的真实 corpus，多对象、多大小、部分失败和稳态轮转。固定物理链路和 Store 副本，测试本地、远端 DRAM、SSD 分层，但分表报告。远端实验从端口计数确认实际过网，本地 memcpy 字节不混入远端 wire 压缩率。

墙钟起点为框架/客户端提交读取，终点为**原生 Host 目标完整或设备可消费**；按路径表明确。纯网络耗时另记录。测 `U/恢复就绪墙钟` 的逻辑带宽，同时测真实 wire 字节/时间；逻辑带宽超过链路标称只表示压缩后的等效处理量，不代表物理链路超速。

记录 N_key、N_slice、N_sge、N_wr、N_post、N_cqe、实际队列占用、元数据 RPC、重试、超时、RAW 比例、输入/输出槽等待、首片与尾片就绪时间。批量提交减少 API 次数，不必然减少 WR；编解码切片可能增加对象内部段数。

**vLLM 必测三条路径：**原生设备直达、RAW Host staging、压缩 Host staging；具备设备 codec 时增加第四条。把 D2H/H2D 与设备等待计入闭环，报告 Host 总内存、CPU 与 PCIe 流量。若 B1 比 B0 慢很多，不能通过和 B1 比较夸大压缩收益。

测试结果作为在线配置选择的输入。只有微基准通过而完整恢复路径不胜出时，停止该路径默认开启，先判断是网络不受限、CPU解码不足还是额外搬运抵消。

## 8. L3：真实在线推理业务实验

### 8.1 最小覆盖矩阵

| 编号 | 场景与构造 | 要回答的问题 |
| --- | --- | --- |
| E01 网络受限 | 工作集低于总缓存预算，固定可用命中；远端读取；按受支持手段扫有效链路容量 | 减少网络字节能否真正缩短 TTFT |
| E02 容量受限 | 固定所有物理缓存预算，扫工作集/预算≈0.7/1.0/1.3/1.7/2.2 | 额外保留的前缀是否减少重算并提高 Goodput |
| E03 计算受限/热命中 | 短输入、主要本地热命中、较长输出；包含无远端拉取请求 | 压缩是否引入不必要 CPU 或生成干扰；bypass 是否有效 |
| E04 混合多轮 | 多租户、多轮代码/检索/问答与长短请求混合，真实工具等待 | 最优单工况策略是否在实际混合业务仍成立 |
| E05 前后台混压 | 在线 Decode + 同时后台换出/恢复，背景速率固定 | TTFT 改善是否以 TPOT/ITL 尾部退化为代价 |
| E06 争用与退化 | CPU 预算减少、内存/片间争用、高熵、低命中、故障恢复 | 自适应选择能否避免负收益与资源积压 |
| E07 IOStash 增量 | 在 E01/E04/E05 的同软件配置做 I0/I1 与最佳组合 | 是否有业务或单位产出资源的独立增量 |
| E08 PD 条件项 | 同样请求和输出，分别在 SGLang/vLLM 直传路径接入 | 首字或后续首个 Decode Token 间隙是否改善；Store 结果不可代替 |

上下文长度以主业务为准，初始可选 2K/8K/32K/64K，模型支持再加 100K；输出长度至少含短输出和 256/1024 Token 长输出。超出模型上下文能力的点不运行。并发从低负载到满足 SLO 的最大稳定到达率，避免只测一个饱和点。

每框架先做自身 A/B，再做跨框架横向展示。框架间可实现的 attention、调度和设备差异都记录，不能将跨框架差值归因于压缩。

### 8.2 命中隔离与容量实验

E01 要隔离纯传输效应：使用同一批逻辑前缀，均能装入缓存，预热到相同可用 token 集；确认本机热池未把预定远端拉取完全截走。以实际恢复 token/字节记录命中，不能只声明“名义命中 95%”。

E02 允许压缩改变命中率，因为容量收益本来就是机制的一部分；必须固定 TTL、淘汰策略、请求序列和总资源预算。依次报告候选存在命中、成功恢复命中、按时可用命中、完整/部分前缀 token 命中与重算 token 数。采集分层容量、实际分配字节和真实淘汰，不能由“100 GB / 64 GB”直接推算 40% 会话未命中。

Host 预算包括原始热池、压缩池、注册 scratch、输入/输出 staging、码本/索引与必要分配余量；服务端副本、客户端热副本和额外 SSD 均计入对应资源总量。每个物理节点配额固定，不能给压缩组额外内存。报告每节点与集群总内存、逻辑保留量、物理占用和碎片；只压 Mooncake 层时不能声称 HBM/HiCache Host 热池容量也扩大。

预热与正式测量分开，两组从等价缓存初始状态开始；每个独立重复使用新 run 命名空间，避免跨实验污染。预热成本另计，可同时给含预热的全生命周期结果。

### 8.3 负载与到达模型

固定到达率实验使用开放环到达（发送时间由 trace/时钟决定），固定随机种子、请求内容、输出配置、到达轨迹和背景 I/O。按 SLO 找最大容量时扫描到达率，不能给优化组更多并发却直接比较平均 TTFT。

多轮 Agent 的下一轮若依赖上轮返回，使用保留依赖的闭环重放并单列，不能简单把所有轮次按绝对时间并行发送。可先用真实完成时间驱动的会话生成，再记录固定轨迹作开放环压力对照，说明两者问题不同。工具等待不计入推理 TTFT，但应保留其对缓存生命周期的影响。

负载发生器需独立资源或隔离 CPU；确认其发送不延迟、token 处理不成为瓶颈。开放环压力持续增长时要报告队列趋势，出现积压增长的点不称为稳定容量。

## 9. 指标定义、打点与归因

### 9.1 客户端业务指标

| 指标 | 定义与注意事项 |
| --- | --- |
| TTFT | 客户端发送请求到收到首个非空输出 token 的时间；包括服务排队，排除纯 HTTP 头和空 SSE 事件 |
| TPOT | 每个请求输出 N≥2 时 `(末token时间-首token时间)/(N-1)`，再对请求统计分布；N<2 记 N/A |
| ITL | 每个输出 token 的相邻时间间隔分布，注明按 token 加权；SSE 一批多 token 无独立时间时不能反推出真实逐 token 时延 |
| 请求/输出吞吐 | 成功请求数/s；有效输出 token 数/s。完整输出、长度、失败和取消策略保持一致 |
| 稳态完成 Goodput | 完成时刻落在稳态窗内且成功、同时满足预先冻结时延与质量要求的请求数 / 窗长；到达 cohort 另计，见下文 |
| 业务达标率 | 窗内到达且观察截止前合格的请求数 / 窗内全部到达请求数；失败、超时、拒绝及截止未完成计为不合格，不能只在成功样本分母中计算 |
| 最大稳定容量 | 队列无持续增长，错误率/达标率及各时延目标均满足时的最大开放环到达率 |

上表 Goodput 拆为两个独立计数口径，报告中不得混用：**稳态完成 Goodput**为实际完成时刻落在稳态窗内且满足条件的请求数/窗长，用于稳定容量；**到达 cohort 达标率**为窗内到达请求在观察截止前达标数/全部到达数，另可给达标数/到达窗长的折算率，后者不叫完成吞吐。停止发压后继续收集到达 cohort 的结果，预先冻结最大观察时限；超时未完成计不合格，不能无限等待。排空不增加稳态完成分子。

每轮报告窗口边界的 arrived、completed、backlog，以及 codec、Get、后台 Put、未完成备份的队列长度/在途字节/队列年龄。稳定容量的起始建议判据：正式窗分成至少 5 个等长子窗，前台 backlog 末/初差不超过到达量 1%，全窗趋势无确定正增长；后台队列、在途字节和最老任务年龄不能持续增长。任何业务超时上限或资源预算越界均不稳定；备份主动丢弃量及命中影响单列。阈值在 P0 冻结且 A/B 相同。

始终同时报告失败、拒绝、超时和待完成数量。TTFT/TPOT P50/P95/P99 连同原始样本量、窗口及有效样本条件一起输出。

PD 额外记录首个来自 Prefill 的 token 与首个来自 Decode 的 token 之间间隙；若部署首字已在 Prefill 发出，后续传输优化可能改善该间隙而不改善客户端 TTFT。必须按真实首字生产位置解释结果。

P0 明确可观测边界：客户端只能识别首个非空生成内容时，指标命名为“首个生成内容 TTFT”，不要声称可定位批内第一个模型 token。输出 token 数使用服务端可信计数或对完整输出统一分词；不能把 SSE 事件数当 token 数。TPOT 的端点用末/首生成内容接收时间时也标明为客户端代理口径。

真实 ITL 验收有两条路径：使用经验证的一 token 一事件客户端时间戳；或采集服务端逐 token 生成事件，注明它不含网络交付抖动。业务请求级 ITL SLO 明确为“该请求内部 ITL 的 P99/最大值”等预先选定统计量；全局 token 加权 P99 只是独立干扰指标，不能直接拿来判每请求合格。缺独立 token 时间戳时，ITL 标证据不足；可在 P0 预先选用 TTFT+TPOT 和流事件间隙作为替代业务 SLO，但报告只能写“通过该替代口径”，ITL 本身仍未验收，不能用 TPOT 冒充。

### 9.2 单请求与分片打点

关联字段：run_id、framework、request/session、逻辑 key hash、group/rank、slice、generation、codec、dtype、布局、源/目的内存类型、实际 transport。

每阶段记录入队、开始、结束：命中查询、页/槽预留、源事件就绪、D2H、编码、Put提交/完成、Get提交/完成、校验、解码、H2D、框架加载确认、attention首次消费和首字输出。记录 RAW/压缩选择原因、失败/回退、原始/存储/分配/重试字节。

同机阶段使用单调时钟；跨机只比较本机时长，若需要跨机关键路径，先验证 PTP 等时钟同步精度并报告误差。不得直接相减未同步的两台机器时间戳。

网络、编码与计算重叠用区间时间线和关键路径判断，不将所有阶段时长相加。分位数不具可加性；要解释哪个请求的哪个等待阻塞了首字。

### 9.3 CPU、I/O Die 与设备资源

- CPU：统计推理调度/worker、codec、网络提交/poll、Store 控制和数据进程、相关内核/IRQ；每节点核秒、占用峰值、按有效请求和有效输出 token 归一化。codec 固定 8 核而其他线程增加时须计入总量。CPU 百分比须说明以单核还是整机为 100%。
- 网络：分别记录应用有效字节、帧元数据、协议/线端口字节、重试与背景流。Wire 压缩率与存储占用比不同。
- 设备/PCIe：记录原生和压缩路径 H2D/D2H 字节、设备计算/codec kernel 占用与等待；Host 压缩不自动减少 H2D 原始流量。
- DDR/片间/I/O Die：保存实际拓扑与计数器归属表。若无直接 I/O Die PMU，仅报告可归属的 RC、DDR、片间代理指标，不称为精确 I/O Die 利用率。不得将多个范围重叠的 uncore 计数重复相加。
- 内存：RSS/PSS、锁页/注册池实际驻留、Store 物理分配、碎片、副本和 staging 峰值；注意映射共享页不要多进程重复计费。容量实验统一同一计费口径。

相同到达率实验比较绝对负载和单位合格产出的负载；最大容量实验比较 Goodput 与单位资源消耗。压缩组处理更多有效请求时总 CPU 上升可接受，但应说明是吞吐换资源；不能仅凭 CPU/request 下降宣称整机 CPU 下降。

稳态资源/合格请求默认用同一稳态窗资源除以稳态完成合格请求数，并核验边界积压稳定；需要 cohort 全生命周期成本时，应单独追踪该 cohort 的成本和观察尾部，不能混用 cohort 分母与稳态资源分子。

### 9.4 采样开销

先在 B0 上比较轻量统计开/关，确认插桩对 TTFT、吞吐、CPU 影响。细粒度 trace 仅采样请求，PMU 批量采集并检查复用；不要每片同步打印或高频系统调用。建议仪表扰动目标 <1%，超出时降低采样并重测，不能直接当作方案开销。

## 10. 重复、统计与准出

### 10.1 重复与报告口径

每个核心点至少 5 次独立运行，A/B 顺序随机或交替。每次先预热到队列、频率与缓存状态稳定，再进入正式窗口；建议起始用 10 分钟，容量拐点与多轮场景依据收敛延长，不以固定分钟替代稳态检查。

P99 结果建议累积 ≥10000 个有效请求，仍须给置信区间；低速场景延长窗口，达不到则写“P99 样本不足”。多轮请求有关联，应按会话或运行分组做 block bootstrap，避免把 token 或片当成独立请求以缩窄置信区间。

报告成对改善值及 95% 置信区间；噪声跨过 0 时不宣称确定收益。算法调参数据与验收数据分离，最终重跑冻结配置。不反复挑选最优一轮作为主结果。

### 10.2 软件路线验收建议

下表为项目本轮建议目标，不是论文事实。SLO 绝对值与主业务权重在 P0 冻结；表内改善率为相对 B0。

| 验收项 | 建议通过标准 | 失败后的决策 |
| --- | --- | --- |
| 正确性 | 无损逐位一致、无提前消费、无取消后槽复用错误；所有功能用例通过 | 阻断该路线性能准出 |
| 网络受限 E01 | TTFT P95 降低 ≥10%，且 95% CI 的改善下界 >0；同时满足非退化约束 | 仅保留有证据的更窄工况，或禁用 |
| 容量受限 E02 | 最大稳定 Goodput 提升 ≥10%，CI 改善下界 >0；物理总预算相同，命中/重算证据闭合 | 不宣称容量业务收益；检查热点重复与额外池 |
| 资源节省路线 | 相同负载、质量和 SLO 下，总 CPU 核秒/合格请求或可归属 I/O 流量/合格请求下降 ≥10%，CI 下界 >0 | 只报告确实下降的资源；CPU/I/O各自结论 |
| 非退化约束 | 各必测主工况 TTFT P99、TPOT P99、可观测 ITL P99 劣化率的单侧95%置信上界不超过 3%；达标率损失置信上界不超过 0.5 个百分点；无新数据错误。不可观测ITL按§9.1预注册分支处理 | 证据不足则不签该项通过；配置缩小范围或回原生，不靠删除慢请求修饰结果 |
| 混合业务 E04/E05 | 预先冻结的主业务 TTFT P95 降≥10%，或最大稳定完成 Goodput 升≥10%，或满足资源节省路线；改善CI下界>0，各类均检查非退化。固定低负载且双方全部达标时，以 TTFT 或单位资源变化判定价值 | 不以单一长上下文最好结果作为默认上线依据 |

每条待启用路线至少通过一个业务价值分支，并满足正确性与非退化。P0 明确宣称的是低 TTFT、更多吞吐还是资源节省，避免试验后随结果更换目标。若针对某类场景专门启用，准出范围应写清，混合业务验证选择器能识别并绕过无收益请求。

E3 全系统项目目标可继续使用 TTFT 降 ≥20%、QPS 提升 ≥10%、TPOT 干扰 <3%，但这是全系统最终目标，不能要求压缩单项独自承担，更不能把多项局部改善叠加当成达标。

### 10.3 IOStash 独立验收

I1/I0 用于早期筛选。**IOStash 单项准出必须重新冻结最终窗口、帧、写策略、亲和、分区、线程配额与远端路径，仅切换 stash off/on 做成对业务复验。**建议该差值的在线业务指标改善 ≥5%，或相同 SLO 与负载下总 CPU 核秒/合格请求、可归属 DDR/片间流量/合格请求至少一项降低 ≥10%；其 95% CI 改善下界 >0，并满足同样非退化约束。DDR完整总量结论还须满足 §6.3 边界条件。

最终组合相对 B0 和最佳软件组的结果用于整条路线净收益，不能替代上述同配置开关的增量证据。固件开关同时改变其他设备流、或不能独立切换时，明确归属“平台组合设置”，IOStash 单项保持未辨识，不签单项通过。

还需有平台配置和硬件/运行证据相符。若只有 codec microbench 加快而在线无价值，记“机制有效但本业务不值得启用”；若只有缓存命中变高且单位业务资源/时延不变，不判业务通过。IOStash 不适用不否定软件压缩方案。

### 10.4 有损分支质量验收

独立比较原生 BF16、已有框架 FP8、拟新增量化、量化再无损压缩。参数、尺度和 codec 命名空间不同，不能混用缓存。拟新增默认建议：主任务正确率下降不超过 0.5 个百分点，关键长上下文检索与代码任务成功率下降不超过 0.5 个百分点，困惑度相对升高不超过 1%；均用预先冻结数据集和 95% CI 做非劣效判定。

样本量不足以排除上述质量损失时，保持实验状态；不能只看平均值“变化很小”。多轮累计误差、异常/饱和比例及长输出稳定性单列。质量通过后仍要经过同样的业务与资源验收。

## 11. 执行顺序、失败定位与结果资产

### 11.1 开发人员与 Agent 执行清单

| 次序 | 操作 | 必须提交的证据 |
| --- | --- | --- |
| T0 | 固定实际版本/配置/拓扑、SLO和主价值目标；确认原生路径 | manifest、回调图、原生 B0 稳态与插桩扰动 |
| T1 | 导出真实 corpus，确定 bound、帧、RAW分支 | corpus manifest、逐位一致性、最坏界/非法帧记录 |
| T2 | L0 选最小有效算法/核数/片大小 | 分层压缩率、核秒、编码/解码、内存曲线 |
| T3 | SGLang RAW→压缩，vLLM RAW Host→压缩；小规模恢复与取消 | 功能矩阵、时间线、失败/引用释放记录 |
| T4 | L2 原生与候选恢复闭环；软件消融 | 全路径延迟、byte/WR/RPC、CPU/DDR/PCIe及实际引擎 |
| T5 | E01/E03 最小在线收益实验 | 低负载/网络受限/无收益点；决定是否深化 |
| T6 | IOStash 能力→最小硬件→真实解码实验 | 配置依据、开关状态、完整对象窗口曲线、观察窗字节与残留写回边界 |
| T7 | E02/E04/E05/E06与最终配置复测 | 同物理预算容量、混合/混压、统计区间与范围配置 |

### 11.2 失败现象到行动

| 现象 | 优先检查 | 调整方向 |
| --- | --- | --- |
| r 较好但 TTFT 更差 | 新增编码/解码、D2H/H2D、组批等待和排队 | 小对象 RAW、降低等待、保留直达或重算 |
| TTFT 好但长输出慢 | codec争用调度/poll核、内存/片间和设备资源 | 限制后台核数、在途字节与优先级，验证前台生成 |
| 逻辑带宽好但 QPS无变化 | 计算瓶颈、到达负载不足、设备容量限制 | 标明仅局部收益；使用适合的网络/容量工况验证 |
| CPU/request下降但整机CPU上升 | 实际服务量改变、额外 Store 与 IRQ 未统计 | 双报绝对与归一化，固定负载再比较 |
| IOStash命中高但DDR未降 | 写回、输出驱逐、共享缓存计数混入 | 完整排空对账，校核事件范围；保留不可证结论 |
| 压缩池容量好但命中没提高 | 热点已装下、原始热副本过大、备份丢弃/写入滞后 | 固定总预算与真实冷热轨迹，统计可用命中 |
| 小窗口L3好但吞吐降 | 在途量不足、输入/输出信用互相阻塞 | 核对带宽时延积，拆开两种槽生命周期 |
