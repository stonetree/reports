## 0. 本次修订结论与口径变更

V3.3 不是在 V3.2 后附加若干说明，而是按两轮初评反馈对立项论证逻辑进行重新组织。主要变化如下。

| 修订项 | V3.3 统一口径 |
|---|---|
| 竞争力证明 | 不承诺“项目完成后必然优于开源方案”；改为提出可证伪的条件性主张，并用同条件对照、消融和阶段门禁形成证据 |
| 客户价值主线 | 从“功能更全、支持介质更多”转为“降低 P99 TTFT、守住 TPOT 尾部、降低单位服务目标合格请求成本” |
| 开源关系 | Mooncake、LMCache 与本项目共生共存；关系是接口兼容、标准开放、能力互补，核心系统独立建设、独立验收、独立承担第一方责任 |
| 比较方式 | 不陷入单项功能有无、短期性能高低的静态比较；重点比较目标硬件第一方适配、非公开微架构信息、跨固件/驱动/运行时协同、P99 安全包络和客户结果责任 |
| 元数据加速 | UBMEM 微基准只说明硬件原语潜力，不能直接折算为端到端收益；完整证据必须覆盖原语、完整前缀查询和端到端三层 |

| P99 竞争力 | 将高并发、后台搬运和资源争用下的 P99 时延断崖作为核心竞争力方向；硬件服务质量控制与实时观测共同形成保护机制 |
| 控制信息缓存定向写入 | 仅用于目录增量、就绪位、完成事件、描述符头和路径状态等小型控制信息，不用于大块 KV 数据正文 |
| DDR 定位 | 不再把“DDR 热缓存”列为顶层差异化；DDR 只保留为经实测证明正收益的条件层级或控制/注册内存角色 |
| 成本口径 | 引入“单位服务目标合格请求成本”，显式核算 NPU、HBM、CPU/DDR、网络、SSD、能耗、软件与运维增量，禁止只计算收益不计算新增成本 |
| 项目基线 | 更新为 2 条系统能力、24 条技术锚点、144 条正式 SRS、5 条工程建议、149 条来源需求、38 个独立交付功能实体和 203 个开发工作包；验证基线为 8 个必做包和 3 个条件项 |
| 用语 | 不使用含义不透明的内部缩写；开源对照统一表述为“当前最佳可行开源组合”；正文以中文表述为主 |

# 第一部分　立项结论：为什么值得做、为什么现在做、为什么由硬件厂商独立做

## 1. 一页结论

本项目应被定义为**面向国产 AI 硬件的第一方推理状态基础设施工程**，而不是另一个缓存组件，也不是对 Mooncake、LMCache 等开源项目的替代工程。KVCache 是首个高价值状态工作负载；项目要完成的核心工作，是把国产硬件的内存、互联、存储、队列、完成语义和运行计数器编译成可被推理框架稳定消费、可验证、可回退、可跨版本认证的端到端能力。

立项依据不是“我们已经证明所有指标领先”，而是以下四点同时成立：

1. KVCache 已经成为在线推理中连接算力、内存、网络、存储和调度的关键状态，直接影响 TTFT、TPOT、吞吐、有效容量和全生命周期成本。
2. 国产硬件拥有 UBMEM、URMA 等有潜力的第一方能力，但从硬件原语到客户业务收益之间仍缺少统一语义、状态决策、传输编排、服务质量控制、证据对账和版本认证层。
3. 开源项目提供了优秀且持续演进的公共能力，但不会天然承担特定国产芯片的非公开微架构优化、跨固件/驱动/运行时协同、首发同步适配、P99 安全包络和客户结果责任。
4. 项目已经形成四层架构、三类契约、149 条来源需求、38 个独立交付功能实体、203 个开发工作包以及 8+3 个原型验证包，具备以阶段门禁控制投入的工程基础。

因此，建议批准**有条件、分阶段**立项：先用 4～5 周原型验证关闭关键事实，再依据 E0～E3 门禁逐步释放投入；若关键假设不成立，应按预设退出条件缩项，而不是以愿景替代证据。

## 2. 为什么要做

### 2.1 AI Infra 正从“算力供给”转向“高价值状态管理”

大模型在线推理的成本不只来自算子执行。相同系统提示词、知识片段、工具定义、多轮会话和智能体上下文会反复产生大规模 KVCache。如果这些状态只能由单个框架实例局部管理，就会出现重复输入预计算、HBM 孤岛、跨节点重复拉取、后台搬运干扰逐词生成、过期或错误对象被消费，以及“底层峰值带宽很高但客户没有收益”等问题。

统一异构 KVCache 存储池的价值，不是简单把更多字节放到 HBM、DDR 或 SSD，而是完成以下闭环：

> 识别可复用状态 → 判断能否安全消费 → 判断加载是否优于重算 → 选择可预测的数据路径 → 在请求时限内完成挂接 → 保护逐词生成 → 用实际路径和客户指标证明收益。

### 2.2 KVCache 是软硬件协同的高杠杆入口

KVCache 同时触达模型语义、框架布局、内存容量、设备互联、存储分层、硬件队列、完成通知和业务服务目标。单纯优化任何一层都可能被其他层抵消：查询快但数据加载慢，命中多但不可消费，传输带宽高但 P99 排队失控，容量大但 TPOT 被后台流量拖垮，最终都不能形成客户价值。

这正是第一方系统的必要性：只有硬件厂商能够持续把对象语义和请求价值映射到本地/远端内存、互联路径、队列优先级、带宽保留、硬件计数器、错误语义以及版本认证，并把运行反馈反向输入芯片、固件和驱动迭代。

## 3. 为什么现在做

### 3.1 推理竞争焦点已经进入系统级效率

模型服务从单请求演示走向多租户、高并发、长上下文、输入预计算与逐词生成分离、智能体持续上下文后，性能瓶颈越来越多地出现在数据移动、状态复用、内存容量和尾延迟，而不仅是单算子峰值。

如果等到硬件定型后再由上层软件被动适配，很多影响 AI Infra 的硬件能力将缺少真实业务牵引；反之，当前启动可以在芯片、固件、驱动和推理框架仍可共同迭代时形成反馈闭环。

### 3.2 产业厂商正在补齐第一方 AI Infra

下表只用于证明“硬件厂商正向系统、软件和生态深入”，不用于证明各家已经交付完整 KVCache 全生命周期存储池。

| 厂商 | 公开动作 | 对本项目的启示 |
|---|---|---|
| AMD | 收购 ZT Systems，强化机架级系统设计和客户使能；收购 MK1，将针对 AMD 内存架构优化的高性能推理技术纳入企业 AI 软件栈 | 硬件竞争已扩展到系统、推理软件、内存架构利用和客户交付 |
| NVIDIA | Dynamo 提供推理路由、分离式服务、KVCache 管理与外部存储扩展，并继续与 LMCache 等开源能力集成 | 第一方软件栈与开源生态并不冲突；硬件厂商仍需掌握端到端系统责任 |
| Intel | OpenVINO 持续提供面向 Intel CPU/GPU 的推理优化，包括 KVCache 量化以降低内存占用并改善时延和吞吐 | 第一方软件负责把硬件特性转化为框架可用能力，是芯片竞争力的一部分 |
| Arm | KleidiAI 以面向 Arm CPU 的优化微内核帮助上层框架利用特定指令和微架构能力 | 统一接口之下仍需要第一方深度优化；硬件特性不会自动转化为应用性能 |

产业证据支持的判断是：**AI 硬件厂商正在从器件供应者转向系统能力提供者。KVCache 是推理状态层的重要收敛点，但不能把上述动作夸大为每家厂商都已公开交付完整的 KVCache 生命周期系统。**

## 4. 为什么要独立做

“独立做”不意味着封闭，也不意味着拒绝开源，而是指项目必须掌握以下不可外包的第一方责任：

- 目标国产硬件的首发同步使能与版本认证；
- UBMEM、URMA、内存层级、互联拓扑、队列、完成与可见性语义的真实能力矩阵；
- 非公开微架构信息和硬件计数器的安全使用；
- 框架布局到硬件传输描述的编译、批量提交与异步执行；
- 高并发下的前后台资源隔离、硬件服务质量控制和 P99 安全包络；
- 错误、过期、未就绪、越权 KVCache 的零消费责任；
- 从请求、决策、对象、实际路径到 TTFT/TPOT/成本的归因；
- 跨芯片、固件、驱动、框架版本的持续回归和客户问题闭环。

如果这些能力只能依赖社区节奏或公开接口，硬件厂商就无法稳定回答三个关键问题：**特定请求为什么慢、硬件能力为什么没有转成业务收益、下一代硬件应该补什么。**

## 5. 我们为什么要做：硬件厂商的独特位置

硬件厂商的第一方优势不是“代码更靠近硬件”这一句，而是能形成其他主体难以长期复制的闭环：

```text
业务请求价值
  → KV 对象语义与生命周期
  → 载入/重算与路径决策
  → UBMEM/URMA/队列/带宽/完成语义
  → 硬件实时观测与 P99 保护
  → 客户 TTFT、TPOT、吞吐和成本
  → 反哺芯片、固件、驱动与框架
```

最终交付应同时承担两类价值：

1. **客户与产品价值。** 在相同模型质量、硬件预算和服务目标下，减少重复输入预计算，提升正价值真实复用，降低 P99 TTFT，守住 TPOT 尾部，提升有效容量和合格请求吞吐。
2. **生态与样本工程价值。** 建立国产硬件第一方 AI Infra 的对象模型、接口、探针、测试、认证、运维和客户交付范式，并孵化内存访问、数据传输、硬件服务质量控制、运行观测、框架连接器等底层软件能力。

# 第二部分　与开源共生：比较的是第一方责任，不是静态功能清单

## 6. 公平比较原则

### 6.1 统一比较条件

所有竞争力对照必须固定以下条件：

- 同一目标硬件、固件、驱动和拓扑；
- 同一模型、权重、分词器、提示模板、KV 布局和精度；
- 同一框架版本、调度参数、并发、到达分布和统计窗口；
- 同一介质配置、网络配置、前缀缓存和换出开关；
- 同一 TTFT、TPOT、正确性和可用性服务目标；
- 同等工程适配时间和调优预算；
- 对照对象使用冻结时点的“当前最佳可行开源组合”，不与默认开箱配置比较。

### 6.2 不做三类不公平比较

1. 不以“某一版本暂时没有某功能”推导长期壁垒；开源软件会持续演进。
2. 不用单一峰值带宽、P50 或平均值替代高并发 P99 和端到端客户结果。
3. 不把本项目可接触的非公开硬件信息隐藏在结果里；必须通过“移除非公开微架构信息”消融量化第一方信息的真实贡献。

## 7. Mooncake 的公开能力与合理边界

### 7.1 公开能力

Mooncake Store 已公开提供面向 LLM 推理的分布式 KV 对象存储、元数据管理、多副本、内存与 SSD 分层、零拷贝与多网卡传输，并支持 vLLM、SGLang、LMCache 等集成。其公开测试在 H800、8 路 RoCE、Qwen3-8B、最大并发 1 的条件下，1K 输入对应 146 MB KV 数据、平均 TTFT 67.29 ms、传输时间 1.50 ms、实际带宽 95.23 GB/s。

这些数据说明 Mooncake 在对象存储和跨节点传输方面已经具有很强能力，不能被简化为“只做传输”。

### 7.2 相对本项目第一方责任的边界

Mooncake 的公开能力不能自动替代以下工作：

- 目标国产芯片的 UBMEM/URMA 原生语义、非公开计数器和跨版本认证；
- 将 KV 对象价值映射为目标硬件队列、带宽保留和前后台资源类别；
- 在目标业务高并发、后台回源和迁移混压下证明 P99 安全包络；
- 对“候选存在—安全可消费—加载有正收益—实际路径成功—客户服务目标改善”全漏斗负责；
- 对特定客户的错误消费、尾延迟断崖和单位合格请求成本承担端到端归因。

尤其要注意：上述 Mooncake 公布的 1K 数据是最大并发 1 下的平均 TTFT，不能据此推导高并发 P99，也不能反向证明 Mooncake 在高并发 P99 上存在问题。它只说明后续公平测试必须补齐负载曲线、尾延迟和混压条件。

## 8. LMCache 的公开能力与合理边界

### 8.1 公开能力

LMCache 面向推理框架提供多层 KVCache 存储与复用，覆盖 GPU 内存、CPU DRAM、本地磁盘/NVMe 和远端后端；其公开架构明确把 CPU DRAM 作为近期 KV 块的热缓存，并通过框架连接器扩展 KVCache 的保存、加载和复用范围。

因此，“支持 DDR 热缓存”本身不构成本项目差异化，项目也不应围绕这一点建立竞争叙事。

### 8.2 相对本项目第一方责任的边界

LMCache 的框架侧和多层存储能力不能自动替代：

- 目标国产硬件 UBMEM/URMA 的第一方深度适配和硬件能力认证；
- 非公开微架构信息、硬件错误语义、队列和带宽控制的跨层协同；
- 以 P99 TTFT、TPOT 尾部、实际路径和单位合格请求成本为结果的客户责任；
- 将运行反馈持续反哺芯片、固件和驱动路线的闭环。

## 9. 本项目与开源方案的关系

统一表述如下：

> 本项目与 Mooncake、LMCache 等开源项目是共生共存关系。项目保持接口兼容、标准开放和能力互补，但第一方核心能力必须独立建设、独立验证并独立承担目标国产硬件上的客户结果责任。

本项目的竞争力不应写成“开源没有、我们有”，而应写成：

| 维度 | 开源项目的合理角色 | 本项目必须承担的第一方角色 |
|---|---|---|
| 社区通用能力 | 提供跨厂商、跨框架的公共抽象、实现和快速创新 | 参与并兼容生态，同时保证目标硬件的稳定适配 |
| 硬件深度 | 依赖公开接口、社区贡献和厂商适配 | 使用目标硬件完整能力、非公开信息与工程团队形成深度协同 |
| 性能责任 | 提供公开基准和社区可复现能力 | 在目标客户工作负载和服务目标下对 P99、正确性和成本负责 |
| 版本责任 | 随社区版本发布和维护 | 覆盖芯片、固件、驱动、框架、存储和网络组合的认证矩阵 |
| 反馈闭环 | 通过 issue、PR 和社区路线演进 | 直接牵引下一代硬件、固件、驱动和系统软件需求 |

### 9.1 可证伪的竞争力主张

V3.3 采用以下正式主张，不使用“必然领先”的绝对承诺：

> 在具有前缀复用价值的目标业务上，在同一国产硬件、同一模型与框架、同一服务目标和同等调优预算下，第一方 UBMEM 控制面快路径、URMA 数据直达、硬件运行观测与服务质量控制，以及正价值载入/重算决策，有机会相对当前最佳可行开源组合降低 P99 TTFT 和单位服务目标合格请求成本；该增量必须由端到端实测和因果消融证明。

# 第三部分　系统已经定义清楚：架构、契约和交付分解

## 10. 四层架构

| 层级 | 主要职责 | 关键输出 |
|---|---|---|
| 框架意图层 | 接收 vLLM、SGLang 等框架对前缀、时限、目标设备和可节省重算时间的请求 | KV 访问请求、目标缓冲与时限 |
| KV 语义层 | 维护模型/版本/布局/租户身份、对象状态、前缀目录、就绪状态、访问租约和消费资格 | 安全可消费候选、对象与副本信息 |
| 传输管理层 | 形成载入/直接访问/移动/重算/放弃决策，编译批量传输描述，管理完成、可见性和回退 | 访问执行方案、传输描述、完成与挂接凭证 |
| 第一方硬件层 | 暴露 UBMEM、URMA、HBM/DDR/SSD、互联拓扑、硬件队列、服务质量控制和运行计数器 | 实际路径能力、完成事件、硬件观测与错误语义 |

主链路为：

```text
KV 访问请求
  → 安全可消费候选
  → 访问执行方案
  → 批量传输描述 / 完成与可见性屏障
  → 实际路径凭证
  → 可消费引用凭证
  → 客户 TTFT / TPOT / 成本结果
```

## 11. 三类交付契约

1. **正确性契约。** 错误、过期、未就绪、越权和多卡不一致的 KVCache 消费必须为 0；完成通知不能替代数据可见性和完整性证据。
2. **性能契约。** 查询、资格校验、描述编译、传输、排队、挂接和逐词生成干扰必须可分解、可观测；计划路径必须与实际路径对账；必须报告 P50/P95/P99 和负载曲线。
3. **生态契约。** 框架、连接器和硬件能力接口保持版本化、可替换、可回退；开放接口不削弱第一方端到端责任。

# 第四部分　竞争力因果链：从物理命中到正收益真实复用

## 13. 核心问题不是“有没有命中”，而是“命中是否产生客户收益”

一个前缀进入业务价值，需要依次通过以下漏斗：

```text
业务存在可复用前缀
  → 目录发现候选
  → 语义匹配
  → 就绪/租约/多卡/权限校验通过
  → 加载优于重算
  → 实际路径按时成功
  → 挂接并被框架消费
  → TTFT 改善且 TPOT 未受损
  → 请求满足服务目标
```

因此，原始命中率、保存率或可寻址容量都不能单独作为北极星。项目应同时管理：

- 自然前缀复用程度；
- 候选保存和发现能力；
- 安全可消费转化率；
- 正价值决策比例；
- 实际路径成功率；
- 服务目标合格率。

### 13.1 正收益判据

对一次复用请求定义：

```text
复用成本
= 前缀查询
+ 消费资格校验
+ 传输描述生成与提交
+ 排队与数据传输
+ 挂接和同步
```

只有满足下式，才允许执行远端或分层加载：

```text
复用成本 + 风险余量 < 等价重算成本
```

等价的 TTFT 净收益表达为：

```text
TTFT 净收益
= 可避免的输入预计算时间
-（查询 + 资格校验 + 数据加载/传输 + 挂接/同步 + 逐词生成干扰）
```

低元数据时延的作用有两层：第一，直接减少请求固定开销；第二，为后续 KVCache 传输释放等量的时限预算，并降低高并发下控制面排队放大。但它只是必要条件，主要收益仍必须来自更高的正价值可消费复用和更快、更可预测的 KVCache 传输。

## 14. 三项最终竞争力

### 14.1 控制面确定性

通过 UBMEM 构建紧凑、只读为主、缓存行对齐的共享元数据快路径，管理前缀索引、版本、就绪位、访问租约和权限状态；结合本地热目录镜像、批量哈希和范围查询，在并发下压低完整前缀查询的 P99。

可选的“控制信息缓存定向写入”作为组件间小型控制信息快通道，只承载目录增量、就绪位图、完成事件、描述符头、拥塞/路径事件、实际路径凭证和回退事件等 64 B～4 KB 小型信息，使消费 CPU 更快看到关键状态。它不是大块 KV 数据传输通道，且只能作为能力探测后的可关闭增强项。

### 14.2 正价值数据传输

通过 URMA 将碎片化 KV 页编译为批量散布/聚集传输描述，结合对象大小、拓扑、队列深度、实时带宽和重算时间逐请求决策；只有加载具有正收益时才发起传输，否则立即回退重算。

这一能力必须同时优化三件事：

- 减少逐块 CPU 提交和格式转换；
- 提高数据正文直达或低主机参与路径的有效带宽；
- 让排队、完成、可见性、取消和回退具有有界语义。

### 14.3 P99 安全包络

将前台请求触发的 KV 加载、逐词生成依赖和同步，与后台预取、淘汰、迁移、副本构建、SSD 回写和压紧分成不同硬件队列或流量等级；为前台保留带宽、限制后台占用，并使用队列深度、互联带宽、DDR/片上互联压力和 NPU 停顿等硬件观测动态调整。

当预计远端加载接近重算成本时，系统停止等待并回退重算；当 TPOT 尾部接近门槛时，立即限速或暂停后台任务；无价值的预取必须可取消。

这三项能力的关系是：**更高的真实复用率提供收益空间，控制面确定性负责快速确认，正价值传输负责把状态按时送达，P99 安全包络负责保证收益在高负载下不反转。**

## 15. DDR 的正式定位

DDR 不作为顶层竞争力。其角色只能按证据启用：

- 元数据和控制信息；
- 已注册的传输内存池；
- 经实测证明正收益的温前缀或预取缓冲；
- 某些远端低时延访问或故障回退场景。

若 HBM→DDR→HBM 增加 TTFT、引发 TPOT 干扰或转移成本，KV 数据正文应退出该路径。项目不以“支持 DDR”证明领先。

# 第五部分　从初步观察到端到端证据

## 16. UBMEM 元数据加速：当前能说明什么、不能说明什么

### 16.1 当前初步观察｜证据等级 B

内部初步测试观察到：在约 1K 输入 token 条件下，Mooncake Master 侧前缀匹配查询处于数百微秒量级；独立 UBMEM 微基准的访问时延处于数百纳秒量级。当前 UBMEM 微基准尚未集成到 Mooncake Master 或完整前缀查询链路中。

两者不是同层测量：前者包含软件数据结构、哈希/遍历、RPC 或进程边界、版本与状态逻辑等完整查询开销，后者只是底层硬件原语微基准。两者相除只能说明硬件原语存在 2～3 个数量级的潜力，不能直接宣称端到端查询加速相同比例，更不能宣称 TTFT 获得相同比例提升。

### 16.2 三层证据瀑布

| 层级 | 必测内容 | 成功判据 | 能支持的结论 |
|---|---|---|---|
| 第 1 层：硬件原语 | 64 B～4 KB 访问、并发、NUMA/拓扑、缓存命中/未命中、P50/P95/P99 | UBMEM 能在目标硬件上稳定提供低时延，且不造成不可接受的缓存污染和一致性成本 | 底层原语具有潜力 |
| 第 2 层：完整前缀查询 | 哈希、最长前缀匹配、版本、就绪、租约、权限、多卡状态、批量查询 | 完整查询 P99 达到目标，错误/过期候选为 0，随并发增长不出现尾部失控 | 控制面快路径成立 |
| 第 3 层：端到端 | 查询→资格校验→决策→传输→完成/可见性→挂接→剩余输入预计算→首 token | P99 TTFT 改善、TPOT 守门、实际路径与主机参与可对账 | 客户业务收益成立 |

### 16.3 元数据加速的定量边界

如果完整查询从 0.300 ms 降到 0.005 ms，单请求直接节省只有 0.295 ms。它的重要性主要体现在：

1. 为后续 KVCache 传输增加 0.295 ms 的等量时限容忍度；
2. 降低控制面在高并发下进入排队区间的概率；
3. 让载入/重算决策有时间使用更完整的实时状态；
4. 为小前缀或短重算场景降低固定成本。

因此，元数据快路径必须与 URMA 数据传输、批量描述编译、硬件服务质量控制和载入/重算决策作为一条完整因果链验证。

# 第六部分　30% / 50% / 70% / 90% 前缀复用场景的立项测算

## 17. 测算用途与限制

> **重要声明：以下是立项测算假设，非当前实测。** 所有数字都是为了回答“各环节应达到什么量级、收益来自哪里、原型应在哪些环节发力”，必须由目标国产硬件上的请求级原始数据替换。分位数不能简单相加，表中结果是使用 P99 路径预算参数形成的单位请求加权估算，不是统计意义上的实测 P99。

### 17.1 变量定义

| 变量 | 定义 |
|---|---|
| `r` | 业务请求中具备完整 1K 前缀复用机会的比例，取 30%、50%、70%、90% |
| `u` | 复用机会转化为“安全、可消费、正价值且路径成功”的综合概率 |
| `c` | 实际正价值消费比例，`c = r × u` |
| `T_fixed` | 每个请求进入复用判断所支付的查询、资格校验、描述提交和挂接/同步固定开销 |
| `T_prefill` | 对完整 1K 前缀重新执行输入预计算的时间 |
| `T_load` | 对完整 1K 前缀的数据传输和 P99 排队预算 |
| `T_other` | 引擎、路由等与复用方案无关的固定时间 |

若存在部分前缀复用，引入平均“等价输入预计算成本节省比例” `p`；只有在输入预计算成本近似随 token 线性变化时，它才可近似为可复用 token 比例。此时：

```text
c = r × u × p
```

更严格的做法是逐请求计算被节省的 token 和层数，而不是把所有命中视为完整前缀。

### 17.2 正价值可消费转化率

本测算把综合转化率拆为四个可验证环节：

```text
u = 语义与候选保持率
  × 就绪/租约/多卡/权限通过率
  × 实际路径按时成功率
  × 载入具有正收益的比例
```

| 环节 | 当前最佳可行开源组合假设 | 本项目目标假设 | 主要发力点 |
|---|---:|---:|---|
| 语义与候选保持率 | 90% | 97% | 统一语义身份、生命周期、缓存感知路由和价值保持 |
| 就绪/租约/多卡/权限通过率 | 95% | 99% | 共享元数据快路径、消费资格屏障、状态一致性 |
| 实际路径按时成功率 | 95% | 99% | 实际路径能力矩阵、URMA 直达、完成/可见性和有界回退 |
| 载入具有正收益的比例 | 98% | 99% | 载入/重算决策、实时观测、拥塞止损 |
| 综合 `u` | `0.90×0.95×0.95×0.98 = 79.60%` | `0.97×0.99×0.99×0.99 = 94.12%` | 全链路联合提升 |

这些比例不是对 Mooncake 或 LMCache 的实测评价，只是建立敏感性模型的占位假设。原型验证必须逐项填实，不允许只调节综合系数得到目标结论。

四项比例在实测时必须定义为漏斗中“以上一阶段通过者为分母”的条件通过率，因此可以连乘；如果采集的是彼此重叠的边际比例，则不能直接相乘。

## 18. 各环节时延预算与技术措施

场景假设：1K 输入 token、可复用请求复用完整前缀。

| 环节 | 当前最佳可行开源组合假设 | 本项目目标假设 | 差值 | 本项目发力措施 | 必测证据 |
|---|---:|---:|---:|---|---|
| 与方案无关的引擎/路由时间 | 8.000 ms | 8.000 ms | 0 | 固定不变，防止把无关优化计入项目 | 请求级时间戳 |
| 完整 1K 前缀重算 | 60.000 ms | 60.000 ms | 0 | 同硬件同模型固定 | 关闭所有复用后的 P50/P95/P99 |
| 前缀查询 | 0.300 ms | 0.005 ms | 0.295 ms | UBMEM 紧凑共享索引、本地镜像、批量查询 | 完整查询 P50/P95/P99、CPU 周期、并发曲线 |
| 消费资格校验 | 0.100 ms | 0.020 ms | 0.080 ms | 版本/就绪/租约/权限位紧凑布局；小型控制信息缓存定向写入 | 校验 P99、缓存缺失、错误/过期消费=0 |

| 挂接和同步 | 0.800 ms | 0.400 ms | 0.400 ms | 预注册目标缓冲、批量完成/可见性、流式就绪与多卡有界同步 | 完成到可消费 P99、多卡等待、错误挂接=0 |
| 固定复用开销 `T_fixed` | **1.600 ms** | **0.575 ms** | **1.025 ms** | 上述四项合计 | 请求级链路分解 |
| 1K 数据线速传输 | 3.000 ms | 2.000 ms | 1.000 ms | URMA 数据正文直达、低主机参与、批量传输 | 有效带宽、主机正文触碰、完成时延 |
| P99 排队/拥塞预算 | 7.000 ms | 2.500 ms | 4.500 ms | 前后台硬件队列隔离、前台带宽保留、后台限速和拥塞回退 | 负载曲线、队列深度、传输 P99 膨胀 |
| 完整前缀加载 `T_load` | **10.000 ms** | **4.500 ms** | **5.500 ms** | 传输与排队合计 | 请求级实际路径凭证 |

### 18.1 单位请求 TTFT 估算公式

```text
c = r × u

TTFT_est
= T_other
+ T_fixed
+ T_prefill × (1 - c)
+ T_load × c
```

代入本节假设：

```text
当前最佳可行开源组合：TTFT_est = 8 + 1.6 + 60×(1-c_open) + 10×c_open
本项目：                 TTFT_est = 8 + 0.575 + 60×(1-c_project) + 4.5×c_project
```

### 18.2 30% / 50% / 70% / 90% 场景结果

| 业务前缀复用机会 `r` | 开源组合正价值消费比例 | 本项目正价值消费比例 | 开源组合 TTFT 估算 | 本项目 TTFT 估算 | 估算改善 |
|---:|---:|---:|---:|---:|---:|
| 30% | 23.9% | 28.2% | 57.66 ms | 52.90 ms | 8.2% |
| 50% | 39.8% | 47.1% | 49.70 ms | 42.46 ms | 14.6% |
| 70% | 55.7% | 65.9% | 41.74 ms | 32.01 ms | 23.3% |
| 90% | 71.6% | 84.7% | 33.78 ms | 21.56 ms | 36.2% |

正确解读是：业务复用机会越高，第一方系统在可消费转化、数据传输和 P99 排队控制上的优势越容易被放大。**更高复用程度本身不是竞争力结论，只有底层软硬件措施把复用机会转成按时到达的正价值 KVCache，才会形成 TTFT 改善。**

### 18.3 50% 复用机会下的收益来源分解

50% 场景下，两方案估算差值为 7.24 ms。采用顺序分解：

| 收益来源 | 计算 | 节省 | 占总差值 |
|---|---|---:|---:|
| 更快的查询、资格、描述和挂接 | `1.600 - 0.575` | 1.03 ms | 14% |
| 更高的正价值可消费转化 | `(47.06%-39.80%) × (60-10)` | 3.63 ms | 50% |
| 更快且更有界的数据传输 | `47.06% × (10-4.5)` | 2.59 ms | 36% |
| 合计 | 三项相加 | **7.24 ms** | **100%** |

这个分解明确了研发优先级：元数据加速必须做，但不能单独承担主要价值；应把更多资源投入消费资格、实际路径成功、URMA 传输和 P99 排队控制。

### 18.4 复用前缀长度的盈亏平衡点

在“重算时间和数据加载时间随前缀长度近似线性、固定控制开销不变”的简化条件下，最低复用比例为：

```text
p_min = T_fixed / (T_prefill - T_load)
```

代入假设：

- 当前最佳可行开源组合：`1.6 / (60-10) = 3.2%`；
- 本项目：`0.575 / (60-4.5) = 1.0%`。

这表示更低固定开销和更快传输可以让更短前缀也具备正收益，但真实系统还要加入风险余量、部分层复用、数据布局和 TPOT 干扰，不能直接把该阈值作为交付结论。

# 第七部分　P99 尾延迟：第一方软硬件协同的关键竞争力

## 19. 为什么不能只看 P50 或平均值

内部测试观察到，请求时延会随负载缓慢上升，并在接近尾部区间时突然恶化。P50 或平均值可能仍然良好，但少量请求已经因为队列积压、互联拥塞、存储回源、内存带宽争用、完成通知延迟或多卡同步进入时延断崖。

因此，本项目不把“P50 大幅提升”作为核心竞争力表达，而是回答：

> 在并发持续增加、后台迁移和预取存在、网络/内存/存储发生争用时，系统能否延后 P99 断崖、降低尾部放大，并在收益转负前自动回退。

### 19.1 公开数据带来的测试启示

Mooncake 的公开 vLLM 分离式推理测试显示，1K 输入对应 146 MB KVCache，在最大并发 1 时传输时间 1.50 ms、实际带宽 95.23 GB/s、平均 TTFT 67.29 ms。这证明其单请求传输能力很强，但测试条件不能回答高并发 P99。

以同一 146 MB 数据作直观估算：

- 95 GB/s 时，传输约 1.54 ms；
- 若前后台竞争后可用带宽降至 20 GB/s，传输约 7.30 ms；
- 若四个同等传输在单队列串行等待，第 4 个请求完成可能接近 29 ms；
- 若硬件服务质量控制为前台保留 60 GB/s 且允许优先绕过后台队列，纯传输约 2.43 ms。

这组数字是排队机制示例，不是对任何方案的实测评价。它说明平均带宽相同并不代表 P99 相同，硬件队列、带宽保留和取消/回退机制会决定尾部结果。

## 20. P99 保护方案

### 20.1 流量分级

| 类别 | 典型任务 | 策略 |
|---|---|---|
| 前台最高优先级 | 当前请求触发的 KV 加载、逐词生成依赖、完成与同步 | 独立队列/流量等级、带宽下限、短队列、优先完成 |
| 前台普通优先级 | 尚有较宽时限的输入预计算加载、流式回填 | 有界排队，可被高优先级抢占 |
| 后台 | 预取、淘汰、迁移、副本构建、SSD 回写、压紧 | 带宽上限、独立队列深度、TPOT 超门槛立即限速/暂停 |

### 20.2 实时观测与自动动作

实时输入包括 URMA 队列深度、链路有效带宽、DDR/片上互联压力、NPU 停顿、SSD 时延、完成队列积压和最近的载入/重算误差。系统据此执行：

- 预计加载接近重算成本时，停止远端等待并转重算；
- TPOT 尾部接近 3% 守门线时，暂停后台预取和迁移；
- 路径 P99 膨胀超过阈值时，降低并发或切换副本/路径；
- 取消已无机会按时消费的预取和加载；
- 保留实际路径凭证和回退原因，用于客户归因和硬件反馈。

### 20.3 P99 必测指标

| 指标 | 公式或定义 | 用途 |
|---|---|---|
| TTFT 尾部放大 | `P99 TTFT / P50 TTFT` | 识别请求尾部是否失控 |
| 混压干扰 | `P99(前后台混压) / P99(仅前台)` | 量化后台任务影响 |
| 传输 P99 膨胀 | `拥塞 P99 / 空闲 P99` | 量化硬件队列与带宽保护效果 |
| P99 断崖负载点 | P99 曲线斜率突变时的并发/QPS/利用率 | 定义安全运行包络 |
| 负收益/迟到加载率 | 已发起但比重算更慢或未按时消费的比例 | 检验载入/重算决策 |
| 服务目标合格率 | 同时满足 TTFT、TPOT、正确性和可用性的请求占比 | 连接成本和客户价值 |

分位数应在请求级完整链路上计算：先对每个请求求和，再计算总体 P99；不得把各环节独立 P99 直接相加作为严格的端到端 P99。

### 20.4 建议目标门槛

- 复用型工作负载 P99 TTFT 改善 ≥20%；
- 前后台混压时 P99 TPOT 回退 <3%；
- 传输 P99 膨胀 ≤2 倍，作为原型阶段待冻结门槛；
- 负收益或迟到加载 <1%，并持续降低；
- 回退成功率 100%，触发后无错误消费；
- 错误、过期、未就绪、越权 KVCache 消费 =0。

这些是最终目标或原型建议门槛，不是当前实测成绩。

# 第八部分　成本主线：单位服务目标合格请求成本

## 21. 成本北极星

仅看设备采购价或平均每请求成本会掩盖尾延迟失败。本项目采用：

```text
单位服务目标合格请求成本
=（NPU + HBM + CPU/DDR + 网络 + SSD + 能耗 + 软件研发/运维）总成本
 / 同时满足 TTFT、TPOT、正确性和可用性的请求数
```

成本分子和合格请求分母必须使用同一核算周期；设备采购、软件研发和认证投入需按统一规则摊销，不能把一次性成本与单日请求量直接相除。

这一口径同时约束分子和分母：系统即使增加存储、网络或软件成本，只要能减少重复计算、提高合格率和有效容量，仍可能降低单位成本；反之，容量变大但合格请求数不变，不能宣称 TCO 改善。

## 22. 降本因果路线

| 路线 | 直接影响 | 成本计算方法 | 必须扣除的新增成本 |
|---|---|---|---|
| 减少重复输入预计算 | 降低 NPU 时间和能耗 | 节省的 NPU 卡时 × 全成本卡时单价 | 元数据、传输和调度开销 |
| 抑制 P99 断崖 | 提高服务目标合格率，减少超时、重试和空转 | 在成本分子近似不变时比较合格请求分母 | 服务质量控制导致的峰值吞吐让渡 |
| 提升 HBM 有效容量 | 降低内存约束下所需设备数或减少 OOM/抢占 | `所需设备数=max(计算约束, HBM约束, SLO约束)` | SSD、网络、DDR 和迁移成本 |
| URMA 低主机参与传输 | 降低 CPU 拷贝、内存带宽和能耗 | CPU 核时、DDR 字节、主机功耗差值 | NIC/互联资源和注册内存成本 |
| 正价值决策 | 减少迟到加载、错误预取和无效跨节点字节 | 负收益请求数 × 浪费的 NPU/网络/存储时间 | 决策引擎和观测开销 |
| 统一第一方运维 | 缩短故障定位和版本认证时间 | 人力、停机、回滚和客户问题成本 | 长期维护与版本矩阵成本 |

### 22.1 50% 复用机会场景的 NPU 卡时估算

在第 18 节假设下，本项目相对开源组合的正价值消费比例增量为：

```text
47.06% - 39.80% = 7.26 个百分点
```

每请求减少的输入预计算时间为：

```text
60 ms × 7.26% = 4.36 ms / 请求
```

若每天 1,000 万请求，且 60 ms 是 8 卡并行组的墙钟时间，则每日节省：

```text
10,000,000 × 4.36 ms × 8 / 3,600,000
≈ 96.8 NPU 卡时 / 日
```

货币价值为：

```text
96.8 × 单卡全成本小时单价
```

该计算只反映“更高正价值消费”产生的 NPU 计算节省，不包含传输加速带来的请求时延收益，也不能与同一资源收益重复计数。

### 22.2 服务目标合格率对单位成本的影响

在成本分子近似不变时，若服务目标合格率从 95% 提升到 98%，单位合格请求成本变化为：

```text
95 / 98 - 1 = -3.06%
```

即仅通过减少尾部失败、超时和不合格请求，就可能使单位合格请求成本下降约 3.1%。真实核算还要加入服务质量控制的资源保留成本和吞吐变化。

### 22.3 HBM 容量收益的成立条件

设备数应按最紧约束决定：

```text
所需设备数 = max（计算需求设备数，HBM 容量需求设备数，服务目标需求设备数）
```

只有 HBM 容量是最紧约束时，提升 HBM 有效容量才可能直接减少设备数；如果计算或服务目标已是瓶颈，容量收益应体现为减少 OOM、抢占、排队或提高并发，而不能重复计为采购节省。

## 23. 成本对账表

原型和客户验证必须至少输出以下对账项：

| 对账项 | 基线 | 本项目 | 差值 | 证据来源 |
|---|---:|---:|---:|---|
| NPU 重复输入预计算卡时 | 待测 | 待测 | 待算 | 请求 trace + NPU 利用率 |
| P99 超时/重试/空转成本 | 待测 | 待测 | 待算 | SLO 结果 + 回退原因 |
| HBM 容量约束设备数 | 待测 | 待测 | 待算 | 模型容量画像 + 集群水位 |
| CPU 拷贝与 DDR 带宽成本 | 待测 | 待测 | 待算 | 主机正文触碰 + CPU/DDR 计数器 |
| 网络与 SSD 新增成本 | 待测 | 待测 | 待算 | 实际路径字节、IOPS、寿命和功耗 |
| 软件研发、认证和运维成本 | 待测 | 待测 | 待算 | 人力、版本矩阵和故障工单 |
| 单位服务目标合格请求成本 | 待测 | 待测 | 待算 | 上述分子 / 合格请求数 |

### 25.1 三个条件/证伪项

- CVT-01：只有热点前缀扇出超过交叉点时才验证硬件多播；无稳定增量则关闭。
- CVT-02：只有软件并发迁移不能满足暂停与回滚要求时才验证硬件原子地址切换；否则保留软件方案。
- CVT-03：DPU、硬件完成队列路由和硬件编解码只允许提供纯增量；主路径必须在无这些能力时成立，禁止用 CPU 软件编解码伪造收益。

| 可消费命中 | 目录/资格判定组件转化提升 ≥15% | 系统可消费命中率建议提升 ≥20% | 分母、统计窗口和“提升”是百分点还是相对值必须冻结 |

| P99 TTFT | 各路径形成分解预算 | 复用型工作负载改善 ≥20% | 报告所有请求，不只报告命中子集 |
| P99 TPOT | 后台任务自动限速和暂停 | 混压回退 <3% | 作为 TTFT 和容量收益的硬守门指标 |

| 单位合格请求成本 | 分项资源账本完整 | 相对公平基线下降，幅度由 E3 冻结 | 必须扣除新增网络、SSD、软件和运维成本 |

## 29. No-Go 与缩项条件

出现以下任一情况，不得继续扩大投入：

1. 真实业务前缀复用空间不足，或可节省重算时间长期小于控制、传输和挂接成本；
2. UBMEM 只能在微基准中快，完整查询 P99 无显著改善或正确性代价不可接受；
3. URMA 实际路径存在隐式 CPU/DDR 数据正文中转，或有效带宽、完成与可见性无法闭环；
4. 高并发下 P99 断崖无法通过硬件服务质量控制、限速和重算回退被约束；
5. TTFT 改善以 TPOT P99 回退 ≥3%、错误消费或显著成本转移为代价；
6. 与当前最佳可行开源组合相比，完整方案在同条件下没有可重复的端到端增量；
7. 单位服务目标合格请求成本不降，或新增存储、网络、软件和运维成本超过收益。

失败后可按证据缩项为特定硬件路径提供器、传输描述编译器、认证与观测工具、P99 服务质量控制组件或专项加速库，不应以沉没成本维持完整产品形态。

# 第十部分　两轮初评意见的正式化表述与项目响应

## 30. 评审意见一：竞争力证据需要从架构合理性升级为量化、可归因证据

**正式表述：** 现有材料较充分说明了项目定位、架构和第一方责任，但尚不足以证明项目交付后能够在目标场景中形成相对开源方案的性能与成本增量。立项材料应建立从底层硬件能力、控制面、数据传输、可消费复用到客户指标的量化因果链，并明确当前实测、初步观察、立项目标和模型测算的边界。

**V3.3 响应：** 增加三层证据瀑布、五组公平对照、30%～90% 敏感性模型、50% 场景收益分解、P99 指标体系和 E0～E5 证据门。

## 31. 评审意见二：项目故事应以客户 TTFT/TPOT 或成本为主线

**正式表述：** 竞争力论证应从客户可感知结果出发，以 P99 TTFT 改善和单位服务目标合格请求成本下降为主指标，以 P99 TPOT、正确性和可用性为守门指标；命中率、带宽、容量和查询时延只作为可解释的中间驱动指标。

**V3.3 响应：** 统一采用“正价值真实复用”漏斗和单位合格请求成本公式，明确每项技术如何影响 TTFT、TPOT、NPU 卡时、HBM 设备约束和合格请求分母。

## 32. 评审意见三：需要给出不同前缀复用程度下的收益测算

**正式表述：** 应针对 30%、50%、70%、90% 的业务前缀复用机会，给出明确的输入假设、各环节时延预算、计算公式、结果和收益来源分解，并在目标硬件实测后逐项替换假设值。

**V3.3 响应：** 第 17～18 节给出完整模型。模型明确显示，元数据固定开销仅贡献 14% 的 50% 场景差值，更高正价值可消费转化和更快、更有界的传输合计贡献约 86%。

## 33. 评审意见四：软硬件结合必须落到实际技术

**正式表述：** “软硬件结合”不应停留在原则描述，至少需要形成可实现、可测量、可关闭的技术路径，并明确其在端到端收益中的位置。

**V3.3 响应：** 明确三项技术路径：

1. UBMEM 共享元数据快路径与小型控制信息缓存定向写入；
2. URMA 批量传输描述、数据正文直达与动态载入/重算；
3. 硬件服务质量控制、实时观测和 P99 有界回退。

## 34. 评审意见五：尾延迟比 P50 更能体现第一方价值

**正式表述：** 对在线推理系统，仅报告 P50 或平均性能可能掩盖高负载下的尾延迟断崖。项目应以负载—P99 曲线、断崖负载点、混压干扰和传输 P99 膨胀验证第一方软硬件联合优化的实际价值。

**V3.3 响应：** 将 P99 安全包络提升为三项最终竞争力之一，给出流量分级、硬件队列与带宽策略、自动回退动作和必测指标。

## 35. 客户界面收益

## 42. 建议决策

建议批准本项目以“第一方推理状态基础设施工程”立项，并采用以下授权方式：

该决策既承认目前证据尚未完全填实，也避免因等待完整产品而错过软硬件协同窗口。它让项目以有限投入验证最关键的客户价值、技术路径和第一方壁垒。

# 附录 B　可直接复算的公式清单

```text
1. 正价值消费比例
c = r × u
u = 语义与候选保持率 × 消费资格通过率 × 实际路径成功率 × 正收益比例

2. 复用正收益
T_reuse + risk_margin < T_recompute
T_reuse = T_lookup + T_eligibility + T_descriptor + T_queue_transfer + T_attach_sync

3. 单位请求 TTFT 立项估算
TTFT_est = T_other + T_fixed + T_prefill × (1-c) + T_load × c

4. 部分前缀盈亏平衡点（线性简化）
p_min = T_fixed / (T_prefill - T_load)

5. 单位服务目标合格请求成本
C_qualified = (C_NPU + C_HBM + C_CPU_DDR + C_network + C_SSD + C_power + C_software_ops)
              / N_requests_meeting_TTFT_TPOT_correctness_availability

6. HBM 容量是否转化为设备节省
N_required = max(N_compute, N_HBM, N_SLO)

7. 尾延迟指标
TTFT_tail_amplification = P99_TTFT / P50_TTFT
mixed_interference = P99_mixed / P99_foreground_only
transfer_P99_inflation = P99_congested / P99_idle
```
