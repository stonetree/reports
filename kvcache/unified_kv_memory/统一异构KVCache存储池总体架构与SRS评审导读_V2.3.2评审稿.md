## 1. 执行摘要

KVCache（大模型注意力键值缓存，即在自回归生成过程中保存历史 Key/Value 激活状态、避免后续 Token 重复计算注意力）在本文中简称 KVCache。

本轮评审需要确认以下结论：

1. 项目路线调整为基于固定版本 Mooncake 深度重构与架构增强。Mooncake 提供已有接口、传输和集群接入基础；项目可修改内部实现、模块边界和数据路径，不受现有框架范围限制。
2. 路线调整没有要求重做功能需求树。现有对象管理、异构介质、动态选路、语义一致性、多卡同步、服务质量、故障处理和可观测等功能域继续成立。
3. 与 Mooncake 持续上游兼容、补丁重放、退化为原生行为和原生缺陷修复有关的事项，不作为新增产品需求。固定基线、改动内聚、支持范围和完整代码包交付由独立开发协议管理。
4. 路线调整对提前验证可信度提出了更高要求。原生 Mooncake 与增强版必须在同一输入、设备、负载和统计口径下对照；各增强项通过统一打点定位收益和副作用。
5. 原型代码用于建立完整工作流，不要求当前已经接入真实设备或形成可运行工程。但命令、参数、输入 Schema、输出字段、比较基线和判定公式必须正确；模拟值不能被识别为实测结果。
6. 当前需求统计为 2 条 SF、24 条 IR、144 条正式 SRS、5 条工程建议、38 条可独立交付 SR 和 203 条 AR。149 条来源项由 144 条 SRS 与 5 条工程建议组成，不能与 144 条正式 SRS 混用。
7. 提前验证结构为 10 个 PVT 和 1 个 CVT。10 个 PVT 均属于立项前验证范围；CVT-01 仅在触发条件满足时执行。

## 3. 术语和指标

| 术语 | 本项目中的含义 |
|---|---|
| Saved-Prefill | 首字生成预计算节省：复用已有 KVCache，减少 Prompt 的重复 Prefill 计算 |
| TTFT | Time To First Token：首 Token 响应时间 |
| TPOT | Time Per Output Token：每个输出 Token 的生成耗时 |
| UBMEM | 统一总线内存直通共享协议：支持跨节点和异构设备直接共享内存地址空间 |
| URMA | 通用远程直接内存访问：用户态高性能 RDMA 驱动接口和通信协议 |
| Direct-View | 远端直读：跨节点直接读取远端显存中的 KV 数据，不产生本地显存拷贝 |
| Copy-to-HBM | 拷贝到本地显存：通过 DMA 将远端 KV 数据搬运到本地 HBM |
| QueryPlan | 查询与放置计划：在请求时限内选择加载、远端直读、SSD 回源或重算路径 |
| ConsumeEligibility | 消费资格校验：检查模型、Tokenizer、模板、LoRA、Ready 和 Lease 等语义状态 |
| RankConsensus | 张量并行多卡状态同步：同步各卡的命中状态和一致动作 |
| SemanticQoS | 前后台服务质量保障：限制后台迁移、换出和拉取对前台 TPOT 的影响 |
| Evidence Level | 证据等级：DEMO、LAB 或 MEASURED |
| INVALID_EVIDENCE | 输入、探针、字段、路径或统计不完整，结果不能用于验收 |

## 4. 项目范围与责任边界

### 4.1 项目负责

- 统一 KV 对象、语义身份、版本、状态和生命周期；
- HBM、DDR、SSD 和远端介质的统一纳管及按收益选路；
- 描述符编译、异步传输、完成通知和可见性管理；
- 加载与重算的动态成本判断；
- 前缀目录、消费资格、租约、多卡同步和故障回退；
- 前后台服务质量、路径观测和端到端指标；
- Mooncake 固定基线上的深度重构、接口适配和完整代码包交付。

### 4.2 不作为当前强制范围

- 跟随任意 Mooncake 上游 Commit；
- 关闭所有增强后恢复为原生 Mooncake 等价行为；
- 以补丁重放方式升级或回退；
- 修复与本项目改动无关的 Mooncake 原生问题；
- 覆盖所有 vLLM、vLLM-Ascend、驱动、固件和硬件组合；
- 在没有代表设备证据时承诺所有目标门槛已经达到。

### 4.3 基线问题处理

原生 Mooncake 对照失败时，先完成问题归因：

- 与项目改动无关的原生问题记录为 `BASELINE_INVALID` 或已知问题；
- 不要求本项目修复原生问题；
- 不能用构造值替代原生基线，也不能把无效基线用于证明增强收益。

## 5. 总体架构

系统按四层组织，横向能力贯穿各层。

| 层级 | 主要职责 | 关键输入输出 |
|---|---|---|
| L1 推理调度层 | 前缀判断预算、加载与重算准入、缓存感知路由、水位和请求调度 | 输入请求、时限和资源状态；输出访问意图和调度动作 |
| L2 KVConnector 层 | 统一接口、布局协商、AttachHandle、状态码、超时和框架接入 | 接收框架调用；输出可执行 QueryPlan、句柄或回退信号 |
| L3 传输管理层 | 对象状态、前缀目录、位置解析、分层策略、描述符、迁移和服务质量 | 维护对象及副本；生成实际传输计划和状态转换 |
| L4 底层传输层 | 内存注册、URMA/RDMA/UBMEM、SSD I/O、完成通知、可见性和硬件错误映射 | 执行数据操作；返回完成、错误、完整性和路径证据 |

横向模块包括：

- 调度与路径决策；
- 统一对象和分层存储；
- 前缀目录与语义身份；
- 传输编排与硬件能力；
- 一致性、安全与前后台服务质量；
- 全路径观测与故障追踪。

## 6. 三条核心流程

### 6.1 命中、加载与接入消费

```text
请求进入
  -> 在 PrefixBudget 内查询前缀目录
  -> 校验语义身份、版本、Ready 和 Lease
  -> 生成 QueryPlan
  -> 比较加载总开销与本地重算耗时
  -> 执行实际路径并记录 actual_path
  -> 完成可见性和多卡状态同步
  -> 返回 AttachHandle 或回退重算
```

判断原则是：拉取、加载、接入和同步总开销小于本地重算耗时时才加载，否则回退重算。

### 6.2 发布与生命周期

```text
分配对象和 Extent
  -> 写入 KV 数据
  -> 完成分路径完整性检查
  -> 发布版本与 Ready
  -> 建立租约和引用计数
  -> 允许消费
  -> 迁移、失效、隔离或回收
```

任何未完成、过期、语义不一致或完整性证据不足的对象均不可消费。

### 6.3 分层与容量

```text
采集复用概率、加载成本、干扰成本和介质能力
  -> 在 HBM、DDR、SSD 和远端介质中选择位置
  -> 必要时直接走 HBM↔SSD
  -> DDR 只在产生持续净收益时承担 warm、remote、prefetch、registered pool 或 fallback staging 角色
  -> 每次位置变化记录触发原因、前后位置和实际成本
```

DDR 不是固定必经层。SSD 是容量主体候选；是否成为正式主路径由 PVT-05 和后续实测决定。

## 9. 提前验证结构

### 9.1 四个核心验证阶段

- E0：确认 Saved-Prefill 净收益在目标复用率下是否存在；
- E1：打通 Host CPU 零数据拷贝、描述符、异步流水、语义校验和多卡状态同步；
- E2：确认远端直读/拷贝边界、动态选路准确性和 SSD 分层扩容收益；
- E3：在代表性跨节点前后台混压下验证 TTFT、QPS 和 TPOT 项目级门槛。

### 9.2 10 个 PVT

| ID | 核心命题 | 主要输出 |
|---|---|---|
| PVT-00 | Saved-Prefill 净收益和通信加速边界 | 实测重算基线、TTFT 分位数和净收益 |
| PVT-01 | Host CPU 零数据拷贝和硬件能力矩阵 | 实际完成量、Host Touch 探针和路径矩阵 |
| PVT-02 | 描述符编译和异步流水 | 正确性、编译 P99、提交事件和重叠率 |
| PVT-03 | Direct-View 与 Copy-to-HBM 边界及安全回退 | Crossover、租约、故障和回退证据 |
| PVT-04 | 微秒级动态决策 | 预测/实际路径、反事实最优和决策后悔值 |
| PVT-05 | SSD 容量主路径和 DDR 条件角色 | 四组对照、可服务容量、OOM 和 Host Touch |
| PVT-06 | 语义一致性和多卡状态同步 | 8 类冲突、独立 Oracle、错误消费和多卡事件 |
| PVT-07 | 前后台混压端到端总门禁 | 原生 Mooncake 混压与增强版混压公平 A/B |

### 9.3 1 个 CVT

CVT-01 验证软件 RCU（Read-Copy-Update，读-拷贝-更新，即通过复制新对象、原子替换引用和宽限期回收旧对象保护并发读）是否足以满足页迁移和显存整理：Reader 停顿 P99 < 1ms、TPOT 干扰率 < 3%、错误读取为 0。无硬件 Atomic Remap 时，硬件对照记 `NOT-SUPPORTED/N/A`。

## 10. Benchmark 和证据契约

每项验证必须填写：验证命题、输入 Schema、被测代码包、对照基线、控制变量、打点、统计、证据等级和结果清单。

统一事件字段至少包括：

```text
run_id, trace_id, request_id, event_name,
monotonic_timestamp_ns, duration_ns,
planned_path, actual_path, payload_bytes,
status, error_code, evidence_level,
package_id, config_hash, hardware_profile
```

证据等级：

- DEMO：Mock、固定样例或 localhost，只证明流程和字段；
- LAB：可用设备组合的局部实测，结论绑定环境；
- MEASURED：代表性跨节点完整路径实测，可关闭对应阶段结论。

环境档位 W0/W1/W2 与实施波次不是同一概念：W0 是单机/Mock，W1 是局部设备实测，W2 是代表性跨节点系统验证。

以下情况必须标记 `INVALID_EVIDENCE`：

- 缺少正式探针、实际完成量或实际路径凭证；
- 输入 Schema 不一致、字段缺失或解析失败；
- 固定样例被标为 LAB/MEASURED；
- 对照模式没有实际切换代码包或配置；
- A/B 的设备、负载、资源配额或后台压力不等价；
- 未保留原始样本、失败请求、版本清单或结果 manifest。

PVT-07 的计算口径固定为：

```text
TTFT/QPS：增强版混压相对原生 Mooncake 混压
TPOT 干扰：增强版混压相对同一增强代码包纯前台
```

## 11. SRS 验收审查方法

V2.3 对 144 条需求的验收文本按需求 ID、模块、场景和直接指标重新生成，避免把批量模板的指标套到无关需求上。每条验收至少检查：

1. 输入来自哪一层，输出由谁使用；
2. 正常、边界和故障状态如何转换；
3. 指标是否直接证明需求描述中的行为；
4. 异常是否阻断错误消费或进入明确回退；
5. 结果是否绑定代码包、配置、环境、原始日志和证据等级；
6. 条件硬件不可用时是否记录 N/A，而不是 PASS；
7. 未采集字段是否使用 `null`，而不是 0。

## 12. 评审检查清单

### 12.1 需求与架构

- 144 条 SRS 是否覆盖四层和六个横向模块；
- 38 条 SR 是否有独立交付物、使用者、接口和回退；
- HBM↔SSD 路径是否允许绕过 DDR；
- 语义身份、Ready、Lease、版本和完整性是否在消费前闭环；
- QueryPlan 是否同时记录预测路径和实际路径；
- 条件硬件是否不阻塞 Raw Direct 软件主路径。

### 12.2 验证

- 10+1 的数量、类型和 IR 追溯是否一致；
- DeepSeek MLA 是否使用运行时布局字节；
- 11 项“明确不做、必须证据、延续资产、证伪标记、周期、IR、SRS 锚点、结论”是否完整；
- 方案命令、原型入口和输出字段是否一致；
- DEMO、LAB、MEASURED 是否区分；
- PVT-07 基线、后台负载和计算公式是否符合公共契约。

### 12.3 Mooncake 对接

- 固定 Commit、全量代码包 ID、配置哈希和支持范围是否明确；
- 项目改动和原生问题是否完成归因；
- 改动是否保持模块内聚并登记接口影响；
- 是否避免把上游生命周期事项误写成产品需求。

## 13. 评审结论格式

| 结论 | 含义 |
|---|---|
| GO | 核心命题、证据和适用边界满足要求，可以进入下一阶段 |
| CONDITIONAL | 仅在限定工作负载、硬件或路径上成立，需要冻结白名单和回退 |
| NO-GO | 核心收益、正确性或路径能力不成立，需要调整架构或范围 |
| NOT-SUPPORTED | 当前平台不具备能力，记录支持边界和替代路径 |
| INVALID-EVIDENCE | 证据不完整或 A/B 不公平，不能形成技术结论 |

每个结论同时记录适用工作负载、模型、软件版本、硬件环境、代码包、配置哈希、原始数据、分位数、异常结果、实际路径、回退和对需求/架构的影响。

## 14. 本轮判断

需求功能主干、总体架构和 10+1 验证主题可以进入后续开发准备。路线调整没有形成需要重做需求树的缺口，也不要求把 Mooncake 上游生命周期内容加入 SRS。

正式冻结前的执行条件是：

- 使用 V1.7 提前验证清单和 Benchmark 公共契约；
- 使用 V2.3 SRS 的逐条验收口径；
