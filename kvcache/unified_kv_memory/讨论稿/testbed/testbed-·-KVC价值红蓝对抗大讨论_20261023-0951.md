> 
> 这才是 HOST 在 Agentic AI 时代围绕 KVC 最硬核的价值。
>

> 
> > **Agentic AI 正在推动 KVCache 从 GPU 内部的一种 attention optimization，演化为跨 HBM、DDR、CXL、SSD、NIC 和远端存储存在的 distributed execution state。**

> # 二、为什么 Agentic AI 会把 KVC 从“显存问题”变成“HOST 系统问题”
> 
> ## 2.1 从 KVC 本身的物理性质出发
> 
> 对一个标准 attention 模型，单 token KV 大小近似：
> 
> $$
> S_{KV/token}
> =
> 2 \times L \times N_{kv} \times D_{head} \times B
> $$
> 
> 其中：
> 
> - $L$：Transformer layer 数；
> - $N_{kv}$：KV heads；
> - $D_{head}$：每个 head 的维度；
> - $B$：数据类型字节数；
> - 前面的 2 分别代表 K 和 V。
> 
> 假设：
> 
> - 80 layers；
> - 8 KV heads；
> - head dimension = 128；
> - BF16 = 2 Bytes；
> 
> 则：
> 
> $$
> S_{KV/token}
> =
> 2\times80\times8\times128\times2
> =
> 327680 Bytes
> \approx 320 KiB/token
> $$
> 
> 128K context 就是约：
> 
> $$
> 320KiB\times128K \approx 40GiB
> $$
> 
> 这意味着一个长上下文 session 的 KV 本身，就可能达到几十 GB。
> 
> 真正重要的是，这些数据具有非常特殊的物理属性：
> 
> 1. **容量巨大；**
> 2. **绝大部分历史 prefix 在生成后基本不再修改；**
> 3. **新 KV 主要以 append 方式产生；**
> 4. **访问不是普通随机缓存访问，而是和 request/session 生命周期强绑定；**
> 5. **不同 block 的“价值”完全不同：有的马上复用，有的可能几十秒、几分钟后才再次使用；**
> 6. **KVC 可以丢，因为可以重新计算，但重算成本非常高。**
> 
> 因此 KVC 既不是普通数据库数据，也不是普通 CPU cache。
> 
> 它更像：
> 
> > **具有确定重建成本的、短至毫秒长至小时生命周期的、可迁移 execution state。**
> 
> 这个定义直接决定了 HOST 软件架构不能简单照搬 page cache、Redis 或普通 block storage。

> # 三、Agentic AI 改变的不是 KV 大小，而是 KV 的“时空分布”
> 
> 传统 chatbot：
> 
> ```text
> Prompt
>  ↓
> Prefill
>  ↓
> Decode
>  ↓
> 结束
> ```
> 
> KVC 生命周期通常与 request/session 较紧密。
> 
> Agent 则是：
> 
> ```text
> LLM
>  ↓
> Tool Call
>  ↓
> Browser / Python / DB / Search
>  ↓
> LLM
>  ↓
> Tool Call
>  ↓
> LLM
>  ↓
> ...
> ```
> 
> 一次 agent 任务可能经历几十甚至上百轮交互。
> 
> 每一轮最特殊的地方在于：
> 
> > **历史 context 很长，但新增加的 delta 很短。**
> 
> 于是：
> 
> $$
> Context_{n+1}
> =
> Context_n+\Delta Context
> $$
> 
> 当：
> 
> $$
> |\Delta Context| \ll |Context_n|
> $$
> 
> 真正需要新增计算的 token 很少，大量已有 KVC 都可以复用。
> 
> SIGCOMM 2026 的 DualPath 正是针对这种生产 Agentic workload：论文指出，多轮、short-append 模式使 KVC storage I/O 而非计算逐渐成为主导瓶颈；通过利用 Decode 节点原本空闲的 storage NIC，增加第二条 KV loading path，其在线 serving throughput 平均提升约 1.96×，且不违反 SLO。([SIGCOMM 会议](https://conferences.sigcomm.org/sigcomm/2026/program/papers/?utm_source=chatgpt.com))
> 
> 所以 Agentic AI 带来的根本变化可以表达为：
> 
> $$
> \frac{Bytes_{KV\ reused}}
> {FLOPs_{incremental\ compute}}
> \uparrow
> $$
> 
> 即：
> 
> > **每执行一单位新的计算，需要重新取得的历史状态越来越多。**
> 
> 这才是 HOST 价值迅速放大的数学根源。
>

>  ↓

> =
> T_{queue}
> +
> T_{lookup}
> +
> T_{placement}
> +

>       ↓

>       ↓

>

> 
> > **它存在明显的 queueing / capacity / backpressure 放大效应。**

> # 五、KVC 数据面：最先进的 HOST 架构恰恰应该尽量少让 CPU 核“碰数据”
> 
> 这是一个非常重要的反直觉结论。
> 
> 错误设计：
> 
> ```text
> NIC
>  ↓
> CPU buffer
>  ↓ memcpy
> another CPU buffer
>  ↓
> cudaMemcpy
>  ↓
> GPU
> ```
> 
> 这种路径：
> 
> - 消耗 CPU cycles；
> - 占用 DDR bandwidth；
> - 污染 cache；
> - 增加 memory copy；
> - 增加 NUMA traffic；
> - 增加 tail latency。

> ```text
>              ┌──────── GPUDirect RDMA ───────→ GPU

>              └→ DDR / CXL ─→ accelerator DMA → GPU

> 
> ```text
> allocate
> register
> authorize
> schedule
> describe
> submit
> monitor
> recover

> ```text

> ```
> 
> 不是所有 copy 都走一个 primitive。
> 
> **Transfer Engine 应当成为 runtime compiler。**
> 
> 它根据：
> 
> $$
> (size,\ source,\ destination,\ topology,\ SLO,\ contention)
> $$
> 
> 选择不同 data mover。
> 
> 这才是 CPU SoC 中各种 accelerator 真正进入 AI Infra 的方式。
> 
> ---
> 
> ## NVIDIA：把 CPU memory 直接拉近 GPU
> 
> NVIDIA 走的是另一条非常激进的路线：
> 
> > **缩小 CPU memory 和 GPU memory 之间的物理距离。**
> 
> Grace/Hopper 使用 coherent NVLink-C2C；DirectKV 在 OSDI 2026 已经直接证明，在 GH200 这类高带宽 CPU-GPU 平台上，可以让 GPU kernel 直接访问 CPU-resident KV，而不必先复制到额外 GPU staging buffer。DirectKV 在 GH200 上降低最多 50% CPU-GPU transfer volume、减少 43% GPU memory use，并获得最高约 1.2× end-to-end speedup。([USENIX](https://www.usenix.org/conference/osdi26/presentation/luo?utm_source=chatgpt.com))
> 
> 最新 Vera 则进一步把方向推向：
> 
> - up to 1.2 TB/s CPU memory bandwidth；
> - up to 1.8 TB/s coherent NVLink-C2C；
> - 针对 control-heavy、branch-heavy agentic workload 设计 CPU cores。([NVIDIA](https://www.nvidia.com/en-us/data-center/vera-cpu/?utm_source=chatgpt.com))
> 
> 从 KVC 角度看，这意味着过去：
> 
> ```text
> Host Memory
>      │
>      │ explicit copy
>      ↓
> HBM
> ```
> 
> 开始可能变成：
> 
> ```text
> Host Memory
>      ↑↓
> GPU direct/coherent access
> ```
> 
> 于是：
> 
> > **HOST memory 不再只是“GPU cache 的 swap space”，而可能成为 accelerator 可以直接消费的第二级 working memory。**
> 
> 这是非常大的体系结构变化。
>

> │                                         │

> 
> # Transfer Planner / Transfer Compiler
>

> Move KVBlock X
> from Node A / SSD

> before deadline T
> ```
>

> SSD
>  ↓

>  ↓

> NIC
>  ↓

>  ↓

> +

> +

> +
> SLOPenalty
> $$

> 
> > **heterogeneous memory and data-movement operating system。**

> # 十、Agentic AI 最需要 HOST 的地方，其实是“冷热状态之间的时间空洞”
> 
> 这是 Agentic workload 与普通 long-context inference 最大的区别之一。
> 
> Agent 调用：
> 
> - browser；
> - Python；
> - database；
> - remote API；
> - search；
> - another agent；
> 
> 期间 GPU 根本不需要一直持有该 session 的 KV。
> 
> 假设一个 agent：
> 
> ```text
> GPU inference  300 ms
> tool call       5 s
> GPU inference  200 ms
> tool call      20 s
> GPU inference  400 ms
> ```
> 
> 如果整个 25 秒都占用 HBM：
> 
> > HBM residency 和 GPU compute residency 完全失配。
> 
> 正确方式应该是：
> 
> ```text
> GPU compute complete
>        ↓
> predict reuse interval
>        ↓
> HBM → DDR/CXL
>        ↓
> tool execution
>        ↓
> prefetch before next LLM turn
>        ↓
> DDR/CXL → HBM
> ```
> 
> 因此 HOST 要优化的不是简单 LRU，而是：
> 
> $$
> Placement
> =
> f(
> reuse\ probability,
> reuse\ deadline,
> KV\ size,
> recompute\ cost,
> transfer\ cost,
> tier\ pressure
> )
> $$
> 
> 这也是 SYMPHONY 使用 workload-derived advisory request 做提前 prefetch 的核心动机：把 KVC migration 从 foreground critical path 尽可能移走。其 NSDI 2026 实验中，相比 vLLM end-to-end latency 最多降低 2.4×，同时可在较小 latency 增长下服务约 4× 更多请求。([USENIX](https://www.usenix.org/conference/nsdi26/presentation/agarwal?utm_source=chatgpt.com))
>

> # 十一、多 Agent 会进一步把 HOST 推向“共享状态管理器”
> 
> 单 Agent 是：
> 
> ```text
> one session
>    ↓
> one growing prefix
> ```
> 
> Multi-Agent 则可能出现：
> 
> ```text
>              shared history
>             /      |      \
>         Agent A  Agent B  Agent C
> ```
> 
> 这会产生新的问题：
> 
> - 同一个 context 是否产生 N 份 KV？
> - sibling agent cache 能否 Copy-on-Write？
> - 不同 LoRA / system prompt 下哪些 block 可以共享？
> - shared prefix 谁负责 refcount？
> - agent branch 回滚如何处理？
> - block version 怎么定义？
> 
> 2026 年的 TokenDance 已经观察到 multi-agent round 中的 All-Gather 式 context sharing 会产生大量 KV duplication；其 preprint 通过 collective KV sharing 与 differential representation，在实验中显著减少 per-agent KV footprint。([arXiv](https://arxiv.org/abs/2604.03143?utm_source=chatgpt.com))
> 
> 这里 CPU/HOST 的角色会进一步从：
> 
> **memory manager**
> 
> 升级成：
> 
> **state relationship manager。**
> 
> 未来 KVC metadata 很可能不再只是：
> 
> ```text
> hash → block address
> ```
> 
> 而是：
> 
> ```text
> Session
>  ├─ Branch
>  ├─ Version
>  ├─ Parent
>  ├─ Shared Prefix
>  ├─ Replica
>  ├─ Placement
>  ├─ Residency
>  ├─ Consumer
>  └─ Lease
> ```
> 
> 这显然已经接近一个 distributed object system。
>

> # 十二、为什么 CXL 对 HOST 很重要，但不能把 CXL 神化
> 
> CXL 非常适合 KVC。
> 
> 因为它可以把更多 memory 置于 CPU/GPU 附近，并提供 byte-addressable/load-store 类语义。
> 
> SIGMOD 2026 的 Beluga 就利用 CXL switch memory pool 做大规模 KVCache management，并报告了相对于其 RDMA baseline 显著的 TTFT 和 throughput 改善。([arXiv](https://arxiv.org/abs/2511.20172?utm_source=chatgpt.com))
> 
> TraCT 更进一步研究：
> 
> ```text
> Prefill GPU
>      ↓
>  shared CXL memory
>      ↑
> Decode GPU
> ```
> 
> 尝试去掉传统：
> 
> ```text
> Prefill → NIC → network → NIC → Decode
> ```
> 
> 这条 KV transfer path；其研究同时明确指出，non-coherent shared CXL memory 会立即带来 synchronization、consistency 和 data-management 问题。([arXiv](https://arxiv.org/abs/2512.18194?utm_source=chatgpt.com))
> 
> 所以：
> 
> > **CXL 消灭的是某些 copy/network hop，而不是 KVC management。**
> 
> 甚至恰恰相反：
> 
> CXL 越强，软件越需要解决：
> 
> - ownership；
> - coherence domain；
> - visibility；
> - synchronization；
> - placement；
> - page allocation；
> - congestion；
> - tenant isolation。
> 
> 也就是说：
> 
> > **memory disaggregation 会减少数据面的某些操作，却增加控制面的复杂度。**
> 
> 这实际上进一步强化了 HOST system software 的重要性。
>

> # 十三、第四项核心竞争力：QoS 与多租户隔离
> 
> KVC 是一个非常特殊的数据对象。
> 
> 它不是模型参数。
> 
> 它包含由用户 prompt、conversation history、企业数据等生成的中间状态。
> 
> 因此 cloud KVC pool 必须至少回答：
> 
> ```text
> Tenant A 能否看到 Tenant B 的 KV？
> ```
> 
> 以及：
> 
> ```text
> Tenant A 能否把 Tenant B 的 memory bandwidth 打满？
> ```
> 
> 这对应两类隔离。
> 
> ### Security isolation
> 
> 需要：
> 
> - IOMMU；
> - PASID/SR-IOV；
> - memory protection；
> - confidential I/O；
> - DPU security domain。
> 
> ### Performance isolation
> 
> 需要：
> 
> - memory bandwidth QoS；
> - NIC queue QoS；
> - PCIe/CXL contention control；
> - cache partition；
> - admission control。
> 
> 例如 NVIDIA Grace 支持 Arm MPAM，可用于监控/分配 cache 和 memory-bandwidth 类资源。([NVIDIA Docs](https://docs.nvidia.com/dccpu/grace-perf-tuning-guide/index.html?utm_source=chatgpt.com))
> 
> Intel IPU、NVIDIA BlueField、AMD Pensando DPU 这一类 infrastructure processor 的真正价值，也不只是“减少 CPU 使用率”，而在于把：
> 
> ```text
> tenant data plane
> ```
> 
> 和：
> 
> ```text
> cloud provider control plane
> ```
> 
> 分离。
> 
> BlueField-3 明确支持 networking、storage、security 和 management 的隔离/offload；AMD Pensando Salina 则提供 400G programmable dataplane，并支持 SR-IOV、QoS、storage virtualization 等能力。([NVIDIA Networking](https://networking-docs.nvidia.com/bf3dpu/introduction?utm_source=chatgpt.com))
>

> # 十四、第五项核心竞争力：P99 而不是峰值 GB/s
> 
> KVC Data Plane 最危险的指标是：
> 
> > “我们的 RDMA 已经跑到 200 GB/s。”
> 
> 这仍然不能证明 serving 快。
> 
> 真正应该测：
> 
> $$
> T_{KV-ready}
> =
> T_{lookup}
> +
> T_{queue}
> +
> T_{submit}
> +
> T_{transfer}
> +
> T_{completion}
> +
> T_{visibility}
> $$
> 
> 以及：
> 
> $$
> TTFT_{P99}
> $$
> 
> 而不是单独：
> 
> $$
> BW_{network}
> $$
> 
> 尤其是高 QPS 下。
> 
> 因为：
> 
> ```text
> NIC bandwidth
> DDR bandwidth
> PCIe bandwidth
> HBM capacity
> metadata QPS
> MR cache
> completion processing
> GPU scheduler
> ```
> 
> 是一个 closed queueing system。
> 
> 任意一个环节进入 saturation region：
> 
> $$
> \rho \rightarrow 1
> $$
> 
> 其等待时间就会非线性上升。
> 
> 所以未来衡量 HOST KVC 能力的 KPI 应该是：
> 
> | 层级 | 真正应测指标 |
> |---|---|
> | Control Plane | prefix lookup P99 |
> | Control Plane | placement decision P99 |
> | Control Plane | publish visibility latency |
> | Transfer | block-ready → GPU-visible latency |
> | Transfer | useful payload bandwidth |
> | HOST | CPU cycles / GB KV |
> | Memory | DDR/CXL BW utilization |
> | Topology | cross-NUMA traffic ratio |
> | NIC | queue depth / CQ latency |
> | GPU | KVC starvation time |
> | Serving | TTFT P50/P99 |
> | Serving | TPOT P99 |
> | Serving | SLO goodput |
> | Capacity | max concurrent sessions |
> | Economics | useful tokens / GPU-hour |
> 
> 最终最值得定义一个：
> 
> $$
> AmplificationFactor
> =
> \frac{\Delta EndToEndMetric}
> {\Delta HostStageLatency}
> $$
> 
> 寻找哪些 HOST 微观优化存在：
> 
> $$
> AmplificationFactor \gg 1
> $$
> 
> 这比单纯追求某一个函数减少 30% latency 有意义得多。
>

> # 十五、必须主动反驳几个非常危险的“HOST 价值论”
> 
> ## 质疑一：GPU 已经可以直接操作 NIC，CPU 会不会被淘汰？
> 
> 不会，但 CPU 的位置会发生变化。
> 
> GPUNetIO 已证明 CPU 完全可以退出高频 packet datapath。([NVIDIA Networking](https://networking-docs.nvidia.com/doca/archive/2-9-0/doca-gpunetio?utm_source=chatgpt.com))
> 
> 因此正确方向就是：
> 
> > **把 CPU 从 packet-by-packet / block-by-block fast path 移走。**
> 
> 但仍然存在：
> 
> - memory allocation；
> - protection；
> - queue setup；
> - MR lifecycle；
> - topology；
> - resource arbitration；
> - placement；
> - failure recovery。
> 
> 因此：
> 
> **GPU 赢得 execution authority；HOST 保留 resource authority。**
> 
> ---
> 
> ## 质疑二：DPU 可以把这些事都做掉，还需要 CPU 吗？
> 
> DPU 可以承担大量 dataplane/control-offload。
> 
> 而且这是正确方向。
> 
> 但这并不削弱“HOST”，只是意味着：
> 
> > **HOST control domain 从 CPU-centric 演化成 CPU+DPU cooperative。**
> 
> 真正错误的是把 HOST 等同于 x86 core。
> 
> 未来的 HOST 很可能是：
> 
> ```text
> CPU
>  +
> DPU
>  +
> memory fabric
>  +
> CXL
>  +
> programmable NIC
> ```
> 
> 共同构成。
> 
> ---
> 
> ## 质疑三：网络升级到 800G，不就解决 KV transfer 了吗？
> 
> 不一定。
> 
> Strata 已经展示，碎片化小 I/O 可以让高物理带宽严重低利用；DualPath 展示的又是 NIC 资源分布不均，而不是纯链路速度不足。([USENIX](https://www.usenix.org/conference/osdi26/presentation/xie-zhiqiang?utm_source=chatgpt.com))
> 
> 链路越快，瓶颈甚至可能进一步转移到：
> 
> ```text
> PCIe
> DDR
> Root Complex
> CQ processing
> memory registration
> ```
> 
> 所以：
> 
> > **更快的 NIC 只能移动 bottleneck，不能自动消灭 bottleneck。**
> 
> ---
> 
> ## 质疑四：KVCache 可以重算，所以为什么需要复杂存储系统？
> 
> 正因为可以重算，KVC 才特别适合做 aggressive tiering。
> 
> 其优化本质是比较：
> 
> $$
> Cost_{reuse}
> <
> Cost_{recompute}
> $$
> 
> 则保留。
> 
> 否则：
> 
> $$
> evict
> $$
> 
> 因此 KVC 的核心不是 durability。
> 
> 而是：
> 
> > **recomputation economics。**
> 
> 它是“可丢失但重建昂贵的派生状态”。
> 
> 这一点与传统数据库完全不同。
> 
> ---
> 
> ## 质疑五：未来 sparse attention / KV compression 把 KVC 做小之后，这个问题会消失吗？
> 
> 不会消失，只会改变 threshold。
> 
> 即使每 token KV 缩小：
> 
> $$
> S_{KV}\downarrow
> $$
> 
> Agent 数量、context 长度和并发 session：
> 
> $$
> N_{agent}\uparrow,\quad
> L_{context}\uparrow,\quad
> N_{session}\uparrow
> $$
> 
> 仍会迅速吃掉收益。
> 
> 更重要的是 sparse attention 甚至可能使访问粒度进一步细化，从“整块搬 KV”变成：
> 
> > “从巨大远端 KV 中只获取本次 attention 真正需要的部分。”
> 
> 此时 addressability、fine-grained access、placement 和 metadata 会变得更加重要。
> 
> ---
> 
> # 十六、真正值得 CPU 厂商打造的产品，不是“KVC 加速指令”，而是 KVC-aware HOST platform

> > “新增一条 KVCache 指令。”

>

>

> KVPublish()

> CXL switch 2

> here
> before this deadline

> 
> 然后 HOST runtime 将 **Intent → Physical Execution Plan**。
> 
> 这才是软硬协同。

> # 十七、这场竞争最终比的是什么

> ```text
> SPEC CPU
> cores/socket
> DDR bandwidth
> PCIe lanes

> 
> # KVC State Service Capability
>

> 
> $$
> KSSC=
> f(
> metadata\ QPS,
> state\ capacity,
> state\ BW,
> state\ latency,
> isolation,
> tail\ latency,
> CPU\ cost

>

>

> 
> # 十八、最终收敛：HOST 在 Agentic AI 中真正“独一无二”的价值
> 
> 不是：
> 
> > CPU 比 GPU 更适合 AI。
> 
> 不是。
> 
> 也不是：
> 
> > CPU 替 GPU 做 KV copy。
> 
> 更不是。
> 
> 真正不可替代的是：
> 
> ### 1. GPU 擅长计算，HOST 决定计算所需状态在哪里。
> 
> ### 2. GPU 拥有 HBM，HOST 掌握跨 DDR/CXL/SSD/Network 的容量层次。
> 
> ### 3. GPU 可以直接驱动数据面，但 HOST 建立并治理 address、protection、topology 和 resource domain。
> 
> ### 4. Agentic workload 把计算变成大量短 burst，把 KVC 变成长生命周期状态；HOST 决定这些状态何时升降级。
> 
> ### 5. Multi-agent 又进一步把 KVC 从“memory block”变成带 sharing、branch、version、replica、lease 的 distributed object。
> 
> 所以整个体系最终会从：

> ```text

> 因此每一次 KV intent 必须携带：
> 
> $$
> Epoch
> $$
> 
> 例如：
> 
> ```text
> request R
> epoch 103
> ```
> 
> HOST 完成 KV 后返回：
> 
> ```text
> READY
> R
> epoch 103
> ```
> 
> 但是此时 GPU 已经进入：
> 
> ```text
> epoch 104
> ```
> 
> 那么：
> 
> $$
> 103 \neq 104
> $$
> 
> 直接丢弃结果。
> 
> 不能进入 active KV mapping。
> 
> 再配合：
> 
> $$
> Lease
> $$
> 
> 定义：
> 
> ```text
> who owns block
> until when
> whether movable
> whether evictable
> whether sharable
> ```
> 
> 整个状态转换就可以从传统的：
> 
> ```text
> HOST says ready
> ```
> 
> 提升成：
> 
> ```text
> GPU-authorized
> versioned
> lease-protected
> state transition
> ```
> 
> 这才足够支撑真正异步、高并发 Agent serving。
>

> # 十一、所以 CPU 真正不应该做的事情已经非常清楚
> 
> CPU 不应该：
> 
> ```text
> per-block memcpy
> ```
> 
> 不应该：
> 
> ```text
> per-packet forwarding
> ```
> 
> 不应该：
> 
> ```text
> 每次 RDMA doorbell 都参与
> ```
> 
> 不应该：
> 
> ```text
> 决定 GPU batch
> ```
> 
> 不应该：
> 
> ```text
> 自行管理 HBM
> ```
> 
> 更不应该：
> 
> ```text
> 和 GPU scheduler 做第二套 placement policy
> ```
> 
> NVIDIA 自己的 GPUNetIO 架构其实已经很好地说明了正确趋势：
> 
> ```text
> Configuration Phase → CPU
> 
> Data Path Phase → GPU/NIC
> ```
> 
> CPU 建立 object、queue、memory 等资源，随后 GPU 可以直接执行高速数据面。([NVIDIA Networking](https://networking-docs.nvidia.com/doca/archive/3-5-0/gpunetio-architecture-and-design?utm_source=chatgpt.com))
> 
> 这不是 CPU 失败。
> 
> 这是正确的 heterogeneous architecture。
>

> # 十二、那么 CPU 剩下什么？——第一项真实价值：它是“资源稀缺性的求解器”
> 
> GPU scheduler 优化的是：
> 
> $$
> GPU\ execution
> $$
> 
> HOST scheduler 优化的是：
> 
> $$
> whole-system\ resource
> $$
> 
> 二者优化空间不同。
> 
> 例如 8 个 GPU 同时说：
> 
> ```text
> 我要 KV-A
> 我要 KV-B
> 我要 KV-C
> ...
> ```
> 
> 每个 GPU 的请求独立看都合理。
> 
> 但是物理系统只有：
> 
> ```text
> 2 × NIC
> 1 × PCIe switch
> 8 × DDR channels
> finite SSD BW
> finite CXL BW
> ```
> 
> 于是：
> 
> $$
> \sum Demand > Supply
> $$
> 
> 此时必须有人回答：
> 
> $$
> Who\ gets\ bandwidth?
> $$
> 
> $$
> Which\ request\ waits?
> $$
> 
> $$
> Which\ KV\ recomputes?
> $$
> 
> $$
> Which\ source\ replica\ serves?
> $$
> 
> 单 GPU scheduler 无法天然解决跨 GPU 的 global contention。
> 
> CPU/DPU/HOST resource manager 的价值就在这里。
> 
> ---
> 
> # 十三、CPU 的第二项价值：管理“GPU 不愿意拥有”的大状态空间
> 
> KVC 的物理状态空间远大于：
> 
> ```text
> current HBM KV table
> ```
> 
> 它可能是：
> 
> ```text
> GPU HBM
>     ↓
> Host DDR
>     ↓
> CXL
>     ↓
> SSD
>     ↓
> Remote DRAM
>     ↓
> Remote SSD
> ```
> 
> Mooncake 的实际生产架构已经把 CPU、DRAM、SSD 和 NIC 组织成 distributed KVC，而不仅仅依赖 GPU HBM。([USENIX](https://www.usenix.org/conference/fast25/presentation/qin?utm_source=chatgpt.com))
> 
> 一旦规模达到：
> 
> ```text
> TB
> PB
> millions of blocks
> thousands of sessions
> ```
> 
> 就出现大量并不适合占用 GPU execution resource 的工作：
> 
> ```text
> directory
> reference
> TTL
> garbage collection
> replication
> health
> quota
> tenant accounting
> cold placement
> failure recovery
> ```
> 
> 理论上这些都可以写 CUDA kernel。
> 
> 问题不是“能不能”。
> 
> 问题是：
> 
> > **为什么要消耗昂贵 GPU execution capacity 去做这些并不需要高吞吐 tensor arithmetic 的后台工作？**
> 
> GPU 是整个数据中心最昂贵的 resource。
> 
> 因此一个合理原则是：
> 
> $$
> GPU\ time
> \rightarrow
> model\ execution
> $$
> 
> 而不是：
> 
> $$
> GPU\ time
> \rightarrow
> distributed\ storage\ bookkeeping
> $$
> 
> CPU 在这里的价值不是比 GPU 强。
> 
> 恰恰是：
> 
> > **CPU 足够便宜、足够通用，所以把 GPU 从低价值控制工作中解放出来。**
> 
> ---

> # 十四、CPU 的第三项价值：处理不可预测的 slow path
> 
> Fast path 可以高度 GPU 化。
> 
> 例如：
> 
> ```text
> known KV
> known source
> registered memory
> healthy NIC
> normal path
> ```
> 
> 完全可以：
> 
> ```text
> GPU → NIC
> ```
> 
> 甚至 GPU 自己 poll CQ。
> 
> 但是生产系统永远存在：
> 
> ```text
> MR miss
> page fault
> source failure
> NIC error
> timeout
> CXL poison
> SSD error
> replica stale
> permission failure
> tenant quota
> path failover
> ```
> 
> 这些是：
> 
> > **exception-heavy / branch-heavy / control-intensive workload。**
> 
> 也正是 CPU 最适合承担的部分。
> 
> 因此未来合理结构不是：
> 
> ```text
> CPU controls everything
> ```
> 
> 而是经典系统架构：
> 
> ```text
> GPU fast path
>    │
>    └── exception
>           ↓
>       CPU/DPU slow path
> ```
> 
> 这和现代 NIC、storage controller、OS 的演进完全一致。
> 
> ---
> 
> # 十五、CPU 的第四项价值：它掌握的是系统“可治理性”，不是 KV timing
> 
> 云厂商面对的不只是一个模型。
> 
> 而是：
> 
> ```text
> Tenant A
> Tenant B
> Tenant C
> ```
> 
> 同时访问：
> 
> ```text
> HBM
> DDR
> CXL
> SSD
> NIC
> ```
> 
> 如果完全让各 GPU 自主发流量：
> 
> 每个 GPU 都会从自己的局部视角优化：
> 
> $$
> min(TTFT_i)
> $$
> 
> 但整个云系统需要优化：
> 
> $$
> max(SLO\ goodput)
> $$
> 
> 并满足：
> 
> $$
> TenantIsolation
> $$
> 
> 这两个目标完全不同。
> 
> HOST/DPU 必须控制：
> 
> ```text
> memory quota
> bandwidth credit
> RDMA QP
> IOMMU mapping
> PASID
> NIC QoS
> CXL capacity
> SSD IOPS
> ```
> 
> GPU 可以拥有 **request priority**。
> 
> 但不能天然拥有：
> 
> > **整个 cloud resource policy。**
> 
> 否则某一个 latency-sensitive tenant 就可以把 memory/network bandwidth 吃完。
> 
> ---

> # 十六、最关键的重新定位：CPU 不再是 KVC “Owner”，而是 KVC State Fabric Controller
> 
> 所以我会彻底修改上一轮里容易产生争议的表述。
> 
> 不能说：
> 
> > CPU 是 KVC controller。
> 
> 更准确的是：
> 
> # Accelerator = KVC Semantic Owner
> 
> 它知道 KV：
> 
> ```text
> 为什么产生
> 什么时候使用
> 什么时候失效
> 属于哪个 request
> ```
> 
> # HOST = KVC Resource Controller
> 
> 它知道：
> 
> ```text
> 物理位置
> 资源压力
> 拓扑
> 带宽
> 故障
> 租户
> 成本
> ```
> 
> # NIC / DPU / DMA / CXL = KVC Data Mover
> 
> 它们执行：
> 
> ```text
> transfer
> ```
> 
> 这个三分结构非常重要。
> 
> ---

> # 十七、未来最合理的系统应该长成这样
>

>                  ┌──────────────────────┐
>                  │  GPU / NPU Runtime   │

> 这是特性，不是缺陷。

> # 十八、一个非常有意思的结果：GPU Direct 越强，HOST memory 反而可能越重要
> 
> 表面上看：
> 
> > GPU 可以绕过 CPU。
> 
> 似乎降低了 HOST 价值。
> 
> 但 DirectKV 实际揭示了另一个方向。
> 
> 当 CPU-GPU interconnect 足够快，GPU 可以直接消费 CPU-resident KV。([USENIX](https://www.usenix.org/conference/osdi26/presentation/luo?utm_source=chatgpt.com))
> 
> 于是原来：
> 
> ```text
> HBM = working memory
> DDR = offload storage
> ```
> 
> 开始演变成：
> 
> ```text
> HBM = L1 working set
> 
> DDR/CXL = L2 GPU-addressable working set
> ```
> 
> 也就是说：
> 
> > **CPU core 的数据面价值下降，不等于 HOST memory/fabric 价值下降。**
> 
> 甚至可能完全相反。
> 
> CPU 不搬数据了。
> 
> 但 CPU socket 带来的：
> 
> ```text
> memory controllers
> DDR capacity
> CXL fabric
> PCIe root complex
> address translation
> protection
> QoS
> ```
> 
> 反而越来越成为 GPU memory hierarchy 的一部分。
> 
> 这是理解未来 CPU 价值最关键的一点。
> 
> ---
> 
> # 十九、这也解释了为什么 Strata 是一个很值得重视的案例
> 
> Strata 并没有试图用 CPU 抢 GPU scheduler 权力。
> 
> 它采用：
> 
> ```text
> GPU-assisted I/O
> +
> hierarchical storage
> +
> cache-aware scheduling
> ```
> 
> 并明确指出，如果 scheduler 不知道 cache loading latency，会产生严重 performance degradation；其生产实现中 throughput 最高达到 vLLM-LMCache 的约 5×。([USENIX](https://www.usenix.org/conference/osdi26/presentation/xie-zhiqiang?utm_source=chatgpt.com))
> 
> 真正值得注意的是其中的思想：
> 
> > **数据面尽可能靠近 GPU，但资源状态必须被 scheduler 感知。**
> 
> 这就是未来正确的 GPU/HOST 协作形态。
> 
> 不是：
> 
> ```text
> GPU vs CPU
> ```
> 
> 而是：
> 
> ```text
> GPU scheduling semantics
> +
> HOST resource reality
> ```
>

> # 二十、HOST side “prediction”也不是没价值，但必须改变预测对象
> 
> HOST 不应该预测：
> 
> > “GPU 下一步一定会用 KV-X，所以我擅自放进 HBM。”
> 
> 这是越权。
> 
> HOST真正应该预测的是：
> 
> ```text
> KV-X 可能很快被使用
> ```
> 
> 然后做：
> 
> ```text
> SSD → DDR
> ```
> 
> 或者：
> 
> ```text
> remote → local CXL
> ```
> 
> 即：
> 
> # Shadow Prefetch
> 
> 把数据移动到 **accelerator 之外的近端层级**：
> 
> ```text
> Cold
>  ↓
> Warm
> ```
> 
> 但是不进入：
> 
> ```text
> HBM Hot Working Set
> ```
> 
> 最终：
> 
> ```text
> Warm → HBM
> ```
> 
> 依然必须由 GPU-issued credit 触发。
> 
> 这样即使预测错：
> 
> 损失的是：
> 
> ```text
> DDR/CXL capacity
> +
> background BW
> ```
> 
> 而不是：
> 
> ```text
> precious HBM
> +
> GPU scheduler stability
> ```
> 
> 这是很重要的 policy separation。
> 
> ---
> 
> # 二十一、Agentic AI 正好强化了这种“Shadow Prefetch”的意义
> 
> Agent workflow：
> 
> ```text
> LLM
>  ↓
> tool call
>  ↓
> Python / Browser / DB
>  ↓
> LLM
> ```
> 
> Tool execution 本身天然提供了一个：
> 
> $$
> Think\ Time
> $$
> 
> 如果系统知道某个 agent 最终有较高概率返回同一个 model：
> 
> HOST 可以提前：
> 
> ```text
> remote SSD
>      ↓
> local DDR/CXL
> ```
> 
> 但是暂时不：
> 
> ```text
> DDR → HBM
> ```
> 
> 等 agent 真正结束 tool call，GPU runtime 创建下一轮 request：
> 
> ```text
> issue HBM credit
> ```
> 
> 然后执行最后一级：
> 
> ```text
> DDR/CXL → HBM
> ```
> 
> 这既利用 Agentic workload 的时间结构，又避免 HOST 干扰 GPU。
> 
> 这比笼统说“CPU 做 KV prefetch”准确得多。
>

> # 二十二、什么时候 CPU 对 KVC 真的几乎没有价值？
> 
> 这个问题必须正面回答，否则所有论述都会变成 CPU 厂商营销。
> 
> 存在非常明确的区域：
> 
> $$
> KVC \subseteq HBM
> $$
> 
> 同时：
> 
> ```text
> single accelerator domain
> no external reuse
> no multi-tenant sharing
> low concurrency
> no storage tier
> no remote cache
> ```
> 
> 那么最优系统很可能就是：
> 
> ```text
> GPU-local KV
> ```
> 
> CPU：
> 
> > **最好什么都不要做。**
> 
> 另一种情况：
> 
> ```text
> large NVLink domain
> +
> GPU-to-GPU sharing
> +
> sufficient HBM
> ```
> 
> GPU peer memory 已经解决问题。
> 
> CPU 价值依然很小。
> 
> 再一种：
> 
> $$
> T_{recompute}<T_{fetch}
> $$
> 
> 那直接 recompute。
> 
> 此时：
> 
> > 不应该为了证明 HOST 有价值而强行保存 KV。
> 
> 这是非常重要的边界。
> 
> ---
> 
> # 二十三、HOST 价值在什么时候急剧出现？
> 
> 当系统跨过以下边界时：
> 
> $$
> KVC_{working-set} > HBM
> $$
> 
> 或者：
> 
> $$
> KVC_{global-state} \gg HBM
> $$
> 
> 并同时出现：
> 
> ```text
> many GPUs
> many sessions
> multi-turn
> multi-agent
> external storage
> multi-tenancy
> PD disaggregation
> remote reuse
> ```
> 
> 此时问题从：
> 
> ```text
> GPU memory management
> ```
> 
> 变成：
> 
> ```text
> distributed state management
> ```
> 
> CPU/HOST 才开始获得真正系统级价值。
> 
> 这也是为什么 Mooncake 在大规模部署中把 CPU/DRAM/SSD/NIC 组合起来，而不是把所有状态问题继续压给 GPU。([USENIX](https://www.usenix.org/conference/fast25/technical-sessions?utm_source=chatgpt.com))
> 
> ---
> 
> # 二十四、因此 CPU 厂商真正应该卖什么？
> 
> 不是：
> 
> > “我们 CPU 很快，所以帮你搬 KV。”
> 
> 这种论点迟早被 GPUDirect 打穿。
> 
> 也不是：
> 
> > “我们帮 GPU 决定 KV placement。”
> 
> GPU scheduler 会拒绝这种越权。
> 
> 真正可以建立的价值主张是：
> 
> # 我提供最好的 Accelerator State Fabric
> 
> 即：
> 
> > **让 GPU 用最少的自身资源和最少的等待时间，访问远大于 HBM 的可共享状态空间。**
> 
> 这里的 CPU/Host 核心竞争力变成：
> 
> | 传统 CPU 指标 | AI HOST 新竞争指标 |
> |---|---|
> | Core count | 可管理 accelerator 数 |
> | SPECint | control-plane QPS |
> | DRAM capacity | warm KVC capacity |
> | DRAM BW | GPU-accessible state BW |
> | PCIe lanes | accelerator/NIC concurrency |
> | CXL | shared state addressability |
> | IOMMU | accelerator isolation |
> | DSA/DMA | CPU-free movement |
> | LLC | metadata/control working set |
> | NUMA | state locality |
> | RAS | KVC failure containment |
> 
> 这才是 AMD / Intel / NVIDIA CPU 真正值得竞争的方向。
> 
> ---
> 
> # 二十五、最终应该用什么 KPI 衡量 HOST 是否真的有价值？
> 
> 不是：
> 
> $$
> CPU\ Utilization
> $$
> 
> 也不是：
> 
> $$
> memcpy\ GB/s
> $$
> 
> 而应该是：
> 
> $$
> Accelerator\ Stall\ Time
> $$
> 
> 即：
> 
> > GPU 因为等待 KVC 而损失了多少执行时间。
> 
> 因此可以定义：
> 
> $$
> StateSupplyLatency
> =
> T_{intent}
> \rightarrow
> T_{GPU-visible}
> $$
> 
> 同时统计：
> 
> $$
> P50,\ P99
> $$
> 
> 再定义：
> 
> $$
> GPU\ State\ Stall\ Ratio
> =
> \frac
> {Time_{GPU\ waiting\ for\ state}}
> {GPU\ serving\ time}
> $$
> 
> 进一步定义：
> 
> $$
> HOST\ Efficiency
> =
> \frac
> {GPU\ State\ Stall\ Eliminated}
> {CPU\ Core + Memory + Fabric\ Cost}
> $$
> 
> 这比：
> 
> > CPU 参与了多少 KV 流程
> 
> 重要得多。
> 
> 理想状态甚至应该是：
> 
> $$
> CPU\ FastPath\ Participation
> \rightarrow 0
> $$
> 
> 同时：
> 
> $$
> GPU\ State\ Stall
> \rightarrow 0
> $$
> 
> 如果能够做到这一点：
> 
> > **CPU 存在感越低，HOST 架构反而可能越优秀。**
> 
> 这是这次红蓝对抗后非常重要的反直觉结论。
> 
> ---
> 
> # 二十六、因此我会把 HOST 的价值主张最终收敛成一句非常严格的话
> 
> 不是：
> 
> > HOST 管理 KVCache。
> 
> 而是：
> 
> > **GPU/NPU 管理 KVC 的语义和消费时序；HOST 管理支撑这些语义所需要的物理状态空间与资源供给。**
> 
> GPU 决定：
> 
> $$
> WHAT
> $$
> 
> 和：
> 
> $$
> WHEN
> $$
> 
> HOST 决定：
> 
> $$
> WHERE
> $$
> 
> 和：
> 
> $$
> HOW
> $$
> 
> 更精确地说：
> 
> ```text
> GPU/NPU:
> “What state do I require,
> and by what deadline?”
> 
> HOST:
> “Where can that state come from,
> what will it cost,
> and how can I satisfy the deadline
> without destabilizing the rest of the system?”
> ```
> 
> ---
>

> # 九、第二类更强的价值：HOST 改变的是容量边界，而不是几百微秒
> 
> 这个价值甚至比 latency optimization 更扎实。
> 
> 考虑一块 GPU：
> 
> [\
> HBM=H\
> ]
> 
> 每个 active session 平均需要：
> 
> [\
> K\
> ]
> 
> 理论 session 数受到：
> 
> [\
> N\_{session}\leq\frac{H-H\_{weights}-H\_{workspace}}{K}\
> ]
> 
> 限制。
> 
> 如果 HOST DDR/CXL 允许 inactive / warm KVC 离开 HBM：
> 
> GPU HBM 不再需要承载：
> 
> [\
> KVC\_{all\ live\ sessions}\
> ]
> 
> 而只需要承载：
> 
> [\
> KVC\_{currently\ executable\ working-set}\
> ]
> 
> 这是一个完全不同性质的变化。
> 
> 它不是：
> 
> [\
> TTFT - 500\mu s\
> ]
> 
> 而是：
> 
> [\
> Concurrency\
> :\
> N\
> \rightarrow\
> M\times N\
> ]
> 
> 或者：
> 
> [\
> GPU\ count\
> :\
> G\
> \rightarrow\
> G-k\
> ]
> 
> 这类能力非常容易转化成客户价值。
> 
> 最近那篇 placement 研究虽然对复杂 policy 很悲观，却恰恰发现，在其模型中 tier capacity 能支持约 73× 更多 concurrent sessions、并显著降低 per-session cost；作者同时明确指出主要收益来自 tier capacity，而非复杂 placement policy。因为这是 simulator 研究，这些绝对数字不能直接当产品承诺，但它对“容量价值 > policy sophistication”的方向性结论很有意义。
> 
> 这个结果其实对 CPU 厂商非常重要：
> 
> > **也许我们不应该卖“聪明的 KVC scheduler”，而应该卖“GPU 可以高效访问的大容量二级状态空间”。**
> 
> 这是完全不同的产品定位。
>

> # 十、DirectKV 给了一个非常漂亮的证据：CPU memory 有价值，不代表 CPU execution 有同样大的价值
> 
> DirectKV 在 GH200 上利用 NVLink-C2C，让 GPU kernel 可以直接访问 CPU-resident KV。
> 
> 结果是：
> 
> [\
> GPU\ memory\ use\
> \downarrow 43%\
> ]
> 
> CPU-GPU transfer volume 最多降低 50%，但端到端性能最高约：
> 
> [\
> 1.2\times\
> ]
> 
> 。
> 
> 这组数字特别值得 CPU 产品经理看。
> 
> 因为它说明两件完全不同的事情。
> 
> 第一：
> 
> > **HOST memory capacity 的价值可能很大。**
> 
> 43% GPU memory reduction 能直接改变可运行 workload 或 concurrency。
> 
> 第二：
> 
> > **不能因为 memory footprint 大幅降低，就把同等数量级的“性能价值”归给 CPU。**
> 
> 性能只有最高约 1.2×。
> 
> 所以产品定义必须拆成：
> 
> [\
> Capacity\ Value\
> ]
> 
> 和：
> 
> [\
> Performance\ Value\
> ]
> 
> 这是过去 HOST 宣传里经常混淆的两个维度。

> # 十三、DualPath 提供的是另一种“放大效应”：资源失衡

> 
> ```text

>

> 
> > 单个操作快 10%。
> 
> 而是：
> 
> > **把原本不可用的闲置物理资源变成系统有效容量。**
>

> 
> [\
> Resource\ Harvesting\
> ]
> 
> 价值。
> 
> 但是还要再次强调：
> 
> > 这是 HOST/Fabric 价值，不自动等于 CPU core 价值。
> 
> 如果 GPU/DPU 完全可以执行 datapath：
> 
> 就应该让它们执行。
> 
> CPU 可以只负责慢速 global resource model。

> # 二十二、于是 HOST 真正值得争夺的，不是“工作量”，而是三个杠杆点
> 
> 经过前三轮对抗，我现在只保留三个我认为真正有资格成为 HOST 核心产品价值的方向。
> 
> ### 第一：Capacity Leverage
> 
> 把 accelerator 可使用的 state space 从：
> 
> [\
> HBM\
> ]
> 
> 扩展成：
> 
> [\
> HBM+DDR+CXL+SSD+Remote\
> ]
>

> 
> 它改变的是：
> 
> [\
> max\ concurrent\ sessions\
> ]
> 
> 和：
> 
> [\
> GPU/HBM\ cost\
> ]
> 
> 不是微秒级延迟。
> 
> Mooncake、DirectKV 以及各种 hierarchical cache 工作都支持这一方向。
> 
> ### 第二：Resource Leverage
> 
> 把系统里原本闲置：
> 
> ```text
> DDR BW
> NIC BW
> SSD BW
> remote memory
> ```
> 
> 变成 accelerator 可消费资源。
> 
> DualPath 的约 1.96× online throughput 是非常典型的实证。
> 
> ### 第三：Queueing Leverage
> 
> 避免外部 KVC 把 GPU 推入：
> 
> [\
> I/O\ stall\
> ]
> 
> 或：
> 
> [\
> \rho\approx1\
> ]
> 
> 的系统饱和区。
> 
> Strata、Bidaw、SYMPHONY 都属于不同形式的这一类：它们分别报告了最高约 5× throughput、1.83× throughput/3.58× latency improvement，以及 2.4× end-to-end latency reduction和服务约 4× 更多请求的实验结果。
> 
> 这三个 leverage 才值得 HOST 厂商真正投入。
>

> 但是随着：
> 
> $$
> KVC_{working-set}/HBM
> \rightarrow1
> $$
> 
> HBM eviction、admission 和 recomputation 突然增加。
> 
> 再继续增加：
> 
> $$
> KVC_{working-set}>HBM
> $$
> 
> 系统可能进入完全不同的 operating region。
> 
> 这就是 **Capacity Knee**。
> 
> 第二类是：
> 
> $$
> ExternalBandwidthDemand/AvailableBandwidth
> $$
> 
> 的带宽拐点。
> 
> 当：
> 
> $$
> \rho_{NIC/DDR/PCIe}<0.6
> $$
> 
> 某项优化可能几乎没有效果。
> 
> 但：
> 
> $$
> \rho\rightarrow0.9
> $$
> 
> 以后，P99 latency 可能迅速恶化。
> 
> 这是 **Bandwidth Knee**。
> 
> 第三类是：
> 
> $$
> ControlPlaneQPS/ServiceRate
> $$
> 
> 的控制面拐点。
> 
> 低 QPS 下：
> 
> $$
> metadata:
> 1ms\rightarrow0.7ms
> $$
> 
> 可能几乎没有业务意义。
> 
> 但是当：
> 
> $$
> \lambda\rightarrow\mu
> $$
> 
> 时，这 300 μs 可能意味着：
> 
> ```text
> metadata queue
>        ↓
> KV publish/release delay
>        ↓
> HBM residency延长
>        ↓
> HBM watermark
>        ↓
> admission blocking
>        ↓
> GPU starvation
>        ↓
> P99 / goodput cliff
> ```
> 
> 这是 **Control-Plane Knee**。
> 
> 第四类是：
> 
> $$
> FetchCost/RecomputeCost
> $$
> 
> 拐点。
> 
> 只有：
> 
> $$
> T_{fetch}<T_{recompute}
> $$
> 
> reuse 才值得进行。
> 
> 这决定了 external KVC 的经济边界。
> 
> 这四类拐点共同形成真正的：
> 
> # HOST-KVC Value Region
> 
> ---
> 
> # 八、因此下一阶段最值得画的，不是一张 architecture diagram，而是一张“HOST KVC Value Surface”
> 
> 可以把 workload 放到这样一个多维空间中：
> 
> $$
> V_{HOST}
> =
> f(
> W/H,
> R,
> C,
> F/R_c,
> B,
> T_{gap}
> )
> $$
> 
> 其中：
> 
> $$
> W/H
> =
> KVC\ WorkingSet/HBM
> $$
> 
> $$
> R
> =
> ReuseRate
> $$
> 
> $$
> C
> =
> Concurrency
> $$
> 
> $$
> F/R_c
> =
> FetchCost/RecomputeCost
> $$
> 
> $$
> B
> =
> ExternalResourcePressure
> $$
> 
> $$
> T_{gap}
> =
> Agent\ Think/Tool\ Gap
> $$
> 
> 这个空间中实际上存在几个完全不同的区域：
> 
> | Operating Region | HOST KVC 判断 | 产品策略 |
> |---|---|---|
> | Working set < HBM | HOST 价值很弱 | GPU-local |
> | Working set > HBM，但 Fetch > Recompute | external cache 不经济 | recompute / evict |
> | Working set > HBM，Fetch < Recompute，低并发 | 容量有价值，复杂控制未必有价值 | simple tier |
> | Working set > HBM，Fetch < Recompute，高并发 | HOST resource contention 开始重要 | 重点优化区域 |
> | 高 reuse + 高并发 + Agent tool gap | HOST 可同时获得容量、预取和资源调度价值 | 最强价值区域 |
> 
> 真正的研究目标就是：
> 
> > **确定这些边界究竟在哪里。**
> 
> 一旦把这张“相图”测出来，很多技术争论都会自然消失。

> # 十一、不要只找 bottleneck，要找“Amplification Chain”
> 
> 一个资源达到 100% 并不自动值得优化。
> 
> 真正值得攻克的必须是：
> 
> ```text
> HOST micro bottleneck
>         ↓
> resource pressure
>         ↓
> queue / state transition
>         ↓
> accelerator stall
>         ↓
> serving KPI
> ```
> 
> 例如：
> 
> ```text
> metadata publish P99
>         ↓
> KV lifecycle lag
>         ↓
> HBM block cannot reclaim
>         ↓
> HBM watermark rises
>         ↓
> admission blocked
>         ↓
> ready batch shrinks
>         ↓
> GPU bubble
>         ↓
> SLO goodput declines
> ```
> 
> 这才是一条完整价值链。
> 
> 因此可以正式定义：
> 
> $$
> AmplificationFactor_X
> =
> \frac
> {\%\Delta EndToEndKPI}
> {\%\Delta HostMetric_X}
> $$
> 
> 如果：
> 
> $$
> AF_X\ll1
> $$
> 
> 说明是低杠杆点。
> 
> 如果：
> 
> $$
> AF_X\approx1
> $$
> 
> 属于普通线性优化。
> 
> 真正值得投入的是：
> 
> $$
> AF_X\gg1
> $$
> 
> 尤其是存在：
> 
> $$
> AF_X
> \rightarrow
> very\ large
> $$
> 
> 的 saturation knee。
>

> # 十二、但还必须增加第二个指标：Attribution
> 
> 即使找到了放大效应，还要证明它属于 HOST。
> 
> 例如：
> 
> $$
> Throughput:
> 1000\rightarrow1600
> $$
> 
> 不能立刻说：
> 
> > HOST 带来了 60%。
> 
> 需要逐层做 counterfactual：
> 
> ```text
> GPU local only
> 
> GPU-native external KVC
> 
> HOST capacity + simple policy
> 
> HOST capacity + advanced policy
> 
> CPU datapath
> 
> CPU-free datapath
> ```
> 
> 最终回答：
> 
> $$
> \Delta KPI_{Capacity}
> $$
> 
> 是多少；
> 
> $$
> \Delta KPI_{Scheduling}
> $$
> 
> 是多少；
> 
> $$
> \Delta KPI_{CPU}
> $$
> 
> 是多少；
> 
> $$
> \Delta KPI_{NIC/DPU}
> $$
> 
> 是多少。
> 
> 这种 attribution discipline 非常重要。
> 
> Strata 就提供了一个典型例子：它同时使用 hierarchical caching、GPU-assisted I/O 和 cache-aware scheduling，最终在 production SGLang 上最高达到相对 vLLM-LMCache 约 5× throughput；这个结果证明系统问题很大，但任何单项 CPU feature 都不能直接把整个 5× 据为己有。([USENIX](https://www.usenix.org/conference/osdi26/presentation/xie-zhiqiang?utm_source=chatgpt.com))
> 
> ---

> # 十三、研究终点也不应该是“找到一个优化”，而应该继续下钻到 silicon opportunity
> 
> 这是你现在提出“软硬协同 → 产品竞争力”最应该补上的最后一环。
> 
> 真正的方法应该是：
> 
> $$
> Workload
> $$
> 
> ↓
> 
> $$
> System\ Knee
> $$
> 
> ↓
> 
> $$
> Root\ Physical\ Resource
> $$
> 
> ↓
> 
> $$
> Software\ Mechanism
> $$
> 
> ↓
> 
> $$
> Hardware\ Primitive
> $$
> 
> ↓
> 
> $$
> Product\ Differentiation
> $$
> 
> 例如最终可能得到这样的映射：
> 
> | 发现的系统失效模式 | 软件层方案 | 可能的硬件支撑 | 最终产品 KPI |
> |---|---|---|---|
> | Warm-KV 受 DDR BW 限制 | NUMA-aware placement、striping、parallel fetch | 更多 memory BW / channels、CXL/C2C | State GB/s、sessions/GPU |
> | 小块 KVC 导致 I/O 利用率低 | aggregation、layout decoupling、scatter/gather | DMA / descriptor engine | useful payload BW |
> | NIC/DDR 资源不均 | topology-aware multi-path | 更多 I/O lanes、多 NIC、DPU | SLO goodput |
> | Control metadata 出现 P99 knee | batching、cache-local metadata、lock-free path | LLC、I/O cache injection、原子操作 | State-ready P99 |
> | CPU 成为 copy bottleneck | CPU bypass / asynchronous offload | DMA / DSA / GPU-direct | CPU cycles/GB |
> | CPU↔GPU tier latency过高 | zero-copy/direct access | coherent C2C | usable tier capacity |
> | 多租户资源互扰 | credit/QoS/admission | bandwidth/cache QoS、IOMMU | P99 isolation |
> 
> 这才叫真正的软硬协同。
> 
> 重点仍然不是：
> 
> > “我芯片上有什么 feature，所以我要找地方用。”
> 
> 而是：
> 
> > **系统实验已经证明这里存在一个高价值拐点，因此下一代 silicon 应该提供某种 primitive。**
> 
> ---

> # 十四、现有产业技术其实已经证明了这种“反推硬件”的方向
> 
> AMD 的 SDCI 允许支持的网络 I/O 将 packet、event 和 metadata 直接注入 CPU cache，以减少再次从 DRAM 获取数据的需求；AMD 自己也明确强调，其收益取决于应用访问模式。换句话说，SDCI 是否适合 KVC control metadata，应该由真实 cache/memory-pressure 数据证明，而不是因为 CPU 有这个 feature 就假设有效。([AMD 文档](https://docs.amd.com/r/en-US/ug1586-onload-user/SDCI?utm_source=chatgpt.com))
> 
> Intel DSA 则把大量 memory-movement 工作从 CPU core 卸载给专门的数据移动加速器。它提示另一种设计原则：如果实验发现 CPU core 花大量周期进行纯数据移动，正确方向可能不是“优化 memcpy”，而是让 core 完全退出。([Intel](https://www.intel.com/content/www/us/en/products/details/processors/xeon/features/data-streaming-accelerator.html?utm_source=chatgpt.com))
> 
> NVIDIA Grace Hopper 更进一步，用高带宽 coherent NVLink-C2C 把 CPU memory 从传统的“外部 offload storage”向 GPU 可直接访问的 secondary memory 转变；DirectKV 已经证明在这种平台上直接利用 CPU-resident KVC 可以减少 GPU memory footprint 和 CPU-GPU transfer。([NVIDIA Docs](https://docs.nvidia.com/dccpu/grace-perf-tuning-guide/index.html?utm_source=chatgpt.com))
> 
> 这三个方向虽然完全不同，却反映同一个逻辑：
> 
> > **CPU/HOST 的竞争力正在从“执行更多 AI 计算”转向“以更低成本向 accelerator 提供 memory、I/O 和 state”。**
> 
> ---
> 
> # 十五、Agentic AI 的意义，在于它扩大了这个价值区域，而不是天然证明 HOST 有价值
> 
> 这一点也必须始终保持克制。
> 
> Agentic AI 的特点：
> 
> ```text
> long context
> 
> multi-turn
> 
> short append
> 
> high prefix reuse
> 
> tool-call gaps
> 
> many concurrent sessions
> 
> multi-agent branch/share
> ```
> 
> 会提高：
> 
> $$
> KVC_{live-state}
> $$
> 
> 并增加：
> 
> $$
> KVC_{working-set}/HBM
> $$
> 
> 同时 tool-call gap 又提供：
> 
> $$
> prefetch\ opportunity
> $$
> 
> 所以它确实让系统更容易进入：
> 
> $$
> HOST-KVC\ Value\ Region
> $$
> 
> DualPath 就明确指出，其 production agentic workload 正越来越受到 KV storage I/O 而非计算本身的限制。([SIGCOMM 会议](https://conferences.sigcomm.org/sigcomm/2026/program/papers/?utm_source=chatgpt.com))
> 
> SYMPHONY 也从 multi-turn stateful serving 的角度证明，利用 workload structure 提前迁移 KVC、让 memory 与 compute 解耦，可以在其测试中降低 2.4× end-to-end latency，并以较小 latency 增长支撑约 4× 请求。([USENIX](https://www.usenix.org/conference/nsdi26/presentation/agarwal?utm_source=chatgpt.com))
> 
> Bidaw 则证明 interactive multi-round workload 中，HOST DRAM + SSD 本身如果组织不好甚至会让 latency 恶化到 3.8×、throughput 降低至约一半；只有 computation/storage coordination 做好之后，这些外部容量才真正转化成服务能力。([USENIX](https://www.usenix.org/conference/fast26/presentation/hu-shipeng?utm_source=chatgpt.com))
> 
> 因此正确表述应该是：
> 
> > **Agentic AI 没有自动创造 CPU 价值，但显著增加了 accelerator state working set 超出 HBM、并且历史状态仍具有高复用价值的概率，因此扩大了 HOST State Supply Plane 的潜在价值区域。**
>

> # 十六、最终产品竞争力应该如何定义

> 如果继续沿着这一指导思想往前走，我认为最终不应该给 CPU/HOST 定义：
> 
> ```text
> KV lookup latency
> KV copy bandwidth
> CPU utilization
> ```
> 
> 这些只能是工程过程指标。
> 
> 真正的产品指标应该逐渐收敛成：
> 
> $$
> \boxed{
> SLOGoodput/GPU
> }
> $$
> 
> $$
> \boxed{
> ConcurrentAgentSessions/GPU
> }
> $$
> 
> $$
> \boxed{
> GPUStateStallRatio
> }
> $$
> 
> $$
> \boxed{
> EffectiveKVCStateCapacity/GPU
> }
> $$
> 
> 以及：
> 
> $$
> \boxed{
> Cost/UsefulToken
> }
> $$
> 
> HOST 的所有内部指标最终都必须能够映射到这些 KPI。
> 
> 甚至可以定义一个更加 HOST-oriented 的指标：
> 
> $$
> StateSupplyEfficiency
> =
> \frac
> {Useful\ external\ KVC\ bytes\ delivered\ within\ deadline}
> {HOST\ watts+CPU\ cores+fabric\ cost}
> $$
> 
> 或者：
> 
> $$
> AcceleratorLeverage
> =
> \frac
> {\Delta SLOGoodput}
> {\Delta HOSTCost}

> 未来 AMD、Intel、NVIDIA 或其他 HOST 平台之间真正值得比较的，可能不是：
> 
> > 谁 CPU core 更多。
> 
> 而是：
> 
> > **在同样的 GPU/NPU、模型和 SLO 下，哪一个 HOST 能够支撑最大的 accelerator-usable state space，并以最低的 P99、最低的 CPU tax 和最低的 TCO 将它交付给 accelerator。**

> # 十八、这样一来，“软硬协同”这个词也获得了更加严格的含义
> 
> 过去的软硬协同经常意味着：
> 
> > 软件看看 CPU 有什么指令，然后找机会调用。
> 
> 这实际上只是：
> 
> $$
> Feature\ Utilization
> $$
> 
> 而不是严格意义上的软硬协同。
> 
> 真正的软硬协同应该是：
> 
> $$
> Workload\ Constraint
> \rightarrow
> System\ Bottleneck
> \rightarrow
> Hardware/Software\ Co-design
> $$
> 
> 换句话说：
> 
> > **软件负责揭示 workload 的真实压力，硬件负责改变该压力下的物理边界，两者最终必须共同改变端到端产品 KPI。**

> 如果最终：
> 
> $$
> HardwareFeature
> \rightarrow
> Microbenchmark +40\%
> $$
> 
> 但是：
> 
> $$
> SLOGoodput +0.5\%
> $$
>

> 
> 而如果：
> 
> $$

> \rightarrow
> HOSTResourceKnee\ 被推迟
> $$
> 
> 进一步导致：
> 
> $$
> MaxQPS +30\%
> $$
> 
> 或者：
> 
> $$
> ConcurrentAgents/GPU +50\%
> $$
> 
> 这才是真正有价值的 silicon/software co-design。

> # 十九、所以我们当前真正要回答的已经不是“HOST 能做什么”
> 
> 而是三个更加严格的问题：
> 
> **第一，哪些 Agentic workload 会把 accelerator 推入外部 KVC 依赖区？**
> 
> 这是场景边界。
> 
> **第二，在这个区域中，哪个 HOST resource 首先出现 knee，并通过什么因果链影响 GPU 与 serving KPI？**
> 
> 这是价值发现。
> 
> **第三，把这个 knee 向右移动，需要什么 software mechanism 和 hardware primitive，而且它是否具有足够普适性，值得进入产品？**
> 
> 这是产品竞争力。
> 
> 只要这三个问题形成证据闭环，就从：
> 
> > “我们做了一个 KVC 优化”
> 
> 真正升级成：
>

因此 testbed **绝不能用 `tokens × layers × heads` 推算实际外部 KVC bytes**；必须从 connector/worker 的真实 `num_bytes`、cache-group/block 事件采集实际数据量，否则 Value Surface 的 `P_HBM`、fetch cost 和带宽利用率都会算错。

这一步我建议直接把 **HOST-KVC Value Surface 的第一阶段实现**落成一个“可重复实验平台规范”，而不是先写若干零散脚本。下面这份细则的目标是：后续 agent 按文档生成代码后，在实验机上原则上只需要修改一个 `testbed.yaml`，执行一条命令，即完成 **环境检查 → trace 准备 → 加盐/变形 → cache 准备 → 控制点注入 → 压测 → 多层指标采集 → 数据校验 → Value Surface/报告生成**。

还有两个当前平台事实会直接影响实现。Qwen3.8-27B 在 vLLM-Ascend 中从 0.23.0 开始支持，A3 也是官方支持平台；截至 2026-10 当前文档已经进入更新的 release line，因此 testbed 不应写死版本，而应启动时自动 fingerprint。([vLLM](https://docs.vllm.ai/projects/ascend/en/latest/tutorials/models/Qwen3.8-27B.html?utm_source=chatgpt.com)) vLLM-Ascend 当前 KV Pool 通过 `AscendStoreConnector` 对接 Mooncake；A3 还支持 Store/PD 流量分离、QoS 等配置。([vLLM](https://docs.vllm.ai/projects/ascend/zh-cn/latest/user_guide/feature_guide/kv_cache_pool_ascend_store.html?utm_source=chatgpt.com))

> # 2. 一个非常关键的 Qwen3.8 特殊处理
> 
> Qwen3.8-27B 不能按照传统全 Attention 模型简单处理。
> 
> 当前 vLLM-Ascend 文档描述其 64 层中：
> 
> $$
> 16
> $$
> 
> 层为 full attention，而其余：
> 
> $$
> 48
> $$
> 
> 层使用 Gated DeltaNet recurrent state。([vLLM](https://docs.vllm.ai/projects/ascend/en/latest/tutorials/models/Qwen3.8-27B.html?utm_source=chatgpt.com))
> 
> Ascend 对这类 hybrid cache 又存在 cache group、非连续 physical allocation、stride/padding 等问题。调度层使用 logical block ID，但实际物理 byte layout 可能明显不同。([vLLM](https://docs.vllm.ai/projects/ascend/en/main/developer_guide/Design_Documents/non_contiguous_kv_cache.html?utm_source=chatgpt.com))
> 
> 所以 Testbed 禁止使用：
> 
> $$
> KVBytes
> =
> TokenCount\times FixedBytesPerToken
> $$
> 
> 作为最终测量结果。
> 
> 必须同时记录：
> 
> ```text
> logical_tokens
> logical_blocks
> cache_group
> physical_blocks
> actual_transfer_bytes
> actual_store_bytes
> ```
> 
> 最终 Value Surface 中：
> 
> $$
> P_{HBM}
> $$
> 
> 和：
> 
> $$
> T_{fetch}
> $$
> 
> 都必须使用实际物理 byte 数据。
>
