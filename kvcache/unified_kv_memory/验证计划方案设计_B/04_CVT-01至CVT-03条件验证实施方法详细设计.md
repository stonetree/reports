# CVT-01 至 CVT-03 条件验证实施方法详细设计

## 1. 条件项统一启动规则

CVT 不进入 4～5 周默认资源基线。每项只有同时满足以下条件才启动：

1. 前序 PVT 的真实证据显示相关场景达到可观测规模；
2. 目标平台具有可测试的硬件/驱动/固件能力；
3. 结论会改变默认架构、硬件采购、首发范围或专项人力；
4. 软件基线和默认回退已实现，可以优先证伪硬件“必需性”；
5. 技术负责人、性能负责人和项目负责人批准独立 ExperimentManifest。

未触发不等于失败，状态记录为 `NOT_TRIGGERED`；硬件不存在为 `NOT_SUPPORTED`；测试后无稳定增量为 `NO-GO` 并关闭 feature flag。

## CVT-01：软件 Fanout Staging 与硬件 Multicast 证伪

### 1. 决策与触发门

验证 1→N 热点前缀分发时，硬件 Multicast 是否相对 N 次独立拉取和软件 Node-level Staging 有稳定净收益。默认假设是软件 Fanout 足够，硬件多播不是 PVT 主链前置。

正式关联：IR-01-04、01-10；SR23-01-04-02、01-10-01；SRS `L4-RDMA-MUL-FABRIC-002`。

建议触发证据（需在项目评审中冻结，不替代 V1.6）：PVT-00/07 表明同一安全域内热点对象经常被 ≥2 个目标并发请求，且独立拉取造成的重复远端字节或源端带宽已成为 TTFT/容量瓶颈；同时目标硬件提供可测 Multicast。

### 2. 三组方案

| 方案 | 数据流 | 默认地位 |
|---|---|---|
| Independent Pull | 每个 Consumer 独立从 Source 拉取 | 功能基线 |
| Software Staging Fanout | 一个拉取者或节点级 UBMEM/Registered Pool 获取一次，再向本地/下游扇出 | 默认候选 |
| Hardware Multicast | Source/Provider 以硬件多播向多个目标发送 | 条件能力 |

软件 Staging 若使用 Host DDR Payload，必须记录 Host Touch 和成本；优先使用不增加 CPU Payload 的 UBMEM/设备侧 staging。三组均遵守相同 Ready、Lease、Rank 和 security domain。

### 3. Fanout Provider 接口

```text
queryMulticastCapability(topology, target_count, object_size) -> Capability
submitFanout(source, targets[], descriptor, deadline) -> FanoutTicket
queryPerTarget(ticket) -> TargetResult[]
cancelTarget(ticket, target) -> CancelResult
release(ticket) -> Lease/Refcount cleanup
```

每个目标独立记录 Completion/Fence/Integrity/Ready；慢或失败 Consumer 不能阻塞已完成目标，也不能使 Source Lease 永久泄漏。

### 4. 实验矩阵

- 1 个 Source，2/4/8 Consumer；平台允许时增加 16 作 stretch；
- 对象 1MB～64MB，至少小/大两档；
- 正常、慢 Consumer、单目标断链/Crash；
- 同机、同机架、跨机架（若能力声明支持）；
- Independent、Software Staging、Hardware Multicast；
- 固定热点前缀、相同 deadline、相同 security domain；每 case ≥3 次。

### 5. 执行步骤

1. 从 PVT-00 提取实际 Fanout 和重复远端字节分布，预注册确认性 N/对象范围；
2. 校准单播链路和 Source egress 上限；
3. 运行 Independent Pull，记录每目标完成、源端 bytes/CPU/BW 和重复拉取；
4. 运行 Software Staging，验证首次获取、引用计数、下游分发和清理；
5. 若硬件支持，运行 Multicast，生成每目标 ActualPathReceipt；
6. 注入慢 Consumer、单目标失败、Lease 超时和目标 Ready 失败；
7. 比较源端 egress、完成 P99、Consumer skew、CPU/NIC、握手/建组成本和错误共享；
8. 计算按 N/对象/拓扑的 crossover；
9. 对达到 crossover 的 case 在真实框架负载中旁路复核；
10. 输出 Provider feature flag、目标数/对象/拓扑白名单和回退。

### 6. 指标与判定

关键指标：源端/全网 bytes、源端 BW/CPU、各 Consumer P50/P99、最慢目标、skew、重复拉取、租约/refcount 泄漏、错误共享、建组/撤销开销。

- Go：重复远端流量下降 ≥50%，源端带宽增长显著低于 O(N)，错误共享/泄漏=0；硬件 Multicast 相对软件 Staging 在确认性场景有可重复的端到端净收益。
- Conditional：硬件无额外净收益，正式架构保留软件 Node-level Staging；或硬件只在限定 N/对象/拓扑开启。
- No-Go：收益无法覆盖握手、同步和尾延迟；关闭硬件 Provider。
- Not Supported：目标平台无 Multicast 或无法生成每目标完成/完整性证据。

### 7. 交付与工作量

6～8 人日（触发后）：软件/硬件 Provider 3～4，故障/Lease 1～2，性能/报告 2。交付 Fanout crossover、源端放大曲线、per-target 正确性、feature flag、回退和是否进入 Async DAG 可选 Provider 的结论。

## CVT-02：软件 RCU + Copy-on-Migrate 与硬件 Atomic Remap 证伪

### 1. 决策与触发门

验证迁移/碎片整理中的硬件 Atomic Remap 是否相对软件 RCU + Copy-on-Migrate 产生稳定净收益，且可在任意故障点可靠回滚。默认正式路径是软件 RCU；硬件 Remap 不是项目成立前提。

正式关联：IR-01-01、01-11、01-12；SR23-01-01-03、01-11-01、01-12-02；SRS `L3-CO-MigrationRCULock-090`、`L4-CO-AtomicRemapPrimitive-065`。

建议触发证据：PVT-05 表明碎片/迁移暂停或 TLB/映射切换已成为 SLO 瓶颈，且软件 RCU 已正确实现；目标平台提供可验证的原子 Remap、IOMMU/SMMU/TLB 和 Fence 语义。

### 2. 三组方案

- Stop-the-world：暂停 Reader、复制、切指针、恢复，作为负面对照；
- Software RCU + Copy-on-Migrate：Reader 持旧 Extent，目标完整 Ready 后发布新版本，经 grace period 释放旧空间；
- Hardware Atomic Remap：目标数据和证据完成后执行原子映射切换，并处理 IOMMU/SMMU/TLB shootdown。

三组不得用 CPU 对 Payload 全量 CRC 补充本地 DDR 迁移校验；按路径使用既有 IntegrityEvidence。

### 3. RCU 状态与不变量

```text
OLD_ACTIVE
  -> COPYING(target allocated, old still readable)
  -> TARGET_VERIFIED(completion + fence + integrity)
  -> PUBLISHED(new epoch/placement)
  -> GRACE_PERIOD(no new old readers)
  -> OLD_RELEASED
```

不变量：

- 任何 Reader 只能看到完整旧版本或完整新版本；
- 目标证据未齐不能 Publish；
- Publish/Remap 失败仍可继续读旧 Extent；
- Grace Period 未结束不能释放旧空间；
- 崩溃恢复从 CommitLog 判断旧/新权威版本；
- Rollback 不返回已释放/半写映射。

### 4. 实验矩阵

- Extent 4MB、16MB、64MB；
- Reader 1/8/32；
- 连续读、随机读、Decode 模拟；
- Stop-the-world、RCU、Hardware Remap；
- 故障点：复制前/中/后、Fence 前/后、Publish/Remap 前/中/后、Grace Period；
- 正常、CPU/NPU 高负载、频繁迁移；每 case ≥3 次。

### 5. 执行步骤

1. 先完成软件 RCU golden/fault suite，证明错误读/越界/use-after-free=0；
2. 运行 Stop-the-world，得到暂停和 TPOT 抖动上界；
3. 运行 RCU，记录 copy、publish、grace、释放和 TLB 行为；
4. 接入硬件 Remap，显式记录指令、Fence、IOMMU/SMMU/TLB shootdown 和 ActualPathReceipt；
5. 对三个方案执行相同 Reader/Extent/负载矩阵；
6. 在每个状态边界注入进程 Crash、设备错误或 Remap 失败，重启后检查权威版本和回滚；
7. 运行长循环，检查映射/Lease/Extent 泄漏和地址复用竞态；
8. 比较 pause P99、TPOT jitter、额外内存、copy/remap 时延、TLB shootdown 和恢复；
9. 确定硬件增量是否稳定且足以改变路线；
10. 默认保留 RCU，只有 Go 才把 Remap 放在 feature flag 后。

### 6. 判定

- Go：脏读/越界=0，迁移 TPOT 抖动 <5%，失败 100% 可回滚，且硬件 Remap 相对 RCU 有稳定净收益。
- Conditional：硬件收益不显著或只在特定 Extent/并发成立；正式默认固定 RCU + Copy-on-Migrate，Remap 仅白名单。
- No-Go：语义不成熟、无法可靠回滚、TLB shootdown 惩罚抵消收益，或出现任何 use-after-free。
- Not Supported：平台无原子映射/必要可见性与错误语义。

### 7. 交付与工作量

8～12 人日（触发后）：RCU/CommitLog 3～4，硬件 Remap 2～3，Fault/Crash 2～3，分析 1～2。交付 RCU 正式基线、Remap Capability、崩溃恢复证据、迁移互锁接口、feature flag 和 No-Go/Go 报告。

## CVT-03：DPU/CQ 路由与硬件 Codec 纯增量验证

### 1. 决策与触发门

验证 DPU CQ/Route 卸载或硬件 Codec 是否在 Raw Direct 主路径已经独立成立的前提下带来纯增量。无 DPU/Codec 时系统必须正常运行；任何卸载故障必须旁路到 Raw Direct，禁止 CPU 软件压缩/解压/全量 CRC 成为回退。

正式关联：IR-01-08、01-09；SR23-01-08-01/02、01-09-01、01-12-01；SRS `L4-MC-HIER-STORE-002/003`、`L4-NET-OFFLOAD-DPU-001`、`L4-FT-PathIntegrityPolicy-077`。

建议触发证据：PVT-01 Raw Direct 已达到正确性和路径门，Host 控制提交/CQ/路由或介质带宽成为瓶颈；目标平台存在硬件 DPU/CQ/Codec，且结论影响采购或 P3 路线。

### 2. 方案组

| 组 | 说明 |
|---|---|
| Raw Direct | Host 只控制提交，不触碰 Payload；无 DPU/Codec，必须成立 |
| DPU CQ/Route | 卸载完成通知、路由表或明确支持的数据处理 |
| Hardware Codec | 设备侧在线压缩/解压，并直接生成可消费布局 |
| DPU/Codec Fault Bypass | 中途关闭/错误，旁路 Raw Direct |
| CPU Software Codec | 仅负面对照，用于证明 CPU 吞噬；不得作为候选或回退 |

### 3. Capability 契约

```text
OffloadCapability:
  operations, supported_layouts, object_size_range, concurrency,
  codec_format/version, precision_contract,
  host_payload_touch, extra_dma_hops, completion/integrity,
  bypass_path, fault_semantics
```

硬件 Codec 的压缩比不是单独成功指标；必须同时满足格式/精度、额外时延、TPOT、Host Touch 和故障旁路。

### 4. 实验矩阵

- 对象 1MB、16MB；可增加 64MB 作敏感性；
- 并发低/中/高三档；
- Raw、DPU CQ/Route、Hardware Codec；
- 正常、卸载通道故障、设备过载、格式不支持；
- 数据分布：可压缩/不可压缩/代表真实 KV；
- 在线热路径与冷数据后台存储分开；每 case ≥3 次。

### 5. 执行步骤

1. 复核 PVT-01 Raw Direct 的 ActualPathReceipt、Host Touch=0 和性能；
2. 记录 Host 在 descriptor、CQ、route lookup 的 CPU/cycles/latency 分解；
3. 接入 DPU CQ/Route，仅启用一种卸载，避免无法归因；
4. 接入硬件 Codec，验证编码版本、layout、数值/输出正确性和设备侧全链；
5. 对各方案运行对象×并发矩阵，记录 Host CPU、CQ、route、带宽、压缩比、额外 DMA、TTFT/TPOT；
6. 在稳态中关闭/故障 DPU/Codec，验证 100% 旁路 Raw Direct 且不增加 Host Touch；
7. 运行 CPU 软件 Codec 负面对照，但不进入 Go 候选；
8. 比较端到端净收益、单位事务成本和硬件采购敏感性；
9. 判断只卸载控制、只用于冷数据、白名单或完全关闭；
10. 输出 CapabilityMatrix、Not Supported/Go、feature flag 和旁路演练。

### 6. 判定

- Go：Host CPU ≥-30%，端到端净收益为正，故障可无损旁路 Raw Direct，Host Payload Touch 不增加。
- Conditional：只卸载 CQ/路由，或 Codec 只用于冷数据后台；硬件缺失时 Raw Direct 不受影响。
- No-Go：增加 PCIe/DMA/TPOT 延迟、格式/精度不闭环，或试图以 CPU 软件 Codec/CRC 伪造效果。
- Not Supported：平台无硬件能力或不能直接生成可消费布局/完整性证据。

### 7. 交付与工作量

5～8 人日（触发后）：DPU/Codec Adapter 2～3，故障旁路 1～2，性能/正确性/报告 2～3。交付能力表、ActualPathReceipt、Host Touch 对账、Not Supported/Go 报告、feature flag 和可选 Backend Provider；主路径始终保留无 DPU/Codec 的 Raw Direct。
